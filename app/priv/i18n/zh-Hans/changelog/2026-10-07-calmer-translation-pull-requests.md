%{title: "更平稳的翻译合并请求", summary: "从让 Glossia 在繁忙仓库中运行自如中所学到的经验，以及翻译合并请求因此产生的变化。"}
---

你的工具第一次遇到真正的项目仓库时，你会学到很多。对我们来说，那就是 Tuist。他们的团队每天多次向 `main` 合并，而 Glossia 完全实现了我们构建它的初衷：翻译每一次变更，并在每个文件准备就绪后立即推送。结果是几乎每次合并都会产生一个新的拉取请求，每个请求包含约 150 个提交，CI 队列中还充满了无人要求的检查。他们的一些文档页面在返回时，其中的组件和警报也变成了纯文本。这并非我们要反复提及的那种安静、后台的体验。

这让我们很不安，因为我们一直说最好的翻译系统是用户无需思考的那种。一个在 CI 中泛滥或破坏文档的 pull request 恰恰相反。所以我们回去重新思考了翻译如何抵达您的仓库。

Glossia 现在为每个项目维护单个 pull request，并根据您的内容变化扩展它。它会读取该分支上已有的锁文件，因此只翻译新增内容，并以批量方式推送而非一个个文件。对于 Tuist 这样的仓库，这意味着只有几个推送，而过去是 150 个。

我们也停止触碰您文档中不属于我们处理的部分。Glossia 过去会重建它翻译的每一页，任何它无法完全理解的东西，比如 Phoenix 组件或 GitHub 警告，结束后可能被逃逸出来。现在它只替换翻译的语句，其他部分完全保留您原文的样子。还有一个我们始料未及的美妙副作用：因为模型现在能看到完整句子和页面其余部分，翻译读起来更自然。以日语为例，链接不再需要别扭地出现在英文句子中的位置。

最后，这个 pull request 现在会告诉您发生了什么。哪些语言和文件被翻译了，来自哪些提交，分数如何，哪些词典术语塑造了它们，以及有什么需要您关注。我们把它看作一位细心的同事在请求审查前留给您的便签。

感谢 Tuist 团队在我们弄清楚这个问题时的耐心。如果 Glossia 再次像这样挡到您的路，我们希望听到您的反馈。
