Glossia 为每个项目仅保留一个开放的翻译拉取请求。针对默认分支的新提交会延续该分支，而不是为每个源提交创建新的拉取请求。在前一个拉取请求合并或关闭后，才会创建新的拉取请求。

发布和会话替换共享一个由数据库支持的项锁，包括当它们在应用不同的复本或独立运行器上运行时。如果运行器创建了拉取请求但无法保存其元数据，下一次发布会在 GitHub 上恢复开放的 Glossia 拉取请求，然后再创建另一个。当分支与源冲突或源历史记录被重写时，开放的拉取请求不会被放弃：会话会失败并保留现有的发布以便于解决。

## 推送限制

该限制固定为 **每小时每个项目 4 次推送**，在所有会话和复本之间共享。目前尚不可配置。

推送是均匀间隔的，并不是按固定的时钟小时区间计数。分支更新至少间隔 15 分钟。下一次间隔从一次发布尝试结束后开始，因此慢批处理不能紧随快批处理之后。源分支合并、中间批次、重试和最终刷新都共享相同的预算。不确定的失败尝试也会占用一个槽位，因为 GitHub 可能在连接失败前已经更新了分支。预算存储在 PostgreSQL 中，不会因新会话或进程重启而重置。

## 批处理

一次运行会收集已验证的文件变更，并在 25 个文件或 15 分钟后请求发布。这些阈值不会绕过推送限制。在冷却期，额外的已完成文件会加入待处理批次；对同一路径的重复变更将保留最新内容。

在运行结束时，最终刷新会等待相同的预算。会话保持活跃并在等待时发送心跳。它会定期重新检查取消和准入，在休眠期间不会保持数据库事务开放。
