Glossia 每个项目只保留一个开放的翻译合并请求。新的默认分支提交会延续该分支，而不是为每个源提交创建一个合并请求。之前的合并请求合并或关闭后，才会创建新的合并请求。

发布和会话替换共享基于数据库的项目锁，即使它们在不同的应用副本或独立运行器上运行时也是如此。如果运行器创建了合并请求但无法保存其元数据，下次发布会从 GitHub 恢复现有的开放 Glossia 合并请求，然后再创建新的一个。当合并请求的分支与源冲突或源历史被重写时，开放的合并请求不会被遗弃：会话会失败并保留现有的发布记录以待解决。

## 推送限制

限制固定为 **每个项目每小时 4 次推送**，在会话和副本间共享。目前尚不可配置。

推送间隔均匀，不计入固定的整点时段。分支更新至少间隔 15 分钟。下一个间隔从发布尝试完成后开始，因此慢速批次后不能立即跟随快速批次。源分支合并、中间批次、重试和最终刷新都共享相同的预算。不明确失败的尝试也会消耗一个槽位，因为 GitHub 可能在连接失败前已经推进了分支。预算存储在 PostgreSQL 中，不会因新会话或进程重启而重置。

## 成批处理

运行会收集已验证的文件变更，在 25 个文件或 15 分钟后请求发布。这些阈值不会绕过推送限制。在冷却期间，额外的已完成文件将加入待处理批次；对同一路径的重复变更保留最新内容。

运行结束时，最终刷新等待相同的预算。会话保持活跃并在此期间发送心跳。它会定期重新检查取消和准入，但在休眠期间不会保持数据库事务开启。
