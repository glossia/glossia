Glossia 每个项目只保持一个开放的翻译拉取请求。针对默认分支的新提交会延续该分支，而不是为每个源提交创建拉取请求。仅在上一轮拉取请求已合并或关闭后，才会创建新的拉取请求。当一个已关闭的发布获取了新的分支名称——包括在重试同一源提交时；其被拒绝的输出不会被复用作已完成的工作。

源同步发生在评估之前的一次性本地检出中，保留开放分支的已完成翻译和锁文件。运行若未发现输出或锁文件变更，则不会仅为了追赶默认分支而推进远程分支，也不会消耗发布槽位。当批次准备就绪，源同步与验证后的变更将合并到一次非强制分支更新中。该保留提交记录将上一发布与经评估的源提交均作为祖先保留。

发布与会话替换共享基于数据库的项目锁定，即使它们在应用程序的不同副本或独立运行器上运行时也是如此。如果运行器创建了拉取请求却无法保存其元数据，下一次发布会在创建一个新请求前从 GitHub 恢复开放的 Glossia 拉取请求。当拉取请求的分支与源冲突或源历史被重写时，开放的拉取请求不会被放弃：会话将失败但保留现有的发布以待解决。

## 推送限制

限制固定为 **每小时每项目 4 次推送**，在所有会话和副本间共享。目前不可配置。

推送均匀分布，不按固定的时钟小时字段统计。分支更新至少相隔 15 分钟。下一次间隔从发布尝试完成时开始，因此一个慢批次后不能立即跟随一个快批次。中间批次、重试和最终刷新均共享同一预算。状态不明的失败尝试同样会消耗槽位，因为 GitHub 可能在连接断开前已推进分支。预算存储在 PostgreSQL 中，且不会被新会话或进程重启重置。

发布前，Glossia 重新读取远程头部并在本地再次合并会话的源。这保留了批次并实现了不动分支地检测冲突。如果早期更新成功但响应丢失，已有的更改将不再被提交；发布元数据和拉取请求将在无需再次分支更新的情况下恢复。如果引用已创建但运行器在创建其拉取请求前停止，无变更评估仍会创建缺失的拉取请求，且不消耗分支更新槽位。

只有当异常远程推进的差异相对于预期的同步树是待发布批次中已存在的一部分时，才会接受这次推进。评估期间制作的其他修改将导致发布失败，而不是被覆盖或发布针对过时输入验证的翻译。保留现有拉取请求以待解决。

## 批处理

运行收集验证后的文件更改，并在收集到 25 个文件或经过 15 分钟后请求发布。这些阈值不会绕过推送限制。在冷却期间，额外的已完成文件加入待发布批次；对同一路径的重复更改保留最新内容。

运行结束时，最终刷新等待相同预算。会话在等待期间保持活跃并发送心跳。它在不持续持有数据库事务的情况下定期重新检查取消和准入状态。
