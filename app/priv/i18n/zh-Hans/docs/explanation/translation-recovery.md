Glossia 在发布翻译内容之前会验证其内容。恢复功能保留了这一要求：重试必须仍然保持源结构和必需的占位符，且每个生成的文件都通过其配置的验证命令。

## Markdown 翻译

Glossia 从不重新渲染已翻译的 Markdown 文档。它仅解析源内容以查找其文本质：段落、标题、列表项、表格单元格、组件面向读者的属性以及 HTML (`title`, `details`, `alt`, `label`, `description`, `summary`, `placeholder`, `aria-label`, `caption`），以及 HTML `<summary>` 中的文本。每个翻译都会写回源内容所占据的确切字节，因此代码、链接目标、组件、GitHub 警报、显式标题锚点（例如 `{#install}`）、列表标记和空行将保持逐字节完全相同。

每个段落或标题作为完整句子进行翻译。内联格式化为编号标签： `<gN>...</gN>`包围已链接或强调的单词， `<gN/>`用于必须不变的内容，例如内联代码或组件。模型可以移动标签以遵循目标语言的词序，但必须保留每个标签恰好一次。每个请求同时也携带周围的源文档，以及来自同一文件的最新翻译，以供参考。

如果某个单元丢弃或发明了标签，它会连同原因被单独重新发送，最多三次。返回有效的单元将被保留。拼接后，Glossia 解析结果并将其结构与源进行对比。如果某个翻译单独会变成标题、列表或强调，其文本将被转义，无需进一步的模型调用。

## 目录翻译

Gettext 目录在翻译前被解析为字符串。请求最多携带八个字符串，并以 8,000 字节的批处理为目标。单个较大的字符串将保持完整。模型返回按相同顺序包含相同数量字符串的数组。Glossia 检查插值变量并拒绝空翻译。

标题在代码中使用目标区域的复数规则构建。源消息标识符、注释和目录结构来自解析后的源。如果一批次返回损坏的内容，Glossia 会重试一次，然后将其拆分为更小的批次。成功的相邻批次无需再翻译。

## 提供商节流

Glossia 协调使用相同凭证和模型的翻译请求。限流响应会延长其共享冷却时间，并增加新请求之间的间隔。在没有发生流控的情况下，经过一分钟的成功流量会逐渐减少该间隔。允许已经运行的请求完成。

提供商重试提示表示最小延迟。重复的失败也会增加退避时间，最多为 30 秒基础延迟加上抖动；较长的提供商提示优先级更高，上限为五分钟。Together 的 `x-ratelimit-reset` 标头与 `retry-after` 一同被识别。

在八次请求尝试失败之后，仓库运行将停止开始新文件。延迟的续传会话将继承翻译分支并恢复未完成的工作。之前的尝试保留在会话历史中，通过该续传进行关联。延迟时间从一分钟增加到五分钟，最多进行六次自动续传。更新的活跃会话享有优先权，取消的会话永远不会恢复。仅凭验证失败不会安排提供商恢复。

## 引擎发布后的恢复

会话有两个独立版本：正在翻译的仓库提交和正在执行它的翻译引擎镜像。在 Kubernetes 中，每个任务都会固定调度它的 Web 副本的确切镜像摘要。任务可以度过 Web 发布，并在翻译中途永远不换代码。因此，在发布前刚刚安排的任务可以在之前的引擎上完成，即使 Web 应用程序已更新。会话详情会显示引擎摘要；没有此溯源的旧会话将显示“未记录”。

每五分钟，Glossia 会检查其部署是否已完全发布。只有来自该健康版本的 worker 才能调度引擎恢复。如果项目的最新会话在该部署完成之前就排队，运行在旧的已记录引擎摘要上，并且在随后六小时内失败，Glossia 可以在当前发布上创建续传。使用排队时间也覆盖了等待容量并在发布后仅启动的任务。不同的镜像摘要本身不会在不相关的部署后触发普通故障的重试。已完成的文件和正在进行的翻译拉取请求会保留；只有未完成的工作会再次翻译。排队的发布续传在发布进行期间等待，最多 15 分钟。Kubernetes API 或权限失败会以明确的错误停止启动，而不是被误认为是正在进行中的部署。

恢复是有目的的限制的：会话必须以已记录的条目验证失败结束，其最新尝试中的每个失败条目必须报告 Markdown 结构、保留内容或 Markdown 单元失败。中断或部分取消的尝试不符合条件。提供商错误、信用额度耗尽、凭证被拒绝、发布失败、源读取错误、外部验证命令失败和未知原因不会通过部署重试。成功、活跃、已取消、被替代和无版本化的会话也保持不变。即使用户取消，更新的会话也会获胜。

会话在另一个引擎发布上最多获取一次续传，处于族系中的发布续传最多三次。如果新引擎仍然失败，它不会在同一镜像上再次重试，包括在回滚之后。族系保留了其之前尝试的引擎摘要，启动器在创建队发送任务之前会再次检查它们。现有的提供商恢复限制在发布续传中得以保留。可变镜像标签和没有配置发布身份标识的部署不会启用自动引擎恢复。

## 持久化进度

已完成的文件及其锁定文件会分批发布到翻译分支：每 25 个文件一个提交，或每 15 分钟一个提交，运行结束时还有一个最终提交。每次推送都会运行仓库的拉取请求检查，因此分批处理可避免大型运行为每个文件启动一次检查运行。每个项目只有一个翻译拉取请求：默认分支上的新提交延续了该开启的拉取请求，并仅翻译自那时以来变更的内容。一旦该拉取请求被合并或关闭，下一次运行将启动一个新的拉取请求。在未完成的文件内部，经过本地验证的片段和恢复批次也会被保存在数据库中七天。这些检查点能够在 worker 进程停止后得以保留。它们的作用范围限于账户、项目、文档输入、有效凭据和模型、上下文，以及片段或修复尝试。

恢复运行仅在输入仍然匹配时才能重用片段。它总是会再次验证最终组装的文档。被拒绝的模型响应不是检查点。由于验证器可能无法识别单个负责的片段，文档级验证失败会启动一个单独的修复尝试。

过期的检查点和不活跃的提供商配速记录将由计划的会话恢复 worker 移除。这些是运维记录；用户无需将它们添加到其仓库或在`L10N.md`中配置它们。
