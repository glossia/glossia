Glossia 在发布翻译内容之前会进行验证。恢复保留了这一要求：重试必须仍然保留源结构和必需的占位符，且每个生成的文件都通过其配置的验证命令。

## Markdown 翻译

Glossia 不会重新渲染翻译后的 Markdown 文档。它仅解析源代码以查找其正文：段落、标题、列表项、表格单元格、组件和 HTML 的面向读者的属性（`title`, `details`, `alt`, `label`, `description`, `summary`, `placeholder`, `aria-label`, `caption`）以及 HTML `<summary>` 的文本。每个翻译都会被写回其源占用的确切字节，因此代码、链接目的地、组件、GitHub 警报、明确的主标题锚点（例如 `{#install}`）、列表标记和空行保持字节级完全相同。

每个段落或标题都作为完整的句子翻译。内联格式化变为编号标签： `<gN>...</gN>` 围绕链接或强调的词语，和 `<gN/>` 用于必须保持不变的内容，例如内联代码或组件。模型可以移动标签以遵循目标语言的词序，但必须精确保留每一个标签。每个请求还携带周围的源文档以及来自同一文件的最新翻译数据以供参考。

丢失或编造标签的单元会伴随着原因单独发送，最多三次。返回有效内容的单元将被保留。在拼接后，Glossia 解析结果并将其结构与其源进行对比。如果翻译单独会变成标题、列表或强调，则其正文会被转义，这不需要进一步的模型调用。

## 目录翻译

Gettext 目录在翻译前会被解析为字符串。请求携带最多八个字符串，目标是 8,000 字节的分批处理。单个较大的字符串保持完整。模型返回一个包含相同数量的字符串的数组，顺序相同。Glossia 检查插值变量并拒绝空的翻译。

标题是在代码中根据目标区域的复数规则构建的。源消息标识符、评论和目录结构来自解析后的源。如果一批数据返回格式错误的信息，Glossia 将重试一次，然后将其分割成更小的批次。成功的相邻批次不需要再次翻译。

## 提供商限速

Glossia 协调使用相同凭据和模型的翻译请求。速率限制响应会延长其共享的冷却时间，并增加新请求之间的间隔。在一个月内无需限速的流量会逐渐减少该间隔。已运行的请求允许完成。

提供商重试提示是最小延迟。重复失败也会增加退避时间，最高为 30 秒基础延迟加上抖动；较长的提供商提示优先，上限为五分钟。Together 的 `x-ratelimit-reset` 标题与 `retry-after` 一同被识别。

在八次未成功请求尝试后，仓库运行将停止启动新文件。延迟的延续将继承翻译分支并恢复其未完成的工作。先前尝试在会话历史中保持可见，通过延续进行链接。延迟从一分钟增加到五分钟，最多进行六次自动延续。较新的活动会取得优先权，而被取消的会话永远不会被恢复。单纯的验证失败不会触发提供商恢复。

## 引擎发布后的恢复

会话有两个独立版本：正在翻译的仓库提交和正在执行它的翻译引擎镜像。在 Kubernetes 中，每个作业固定了调度它的 Web 副本的确切镜像摘要。作业能够经受 Web 发布并在翻译中途不会切换代码。因此，在发布前一刻调度的作业即使在 Web 应用程序更新后也能够在旧的引擎上完成。会话详情显示引擎摘要；没有这种来源的旧会话显示“未记录”。

每五分钟，Glossia 检查其部署是否完全发布。只有来自该健康版本的 worker 才能调度引擎恢复。如果项目的最新会话在该发布完成前排队，然后在较旧的已记录引擎摘要上运行，并在过去六小时内失败，Glossia 可以在当前版本上创建延续。使用排队时间也包括那些等待容量且在发布后才启动的作业。不同的镜像摘要本身不会在无关部署后触发普通错误的重试。已完成的文件和开放的翻译拉取请求会保留；只有未完成的工作会被再次翻译。排队的发布延续在发布进行中时等待，最多 15 分钟。Kubernetes API 或权限失败会通过明确的错误停止启动，而不是被误认为是持续进行的发布。

恢复是有意狭窄的：会话必须以记录的条目验证失败结束，且其最新尝试中的每个失败条目都必须报告 Markdown 结构、保留内容或 Markdown 单元失败。中断或部分取消的尝试不符合条件。提供商错误、耗尽的信贷、被拒绝的凭据、发布失败、读取源错误、外部验证命令失败和未知原因不会通过部署重试。成功、活跃、已取消、被取代和无版本会话也保持不变。即使用户取消了它，较新的会话总是优先。

会话在不同引擎版本上最多获得一次延续，谱系中至多有三个发布延续。如果新引擎仍然失败，它不会在同一镜像上再次重试，包括回滚后。谱系保留其先前尝试过的引擎摘要，启动器在创建排队作业前会再次检查它们。现有的提供商恢复限制在发布延续期间得到保留。可变的镜像标签和没有配置发布标识的部署不会启用自动引擎恢复。

## 持久进度

已完成的文件和其锁文件以批次形式发布到翻译分支：每 25 个文件进行一个提交，或每 15 分钟进行一个提交，运行结束时进行最终提交。每次推送都会运行仓库的拉取请求检查，因此批次处理可避免为每个文件启动单独的检查运行。项目只有一个翻译拉取请求：默认分支上的新提交延续了当前开放的拉取请求，且仅翻译自上次以来的更改。该拉取请求被合并或关闭后，下一次运行会启动新的拉取请求。在未完成的文件中，本地验证过的段和恢复批次也会保存在数据库中七天。这些检查点在 worker 进程停止后依然存在。它们的范围限定于账户、项目、文档输入、有效凭据和模型、上下文、以及段或修复尝试。

恢复运行仅在其输入仍匹配时才能重用段。它总是重新验证最终组装的文档。被拒绝的模型响应并非检查点。文档级别的验证失败会触发独立的修复尝试，因为验证器可能无法识别单个负责的段。

过期的检查点和不活跃的提供商速率控制记录将由计划的会话恢复 worker 移除。这些是操作记录；用户无需将它们添加到仓库，或在 `L10N.md` 中配置它们。
