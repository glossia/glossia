词汇表是一组精心筛选的术语，你的翻译必须每次都一致呈现。版本控制概念中的“Commit”保持 `commit`，在简体中文中变为 `提交`，在日语中变为 `コミット`。每种语言一个决策，强制执行。

## 词汇表可以存放的两个位置

Glossia 会在两个地方寻找词汇表条目，并在翻译时合并它们：

- **您的仓库**，在您已用于翻译设置的文件中。`L10N.md` 声明术语，每种语言的 `L10N/<locale>.md` 声明它们的翻译。这是开发者主导的词汇表：更改通过拉取请求进行，每种语言的评审员拥有自己的文件，嵌套文件可以针对仓库的一部分对其进行细化。
- **您的 Glossia 账户**，通过托管仪表板进行管理。这是语言专家主导的词汇表：评审员和本地化贡献者可以通过仪表板、[REST API](/docs/reference/apis)或[MCP 服务器](/docs/reference/mcp)添加或优化条目，而无需触碰代码。它适用于账户翻译的所有仓库。

两个地方都很实用，且互不取代。

## 何时使用哪一个

在 **你的 Glossia 账户** 中定义术语的情况：

- **它适用于多个仓库。** 产品名称、品牌术语和公司词汇只需定义一次，并到处使用。
- **决定术语的人员不在仓库内工作。** 语言学家、评审员和外部贡献者即使仓库是私有源码或他们没有写入权限，也可以优化词汇表。
- **您希望在无代码更改的情况下修复术语。** 更正后的翻译在下一次运行中生效，无需针对代码库提交拉取请求。
- **更改需要审查和记录。** 每次编辑都会创建一个带有变更说明的新版本，贡献者可以以建议的形式提出更改供某人批准，且早期版本保持可用。
- **其他工具需要它。** 代理和集成可以通过 REST API 和 MCP 服务器读取词汇表，例如生成已使用已批准术语的新内容。

在 **您的仓库** 中定义术语的情况：

- **它属于此代码库。** 含义特定于一个项目的术语，例如版本控制动作的“commit”，就放在使用该术语的代码旁边。
- **它应随原文档同步更改。** 术语和引入它的文案在同一个拉取请求中落脚，并一起接受审查。
- **只有仓库的一部分需要它。** 嵌套的 `L10N.md` 或 `L10N/<locale>.md` 可以针对一个目录添加或覆盖条目，如营销页面。
- **它必须覆盖账户词汇表。** 对于该术语及它翻译的语言，仓库条目优先于账户条目。

## 它们如何结合

对于每个文件和目标语言，Glossia 将两个词汇表解决为一个有效集合：

1. 首先，以目标语言的账户词汇表条目为起点。
2. 叠加该语言的仓库条目：即来自文件 `L10N.md` 链中在 `L10N/<locale>.md` 链中具有翻译的术语。当仓库条目与账户条目具有相同的源术语时，仓库条目胜出。
3. 如果某单词在一种语言中没有翻译，该语言的账户条目仍然适用。仓库绝不会阻止它未曾翻译的语言。

合并是 **按目标语言分别进行** 的，而非按条目。在 `L10N/es.md` 中“提交”的西班牙语翻译会替换账户中“提交”的西班牙语条目，但不会影响账户中该术语的日语条目。审核人员可以查看哪些账户条目被替换：翻译会话摘要显示有多少个被覆盖，每个文件的锁文件在 `glossary.shadowed` 下列出它们。

## 词汇表变更时，文件重新翻译

当你编辑词汇表条目时，Glossia 仅重新翻译那些 *有效词汇表发生变化* 的文件。如果文件源文本不包含编辑术语的匹配项，其翻译保持原状。如果文件使用该术语，其下一次翻译过程将包含更新后的说明。

相同的原理也适用于反向操作：仅为部分文件添加术语并不强制完整重新运行。

## 词汇表不是什么

- 不是机器翻译词典。Glossia 的模型会读取周围上下文，若句子需要，可以以不同方式呈现术语。词汇表是指引，而非替换。
- 不是完整的风格指南。语音、语气、正式度和受众存在于您的账户的声音配置以及 `L10N.md` 中。词汇表仅用于单个术语及其批准的翻译。
- 并非静默。每个应用的术语都被记录在文件锁定文件中，以便评审员可以确切追踪哪些词汇表条目到达了模型。
