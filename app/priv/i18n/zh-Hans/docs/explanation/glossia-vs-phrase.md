**当您需要语言工作遵循产品交付系统，而不是为其建立并行翻译管理流程时，选择 Glossia。** 将内容保留在 Git 中，使用自己的凭据选择支持模型，并使用仓库已信任的检查验证结果。

[Phrase](https://phrase.com/) 提供一套本地化工具包，包括用于不同软件本地化和托管翻译需求的 Phrase Strings 和 Phrase TMS。Glossia 采用专注的方法：为软件团队提供一个符合其现有审查和交付循环的语言操作系统。

## 为何选择 Glossia

| 您的优先级 | Glossia 的优势 |
|---|---|
| 随软件交付语言变更 | 仓库变更驱动本地化，输出以可审查变更形式返回。 |
| 审查并掌控处理过程 | 公开源代码可见应用和部署实现，根据许可证条款允许修改和自托管。 |
| 自备令牌 | 配置您自己的支持模型提供商凭据；通过仓库配置中的账户句柄选择模型。 |
| 复用验证管道 | 运行原生仓库检查，而不是将语言审批视为文件可构建的证明。 |
| 保持持久所有权 | 发布的文件、配置和拉取请求历史记录保留在仓库中。 |

## 将本地化作为持续交付的一部分

Glossia 的变更检测避免了为未更改的输入重复翻译工作。其仓库工作流为每个项目保留一个开放的翻译拉取请求，并以批次发布进度，因此快速迭代的源代码仓库无需为每个小变更创建新的翻译流程。

目标并非未经审查的上线冲刺。而是使语言工作能够通过您团队已使用的管道持续可审查和交付。

Phrase 也提供 API、集成功能和自动化工具。Glossia 强调的优势在于架构对齐：仓库仍然是内容权威和交付边界，而不仅仅是同步另一个工作区结果的场所。

## 将模型选择与凭据掌握在自己手中

Glossia 接受支持模型的使用方 API 令牌。凭据保留在账户设置中；仓库选择稳定的句柄。团队可以轮换令牌或更改句柄背后的模型，而无需重写其仓库指令。

不同的内容范围和目标语言可以使用不同配置的模型。可选决策模型可评估完整翻译并提出修正请求，而人类对语言判断负责。查看 [账户模型](./account-models) 了解当前行为和限制。

## 您的仓库已了解有效内容的含义

翻译管理系统对字符串的视图不一定与应用对文件的视图相同。仓库可能拥有自己的解析器、编译器、组件规则、文档构建和占位符检查。

Glossia 可以通过 `L10N.md` 验证命令复用这些检查。该命令及其依赖项必须在执行环境中可用。

这使得团队可以扩展现有的质量边界，而不是仅在翻译工作区内单独维护“有效”的定义。查看 [L10N.md](/docs/reference/l10n-md)。

## 公开实现，而非黑盒

Glossia 的应用程序、CLI、SDK 和部署源是公开的。您可以检查内容处理方式，并根据 [O'Saasy license](https://github.com/glossia/glossia/blob/main/LICENSE.md) 修改或自托管该实现。该许可证限制竞争性托管服务，并非不受限制的开源许可。

更广泛的翻译套件对于专业翻译运营和复杂协调可能更有意义。如果您的优先事项是 **用自己的令牌和仓库检查来匹配软件交付速度**，Glossia 旨在保持该工作流程的直接性。

迁移已建立的翻译计划仍需为其记忆、术语和历史制定计划。本页面不承诺自动 Phrase 导入程序或全套套件平齐，也不断言 Phrase 缺乏所有等效集成。查阅 [Phrase 的文档](https://support.phrase.com/) 了解特定产品的当前功能。
