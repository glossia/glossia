**当您需要语言工作遵循产品的交付系统，而不是围绕它建立一个平行的翻译管理流程时，请选择 Glossia** 将内容保留在 Git 中，使用您自己的凭证选择支持的模型，并使用您的存储库已信任的检查验证结果。

[Phrase](https://phrase.com/) 提供一套本地化工具，包括适合不同软件本地化和托管翻译需求的 Phrase Strings 和 Phrase TMS。Glossia 采取专注的方法：为软件团队提供一个契合其现有评审和交付循环的语言操作系统（OS）。

## 为什么选择 Glossia

| 您的优先级 | Glossia 的优势 |
|---|---|
| 随软件交付语言更改 | 存储库变更驱动本地化，输出以可评审的变更形式返回。 |
| 检查并掌控处理过程 | 公开源代码揭示了应用程序和部署实现，在许可条款允许下可进行修改和自托管。 |
| 自行携带 Token（令牌） | 配置您自己的支持模型提供商凭证；通过存储库配置中的账户句柄选择模型。 |
| 复用验证管道 | 在处理翻译候选项运行时使用存储库原生的检查，而不是将语言批准视为文件可构建的证明。 |
| 保持持久所有权 | 发布的文件、配置和拉取请求历史记录保留在存储库中。 |

## 将本地化作为持续交付的一部分

Glossia 的变更检测避免了对未更改输入重复翻译工作。其存储库工作流每项目保持一个开放的翻译拉取请求，并以批次形式发布进度，因此快速迭代的内容存储库不需要为每个微小变更创建新的翻译流程。

目标不是未经评审的进入生产竞速。而是使语言工作能够持续被评审并通过团队已使用的管道进行交付。

Phrase 也提供 API、集成和自动化。Glossia 强调的优势是架构对齐：存储库仍然是内容权威和交付边界，而不仅仅是同步另一个工作流程结果的场所。

## 将模型选择和凭证的控制权掌握在自己手中

Glossia 接受您自己为支持模型提供的提供商 API Token。凭证保留在账户设置中；存储库选择稳定的句柄。团队可以在不重写其存储库说明的情况下轮换令牌或更改句柄背后的模型。

不同的内容范围和目标语言可以使用不同的配置模型。可选的决策模型可以评估完整的翻译并请求更正，而人类保留对语言判断的负责权。请查看 [账户模型](./account-models) 了解当前行为和限制。

## 您的存储库已经知道有效内容的含义

翻译管理系统对字符串的看法不一定就是应用程序对文件的看法。存储库可能有自己专用的解析器、编译器、组件规则、文档构建和占位符检查。

Glossia 可以通过 `L10N.md` 验证命令复用这些检查。它临时将候选项写入其真实的目标路径进行验证，并且仅在通过所需的检查后才接受它。该命令及其依赖项必须在执行环境中可用。

这使得团队能够扩展其现有的质量界限，而不是仅在翻译工作空间内维护“有效”的独立定义。请查看 [L10N.md](/docs/reference/l10n-md)。

## 公开实现，而非黑盒

Glossia 的应用程序、CLI、SDK 和部署源是公开的。核心在 [Apache-2.0](https://github.com/glossia/glossia/blob/main/LICENSE-APACHE) 协议下开源，允许修改、分发、自托管和竞争托管服务。`ee/` 下的企业代码拥有独立的 [许可证](https://github.com/glossia/glossia/blob/main/ee/LICENSE.md)，生产使用需要书面商业协议。

更广泛的翻译套件对于专门的翻译操作和复杂协调可能具有意义。如果您的优先级是 **将软件交付速度与您自己的令牌和存储库检查相匹配**，Glossia 旨在保持该工作流的直接性。

迁移既定的翻译计划仍需要为记忆库、术语和历史制定计划。本页不承诺自动的 Phrase 导入程序或完整的套件对等，也不断言 Phrase 缺乏所有等效集成。请查阅 [Phrase 的文档](https://support.phrase.com/) 以了解特定产品的当前功能。
