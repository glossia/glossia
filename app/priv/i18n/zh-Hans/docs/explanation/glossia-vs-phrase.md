**选择 Glossia 当您希望语言工作跟随产品的交付系统展开，而不是围绕它建立一套平行的翻译管理流程时。** 将内容保留在 Git 中，使用您的凭据选择支持的模型，并利用您的仓库已信任的检查来验证结果。

[Phrase](https://phrase.com/) 提供一套本地化套件，包括适用于不同软件本地化和托管翻译需求的 Phrase Strings 和 Phrase TMS。Glossia 采取专注的方式：为软件团队提供一个契合他们现有审查和交付循环的语言操作系统。

## 为何选择 Glossia

| 您的优先级 | Glossia 的优势 |
|---|---|
| 随软件发布语言变更 | 仓库变更驱动本地化，输出结果以可审查的变更形式返回。 |
| 审查并掌控处理过程 | 公开源码展示了应用和部署实现，在许可条款允许下可进行修改和自行托管。 |
| 自备令牌 | 配置您自己的支持模型提供商凭据；通过仓库配置中的账户手柄选择模型。 |
| 复用验证流水线 | 对候选译文运行仓库原生检查，而不是将语言批准视为文件可构建的证明。 |
| 保持持久所有权 | 已发布文件、配置和拉取请求历史均保留在仓库中。 |

## 将本地化纳入持续交付

Glossia 的变更检测避免了为未更改的输入重复翻译工作。其仓库工作流程为每个项目保持一个开放的翻译拉取请求，并按批次发布进度，因此快速变更的源仓库无需为每个微小变更启用新的翻译流程。

目标不是在未审查的情况下冲刺到生产环境。而是让语言工作能够通过您的团队已使用的流水线持续接受审查和交付。

Phrase 同样提供 API、集成和自动化。Glossia 强调的优势是架构对齐：仓库依然是内容权威和交付边界，而不仅仅是同步另一工作区结果的地方。

## 掌控模型选择和凭据

Glossia 接受您自己的提供商 API 令牌用于支持的模型。凭据保留在账户设置中；仓库选择稳定的手柄。团队可以轮换令牌或通过手柄更改模型，而无须重写其仓库说明。

不同的内容范围和目标语言可以配置不同的模型。可选决策模型可以评估完整翻译并请求修正，而人类继续对语言判断负责。有关当前行为和限制，请参阅 [账户模型](./account-models)。

## 您的仓库已了解有效内容的含义

翻译管理系统对字符串的视图不一定是应用对文件的视图。仓库可能有自己的解析器、编译器、组件规则、文档构建和占位符检查。

Glossia 可以通过 `L10N.md` 验证命令复用这些检查。它将候选内容临时写入真实目标路径以供验证，仅在通过必要的检查后才接受该候选内容。该命令及其依赖项必须在执行环境中可用。

这使得团队能够扩展其现有的质量边界，而不是仅在翻译工作区内维护“有效”的独立定义。参见 [L10N.md](/docs/reference/l10n-md)。

## 公开实现，而非黑盒

Glossia 的应用程序、CLI、SDK 和部署源码均为公开。您可以检查内容处理方式，并根据 [O'Saasy license](https://github.com/glossia/glossia/blob/main/LICENSE.md) 修改或自行托管该实现。该许可限制竞争性的托管服务，并非无限制开源许可。

更广泛的翻译套件对于专业翻译运营和复杂协调可能更有意义。如果您的优先事项是 **将自有令牌和仓库检查与软件交付速度相匹配**，Glossia 旨在保持该工作流程的直接性。

迁移现有的翻译计划仍需对其记忆、术语和历史进行规划。本页面不承诺提供自动 Phrase 导入器或全套套件对等性，也不断言 Phrase 缺乏所有等效集成。请参阅 [Phrase 的文档](https://support.phrase.com/) 以了解特定产品的当前功能。
