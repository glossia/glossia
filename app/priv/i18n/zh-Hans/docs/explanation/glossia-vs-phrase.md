**选择 Glossia 的情况是您希望语言工作跟随产品的交付系统，而不是围绕它建立平行的翻译管理流程。** 将内容保留在 Git 中，使用自己的凭证选择支持的模型，并使用 Git 仓库已有检查来验证结果。

[Phrase](https://phrase.com/) 提供本地化套件，包括 Phrase Strings 和 Phrase TMS，以满足不同的软件本地化和托管翻译需求。Glossia 采取聚焦的方法：为软件团队提供一个语言操作系统，适配他们现有的审核和交付循环。

## 为什么选择 Glossia

| 您的优先考虑 | Glossia 的优势 |
|---|---|
| 随软件交付语言变更 | 仓库变更驱动本地化，输出返回为可审核的变更。 |
| 审核并掌控处理流程 | 公开源码暴露应用和部署实施工序，许可证条款允许修改和自托管。 |
| 自带 token | 自行配置支持的模型提供商凭证；通过仓库配置中的账户句柄选择模型。 |
| 复用验证流水线 | 对翻译候选运行仓库原生检查，而不是将语言批准视为文件可构建的证明。 |
| 保持持久所有权 | 发布的文件、配置和拉取请求历史保留在仓库中。 |

## 让本地化成为持续交付的一部分

Glossia 的变更检测避免对未变更的输入重复翻译工作。其仓库工作流程为每个项目保持一个开放的翻译拉取请求，并按批次发布进度，因此快速迭代的源仓库无需为每个小变更建立新的翻译流程。

目标不是未经审核的生产竞速。而是让语言工作在您的团队现有管道中保持持续可审核和可交付。

Phrase 也提供 API、集成和自动化工具。Glossia 强调的优势是架构对齐：仓库保持内容权威和交付边界，而不仅仅是一个同步另一个工作区结果的地方。

## 将模型选择和凭证控制在您手中

Glossia 接受您为支持的模型提供自己的提供商 API token。凭证保留在账户设置中；仓库选择稳定的句柄。团队可以轮换 token 或更改句柄背后的模型，而无需重写其仓库指令。

不同的内容范围和目标语言可以使用不同的配置模型。可选的决策模型可以评估完整翻译并请求更正，同时人工保留语言判断的责任。查看 [账户模型](./account-models) 了解当前行为和限制。

## 您的仓库已经知道什么是有效内容

翻译管理系统对字符串的观点不一定等同于应用对文件的观点。仓库可能拥有自己的解析器、编译器、组件规则、文档构建和占位符检查。

Glossia 可以通过 `L10N.md` 验证命令复用这些检查。它将候选临时写入其真实目标路径进行验证，仅在所需检查通过后才接受。命令及其依赖必须在执行环境中可用。

这让团队可以扩展其现有质量边界，而不是在翻译工作区内单独维护'有效'的定义。查看 [L10N.md](/docs/reference/l10n-md)。

## 公开实现，而非黑盒

Glossia 的应用程序、CLI、SDK 和部署源码均公开。您可以检查内容处理方式，并根据 [O'Saasy 许可证](https://github.com/glossia/glossia/blob/main/LICENSE.md) 修改或自托管实施工序。该许可证限制竞争性托管服务，不是无限制的开源自许可。

更广泛的翻译套件对于专业翻译操作和复杂协调有意义。如果您的优先级是 **用自有 token 和仓库检查匹配软件交付速度**，Glossia 设计为保持该工作流程直接。

迁移已建立的翻译计划仍需要为其记忆、术语和历史制定计划。本页不承诺自动 Phrase 导入器或完整套件平等，也不断言 Phrase 缺乏所有等效集成。查看 [Phrase 的文档](https://support.phrase.com/) 了解特定产品的当前能力。
