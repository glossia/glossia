**当产品仓库需要保持多语言内容的权威时，请选择 Glossia。** 字符串、文档、配置及其检查已随您的应用程序演变。Glossia 将语言变更附加于该演变过程，而不是要求您的团队将托管编辑器作为发布权威。

[Lokalise](https://lokalise.com/) 提供协作本地化、翻译管理和开发者集成。Glossia 的提议更为具体：保留仓库工作流，自备模型凭证，重用现有的检查，并检查执行工作的系统。

## 为何选择 Glossia

| 您的优先事项 | Glossia 的优势 |
|---|---|
| 匹配软件交付速度 | 源代码变更驱动翻译工作；提出的输出通过仓库审查工作流返回。 |
| 掌控实施 | 公开源代码使处理过程可检查，并支持在许可条款下进行修改和自托管。 |
| 使用自己的模型令牌 | 账户级别的提供商凭证允许您选择支持的模型，而无需将密钥放入 Git。 |
| 验证真实的应用程序内容 | 仓库脚本可以检查应用程序预期找到候选项的位置。 |
| 保留清晰的审查边界 | 合并请求保持语言变更在用于审查产品的相同工具中可见。 |

## 将语言变更附加于产品变更

新的 UI 消息或文档部分不是一个孤立的翻译任务。它属于产品修订版，使用其术语，并必须与其结构配合工作。

Glossia 读取仓库拥有的 `L10N.md` 配置，使用内容和上下文变更来识别过期的翻译，并提出供审查的更新。审查人员看到实际文件和差异；发布管道保留在您手中。

Lokalise 也具有自动化和 Git 集成。Glossia 的区别在于预期的记录系统：您的仓库拥有发布的内容及其交付规则，而 Glossia 提供语言上下文和转换机制。

## 自备令牌而非固化单一模型选择

Glossia 允许您使用自己的提供商 API 令牌配置支持的模型。仓库使用稳定的模型句柄，因此轮换凭证或更新该句柄背后的模型不会要求更改每个项目。

嵌套配置和区域/语言特定指南可以选择特定区域或语言的不同的配置模型。这是明确的选择，而不是自动提供商故障转移的承诺。请查看 [账户模型](./account-models)。

## 重用已了解您应用程序的验证

您的仓库可能已经知道如何检测无效字符串、格式错误的文件、损坏的组件属性或文档构建失败。Glossia 可以通过配置的验证命令调用该知识。

候选项在检查时被暂时放置在其真实输出路径上。每次验证尝试后恢复之前的目标，并在之后写入已接受的候选项。被拒绝的输出经过配置的恢复预算，而不是仅仅因为文本看起来可信就被接受。

结构和仓库检查不能证明每个句子都是正确的。它们补充人类语言审查，并使该审查成为可交付变更的一部分。请查看 [L10N.md](/docs/reference/l10n-md) 和 [翻译恢复](./translation-recovery)。

## 公开源代码和仓库拥有的输出

Glossia 的实施可用于检查、修改，并在 [O'Saasy](https://github.com/glossia/glossia/blob/main/LICENSE.md) 下自托管。该许可限制竞争性托管服务，并非不受限制的开源许可。

更重要的是日常交付，您的翻译输出保留在 Git 中。您不需要在另一个产品中进行编辑会话，只需发布您现有的文件。

Lokalise 可能适合想要集中式浏览器编辑和本地化协调的团队。当 **仓库所有权、自己的模型令牌和现有的产品检查** 是您想要保留的工作流时，Glossia 是首选。

在切换系统之前测试一个代表性的变更。本页面不承诺自动迁移或功能一致性，也不宣称 Lokalise 缺乏自动化或所有提供商选项。请查看 [Lokalise 文档](https://docs.lokalise.com/) 以了解其当前功能。
