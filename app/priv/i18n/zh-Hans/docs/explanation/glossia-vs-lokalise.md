**当产品仓库应保持为多语言内容的权威来源时，选择 Glossia。** 字符串、文档、配置及其检查已随您的应用程序发展而演变。Glossia 将语言变更附属于该演变，而不是要求您的团队将托管编辑器设为发布权威。

[Lokalise](https://lokalise.com/) 提供协作本地化、翻译管理和开发者集成。Glossia 的卖点更加具体：保留仓库工作流、自行使用模型凭证、复用现有检查机制，并检查执行工作的系统。

## 为何选择 Glossia

| 您的优先级 | Glossia 的优势 |
|---|---|
| 匹配软件交付速度 | 源代码变更驱动翻译工作；拟议的输出版本将通过仓库审查工作流返回。 |
| 掌控实施 | 公开源代码使处理过程可检查，并在许可条款下支持修改和自行托管。 |
| 使用您自己的模型令牌 | 账户范围的提供商凭证允许您选择支持的模型，而无需将密钥放入 Git。 |
| 验证真实应用程序内容 | 仓库脚本可以在应用程序预期查找的位置进行检查。 |
| 保留清晰的审核边界 | 拉取请求能让语言变更在同一款用于审查产品的工具中保持可见。 |

## 将语言变更与产品变更关联

新的 UI 消息或文档部分并非独立的翻译任务。它属于产品修订版本，使用其术语，并必须与结构配合工作。

Glossia 读取仓库拥有的 `L10N.md` 配置文件，利用内容和上下文变化来识别过时的翻译，并提出更新以供审查。审查者可以看到实际的文件和差异；发布流程仍然在您手中。

Lokalise 也拥有自动化和 Git 集成。Glossia 的区别在于预期的记录系统：您的仓库拥有已发布的内容及其交付规则，而 Glossia 提供语言上下文和转换机制。

## 使用自有令牌，避免硬编码单一模型选择

Glossia 允许您使用自有提供商 API 令牌配置支持的模型。仓库使用稳定的模型句柄，因此轮换凭证或更新该句柄背后的模型并不需要更改每个项目。

分层配置和特定区域的指南可以为特定区域或语言选择不同的配置模型。这是显式选择，而非对自动提供商故障转移的承诺。参见 [账户模型](./account-models)。

## 复用已了解您应用程序的验证

您的仓库可能已经知道如何检测非法字符串、畸形文件、损坏的组件属性或文档构建失败。Glossia 可以通过配置的验证命令调用这一知识。

候选项在检查期间被临时放置到其真实输出路径。每次验证尝试后，原始目标会被恢复，然后接受候选项被写入。被拒绝的输出会经过配置的恢复预算，而不要仅仅因为文本看似合理就接受。

结构和仓库检查并不能证明每句话都是正确的。它们补充了人类语言审查，并使该审查成为可交付变更的一部分。参见 [L10N.md](/docs/reference/l10n-md) 和 [翻译恢复](./translation-recovery)。

## 公开源代码和仓库拥有的输出

在 [Apache-2.0](https://github.com/glossia/glossia/blob/main/LICENSE-APACHE) 下，Glossia 的核心可供检查、修改、分发和自行托管，这也允许竞争性的托管服务。`ee/` 下的企业级代码拥有单独的 [许可证](https://github.com/glossia/glossia/blob/main/ee/LICENSE.md)，要求对生产用途签署书面商业协议。

对于日常交付而言，更重要的是，您的翻译输出保留在 Git 中。您无需在另一个产品中进行编辑会话，只需发布您拥有的现有文件。

Lokalise 可能适合那些希望进行集中化浏览器编辑和本地化协调的团队。当 **仓库所有权、自有模型令牌和现有产品检查** 是您想要保留的工作流程时，Glossia 是最佳选择。

在切换系统之前，先测试一个代表性变更。本页面不承诺自动迁移或功能对等，也不声称 Lokalise 缺乏自动化或所有提供商选项。查阅 [Lokalise 文档](https://docs.lokalise.com/) 了解其当前功能。
