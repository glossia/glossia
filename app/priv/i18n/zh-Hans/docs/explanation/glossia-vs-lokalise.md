**应保持多语言内容权威性由产品仓库行使时，请选择 Glossia。** 字符串、文档、配置及其检查已随您的应用程序同步演进。Glossia 将语言变更与这一演进保持关联，而非要求您的团队将托管编辑器定为发布权威。

[Lokalise](https://lokalise.com/) 提供协作本地化、翻译管理以及开发者集成。Glossia 的诉求更为具体：保留仓库工作流，自备模型凭证，复用现有检查，并检查执行工作的系统。

## 为何选择 Glossia

| 您的优先事项 | Glossia 的优势 |
|---|---|
| 匹配软件交付速度 | 源代码变更驱动翻译工作；提出输出通过仓库审查流程返回。 |
| 掌握实施权 | 公开源代码使处理过程可检查，并支持依据许可证条款进行修改和自托管。 |
| 使用您自己的模型令牌 | 基于账户范围的提供者凭据让您选择支持的模型，而无需将密钥放入 Git。 |
| 验证真实的应用程序内容 | 仓库脚本可以检查应用程序期望发现它的候选位置。 |
| 保留清晰的审查界限 | 拉取请求可使语言变更与用于审查产品的工具一同可见。 |

## 保持语言变更与产品变更关联

新的 UI 消息或文档部分并非孤立的翻译任务。它属于产品修订，使用自身术语，并必须与自身结构协同工作。

Glossia 读取仓库拥有的 `L10N.md` 配置，利用内容和上下文变更识别过期的翻译，并提出更新以供审查。审查员可见实际文件及差异；发布流程仍由您掌控。

Lokalise 同样具备自动化工具和 Git 集成。Glossia 的差别在于预定系统记录：您的仓库拥有发布内容及交付规则，而 Glossia 提供语言上下文和转换机制。

## 自备令牌而非硬编码单一模型选择

Glossia 允许您使用自有提供者 API 令牌配置支持模型。仓库使用稳定的模型句柄，因此轮换凭证或更新该句柄后的模型无需更改每个项目。

嵌套配置和本地特定指导可为特定区域或语言选择配置模型。这是显式选择，而非自动提供者故障转移的承诺。参见 [账户模型](./account-models)。

## 复用已了解您应用程序的验证

您的仓库可能已知如何检测无效字符串、畸形文件、组件属性损坏或文档构建失败。Glossia 可通过配置的验证命令调用此知识。

候选项暂时放置于检查时的真实输出路径。每次验证尝试后恢复之前的目标，然后写入接受的候选项。被拒绝的输出经过配置的恢复预算，而非仅因文本看似合理就被接受。

结构及仓库检查不能证明每个句子均正确。它们补充人工语言审查，使该审查成为交付变更的一部分。参见 [L10N.md](/docs/reference/l10n-md) 和 [翻译恢复](./translation-recovery)。

## 公开源代码和仓库拥有的输出

Glossia 采用开放核心模式。核心代码使用 [Apache-2.0](https://github.com/glossia/glossia/blob/main/LICENSE-APACHE)，根据其条款允许商业使用、修改、分发、自托管以及提供竞争性托管服务。`ee/` 中的代码可供查看，但并非开源；它适用单独的 [Enterprise 许可证](https://github.com/glossia/glossia/blob/main/ee/LICENSE.md)，生产使用需要签订书面商业协议。

对于日常交付而言，更重要的是您的翻译输出保留在 Git 中。您无需在其他产品中拥有编辑会话，仅为了发布您现有的文件。

Lokalise 可能适合想要集中浏览器编辑和协调本地化的团队。当 **仓库所有权、您自己的模型令牌和现有产品检查** 是您想要保留的工作流时，Glossia 是最佳选择。

切换系统前请测试代表性变更。本页不承诺自动迁移或功能对等，亦不声称 Lokalise 缺乏自动性或所有提供者选项。参见 [Lokalise 的文档](https://docs.lokalise.com/) 了解其当前能力。
