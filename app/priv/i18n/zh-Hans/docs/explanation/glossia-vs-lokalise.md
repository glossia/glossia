**当产品仓库应作为多语言内容的权威来源时，选择 Glossia。** 字符串、文档、配置文件及其检查已随您的应用不断演进。Glossia 将语言变更与此演进过程联系起来，而不是要求您的团队建立一个托管编辑器作为发布权威。

[Lokalise](https://lokalise.com/) 提供协作本地化、翻译管理和开发者集成。Glossia 的提议更具体：保留仓库工作流，自行带入模型凭证，复用现有的检查，并检查执行工作的系统。

## 为什么选择 Glossia

| 您的优先级 | Glossia 的优势 |
|---|---|
| 匹配软件交付速度 | 源变更驱动翻译工作；建议输出通过仓库审查工作流返回。 |
| 掌控实现 | 公开来源使处理过程可检查，并支持在许可证条款下进行修改和自我托管。 |
| 使用您自己的模型令牌 | 账户范围的提供商凭证使您能够选择支持的模型，而无需将密钥放入 Git 中。 |
| 验证真实的应用程序内容 | 仓库脚本可以在应用程序预期找到它的位置检查候选项。 |
| 保持明确的审查边界 | 拉取请求将语言变更保留在与产品审查相同的工具中可见。 |

## 将语言变更附加到产品变更

新增的 UI 消息或文档章节并不是孤立的翻译任务。它属于产品修订版，使用其术语，并必须与其结构配合工作。

Glossia 读取仓库拥有的 `L10N.md` 配置，使用内容和上下文变更来识别过时的翻译，并提出待审查的更新。审查者可以看到实际的文件和差异；发布流水线仍归您所有。

Lokalise 也有自动化和 Git 集成。Glossia 的区别在于预期的系统记录：您的仓库拥有发布的内容及其交付规则，而 Glossia 提供语言上下文和转换机制。

## 自行带入令牌以替代硬编码单一模型选择

Glossia 允许您使用自己的提供商 API 令牌配置支持的模型。仓库使用稳定的模型句柄，因此轮换凭证或更新该句柄背后的模型无需更改每个项目。

嵌套配置和特定区域的语言特定指导可以为特定区域或语言选择不同的配置模型。这是显式选择，而非自动提供商故障转移的承诺。参见 [账户模型](./account-models)。

## 复用已经了解您的应用程序的验证

您的仓库可能已经知道如何检测无效字符串、格式错误的文件、损坏的组件属性或文档构建失败。Glossia 可以通过配置好的验证命令调用这种知识。

候选项在检查时暂时放置在其真实输出路径中。每次验证尝试后恢复之前的目标，并在之后写入接受的候选项。被拒绝的输出通过配置的恢复预算进行处理，而不仅仅因为文本看起来合乎情理就被接受。

结构和仓库检查并不能证明每句话都是正确的。它们补充人工语言审查，并使其成为可交付变更的一部分。参见 [L10N.md](/docs/reference/l10n-md) 和 [翻译恢复](./translation-recovery)。

## 公开来源和仓库拥有的输出

Glossia 采用开放核心模式。核心代码使用 [Apache-2.0](https://github.com/glossia/glossia/blob/main/LICENSE-APACHE)，根据其条款允许商业使用、修改、分发、自托管以及提供竞争性托管服务。`ee/` 中的代码可供查看，但并非开源；它适用单独的 [Enterprise 许可证](https://github.com/glossia/glossia/blob/main/ee/LICENSE.md)，生产使用需要签订书面商业协议。

对于日常交付而言更重要的是，您的翻译输出保留在 Git 中。您不需要在另一个产品中进行编辑会话来发布您现有的文件。

Lokalise 可能适合想要集中式浏览器编辑和本地化协调的团队。当 **仓库所有权、您自己的模型令牌和现有的产品检查** 是您想要保留的工作流时，Glossia 是最佳选择。

在切换系统之前测试一个代表性变更。此页面不承诺自动迁移或功能对等，或声称 Lokalise 缺乏自动化或所有提供商选项。参见 [Lokalise 文档](https://docs.lokalise.com/) 了解其当前功能。
