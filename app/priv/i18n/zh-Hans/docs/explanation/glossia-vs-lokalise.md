**当产品仓库应保持多语言内容的权威时选择 Glossia。** 字符串、文档、配置及相关检查已随您的应用程序演进。Glossia 将语言变更附于该演进，而非要求您的团队使托管编辑器成为发布权威。

[Lokalise](https://lokalise.com/) 提供协作本地化、翻译管理及开发者集成。Glossia 的定位更具体：保留仓库工作流、使用自有模型凭据、复用现有检查并监管执行工作的系统。

## 为何选择 Glossia

| 您的优先事项 | Glossia 的优势 |
|---|---|
| 匹配软件交付速度 | 源变更驱动翻译工作；拟定输出将通过仓库评审工作流返回。 |
| 掌控落地实现 | 公开源码使处理过程可审核，并支持在许可条款下修改和自托管。 |
| 使用自有模型令牌 | 账户范围的提供商凭据允许您选择支持的模型，而无需将密钥写入 Git。 |
| 验证真实应用程序内容 | 仓库脚本可在应用程序期望找到其位置检查目标。 |
| 保留清晰的评审边界 | 拉取请求在用于评审产品的工具中保持语言变更可见。 |

## 将语言变更附于产品变更

新的 UI 消息或文档部分并非孤立的翻译任务。它属于产品修订版，使用其术语，且必须与其结构配合。

Glossia 读取仓库所有 `L10N.md` 配置，利用内容和上下文变更识别过期翻译，并提议更新以供评审。评审者能看到实际文件及差异；发布流水线仍由您掌控。

Lokalise 同样拥有自动化和 Git 集成。Glossia 的区别在于其预定记录系统：您的仓库拥有发布内容及其交付规则，而 Glossia 提供语言上下文和转换机制。

## 自选令牌而非硬编码单一模型选择

Glossia 让您使用自有提供商 API 令牌配置支持的模型。仓库使用稳定的模型句柄，因此轮换凭据或更新该句柄背后的模型不需要更改每个项目。

嵌套配置和区域特定指南可为特定区域或语言选择不同的配置模型。这是显式选择，而非自动提供商故障转移的承诺。参见 [账户模型](./account-models)。

## 复用已了解您的应用程序的验证

您的仓库可能已知道如何检测无效字符串、格式错误的文件、崩溃的组件属性或文档构建失败。Glossia 可通过配置的验证命令调用该知识。

目标候选项临时放置于其实际输出路径以供检查。每次验证尝试后恢复之前的目标，并将被接受的候选项写入。被拒绝的输出将通过配置的恢复预算处理，而非仅因文本看似合理即被接受。

结构和仓库检查并不能证明每句话都正确。它们辅助人工语言评审，并使该评审成为可交付变更的一部分。参见 [L10N.md](/docs/reference/l10n-md) 和 [翻译恢复](./translation-recovery)。

## 公开源码及仓库自有输出

Glossia 的实现可用于检查、修改，并在 [O'Saasy](https://github.com/glossia/glossia/blob/main/LICENSE.md) 下自托管。该许可限制竞争性托管服务，并非无限制开源许可。

对日常交付而言更重要的是，您的翻译输出将保留在 Git 中。您无需在另一个产品中进行编辑会话，仅为了发布您已拥有的现有文件。

Lokalise 可能适合希望集中浏览器编辑和本地化协调的团队。当 **仓库所有权、自有模型令牌及现有产品检查** 是您希望保留的工作流时，Glossia 是正确的选择。

在切换系统前测试代表性变更。本页面不承诺自动迁移或功能齐平，或声称 Lokalise 缺乏自动化或所有提供商选项。见 [Lokalise 文档](https://docs.lokalise.com/) 了解其当前功能。
