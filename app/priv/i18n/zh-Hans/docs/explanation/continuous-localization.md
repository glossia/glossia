持续交付之所以有效，是因为小变更能够流经可重复的配置管道：版本控制、审查、验证和部署。本地化应该适应这一管道，而不是引入一个不相关的记录系统。

## ## 脱节的循环

在脱节的工作流中，产品变更会触发导出，工作会在另一个工具中进行，翻译后的内容最终会返回。在这些步骤之间，源内容可能再次发生更改。团队必须协调版本，决定翻译是否已过时，并协调下一次发布。

问题并不在于网页编辑器本身固有错误。而在于一个独立权威的编辑系统可以将语言决策与其描述的代码和内容修订分离开来。

## ## 仓库循环

Glossia 的仓库工作流将源文件和本地化配置保留在 Git 中。连接的仓库提供内容和目标语言。翻译变更以可审查的仓库变更形式返回，因此团队可以应用现有的拉取请求和发布约定。

一个典型的循环是：

1. 团队随产品更改源内容。
2. Glossia 识别需要翻译或优化的内容。
3. 语言指导和术语为转换提供了背景。
4. 验证检查结果，失败的情况则保持可操作。
5. 审查员在发布管道交付之前检查变更。

[渐进优化](./progressive-refinement) 解释了哈希和验证如何契合此循环。[翻译恢复](./translation-recovery) 解释了生成或验证失败时会发生什么。

## ## 持续并不等于未经审查

持续可交付的变更并不一定意味着自动批准的变更。法律文本、产品承诺和文化敏感材料可能需要专业审查。保持该审查在交付循环中，使团队选择适当的关卡而不必维持独立的发布权限。

同样，持续本地化并不意味着每次提交都翻译整个仓库。未更改的内容不应重复消耗相同的资源。

## ## 实际界限

Glossia 提供语言上下文和本地化机制。您的仓库的检查和部署流程仍然定义了何时变更可以安全发布。Glossia 不是应用程序测试或编辑者对准确性的责任的替代品。

其他平台也提供 Git 集成和 CI 自动化。区别在于预期的重心：Glossia 围绕仓库中的内容所有权和审查构建，而不是要求将正在进行的编辑权限移至托管的翻译工作区。
