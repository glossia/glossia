持续交付之所以有效，是因为小改动通过可重复的流水线：版本控制、审查、验证和部署。本地化应该顺应该流水线，而不是引入不相关的记录系统。

## ## 断开的循环

在断开的工作流中，产品变更会触发导出，工作在其他工具中进行，翻译内容最终会返回。在这些步骤之间，源文件可能会再次更改。团队需要核对版本，决定翻译是否过时，并协调另一次发布。

问题不在于 Web 编辑器本质上错误。而在于一个独立权威的编辑系统可以将语言决策从它们所描述的代码和内容修订中分离出来。

## ## 仓库循环

Glossia 的仓库工作流将源文件和本地化配置保存在 Git 中。连接的仓库提供内容和目标语言。翻译变更作为可审查的仓库变更返回，这样团队就可以应用现有的拉取请求和发布约定。

一个典型的流程是：

1. 团队随产品修改源内容。
2. Glossia 识别需要翻译或改进的内容。
3. 语言指南和术语为转换提供上下文。
4. 验证检查结果，且失败项仍可处理。
5. 审查员在发布流水线交付之前检查变更。

[渐进式细化](./progressive-refinement) 解释了哈希和验证如何适应此循环。[翻译恢复](./translation-recovery) 解释了生成或验证失败时会发生什么。

## ## 持续并不意味着未经审查

可连续交付的变更不一定是自动批准的变更。法律用语、产品承诺和文化敏感材料可能需要专家审查。将该审查保留在交付循环中，使团队可以选择适当的关口，而无需维护单独的发布权限。

持续本地化也不意味着每次提交都翻译整个仓库。不应重复为未变更的内容消耗相同资源。

## ## 实际边界

Glossia 提供语言上下文和本地化机制。仓库的检查流程和部署过程仍然定义何时变更可以安全发布。Glossia 不是应用程序测试或编辑者对准确性责任的替代品。

其他平台也提供 Git 集成和 CI 自动化。区别在于预期的重心：Glossia 是围绕仓库中的内容所有权和审查构建的，而不是要求将持续的编辑权限移动到托管翻译工作区。
