持续交付之所以有效，是因为小变更通过可重复的管道流程：版本控制、审查、验证和部署。本地化应适配该流程，而不是引入一个不相关的记录系统。

## 断开的循环

在断开的工作流程中，产品变更会触发导出，工作在其他工具中进行，而翻译内容最终会返回。在这些步骤之间，源内容可能会再次发生变化。团队需要协调版本，判断翻译内容是否已过时，并协调另一次发布。

问题不在于 Web 编辑器在本质上就是错误的。而在于一个独立权威的编辑系统可以将语言决策与其所描述的代码和内容修订分隔开。

## 仓库循环

Glossia 的仓库工作流将源文件和本地化配置保留在 Git 中。连接的仓库提供内容和目标语言。翻译变更以可评审的仓库变更形式返回，因此团队可以应用其现有的拉取请求和发布约定。

典型的循环如下：

1. 团队用产品修改源内容。
2. Glossia 识别需要翻译或改进的内容。
3. 语言指导和术语为转换提供上下文。
4. 验证检查结果，且失败保持可操作。
5. 发布管道交付前，审核员检查变更。

[渐进式细化](./progressive-refinement) 解释了哈希和验证如何适配此循环。[翻译恢复](./translation-recovery) 解释了生成或验证失败时会发生什么。

## 持续并不意味着未经审查

持续可交付的变更不一定意味着自动批准的变更。法律语言、产品承诺和文化敏感材料可能需要专家审查。将审查保留在交付循环中，使团队能够选择合适的关口，而无需维护单独的发布权威。

持续本地化并不意味着在每个提交时翻译整个仓库。未变更的内容不应反复消耗相同的资源。

## 实际边界

Glossia 提供语言上下文和本地化机制。您的仓库的检查和部署流程仍定义何时变更可安全发布。Glossia 不是应用程序测试或编辑器准确责任的替代品。

其他平台也提供 Git 集成和 CI 自动化。区别在于预期的重心：Glossia 是围绕仓库中的内容所有权和审查构建的，不必将持续的编辑权威移至托管翻译工作区。
