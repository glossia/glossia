持续交付之所以有效，是因为小的变更通过可重复的管道：版本控制、审查、验证和部署。本地化应适应该管道，而不是引入不相关的记录系统。

## 断连循环

在断连工作流中，产品变更触发导出，工作在另一工具中进行，翻译内容最终返回。在这些步骤之间，源内容可能再次变更。团队必须协调版本，决定翻译是否过时，并协调另一次发布。

问题不在于网络编辑器本质上就有错。而在于独立的权威编辑系统可以将语言决策与他们所描述的代码和内容修订分离开来。

## 仓库循环

Glossia 的仓库工作流将源文件和本地化配置保留在 Git 中。连接的仓库提供内容和目标语言。翻译变更返回为可审查的仓库变更，因此团队可以应用其现有的拉取请求和发布惯例。

典型的循环如下：

1. 团队随产品更改源内容。
2. Glossia 标识需要翻译或改进的内容。
3. 语言指导和术语为转换提供上下文。
4. 验证检查结果，且失败保持可处理状态。
5. 发布管道交付之前，审查人员检查更改。

[渐进式细化](./progressive-refinement) 解释了哈希和验证如何适应此循环。 [翻译恢复](./translation-recovery) 解释了当生成或验证失败时会发生什么。

## 持续并不意味着未经审查

持续可交付的变更不一定是自动批准的变更。法律语言、产品承诺和文化敏感材料可能需要专家评审。将该审查保留在交付循环中，使团队可以选择适当的关口，而无需维护独立的发布权。

持续本地化并不意味着每次提交都翻译整个仓库。未变更的内容不应重复消耗相同的资源。

## 实际的边界

Glossia 提供语言上下文和机制化的本地化。仓库的检查机制和部署流程仍然定义何时更改安全以发布。Glossia 不是应用程序测试的替代品，也不是编辑对准确性的责任。

其他平台也提供 Git 集成和 CI 自动化。区别在于预期的重心：Glossia 是围绕仓库中的内容拥有权和审查构建的，而不是要求将持续的编辑权移至托管翻译工作空间。
