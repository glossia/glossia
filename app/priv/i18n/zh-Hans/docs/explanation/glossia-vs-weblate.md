**当你希望语言自动化能像软件交付的其他部分一样运作时请选用 Glossia:** 源代码控制指令、您自己的模型令牌、仓库原生检查以及用于审查的拉取请求。

[Weblate](https://weblate.org/) 是一个开源本地化系统，具备网络翻译界面、版本控制集成和自托管选项功能。公开代码和 Git 集成并非 Glossia 专属。选择 Glossia 的理由在于其仓库为中心交付、基于模型的转换以及为人类和代理者提供的可重用语言上下文的组合。

## 为何选择 Glossia

| 您的优先项 | Glossia 的优势 |
|---|---|
| 保留审查在产品工作流中 | 通过仓库变更和拉取请求审查实际的受控输出。 |
| 跟上快速变化的源仓库 | 变更检测和批量发布支持持续本地化循环，无需反复翻译未变更的输入。 |
| 自行引入模型令牌 | 使用账户作用域的提供商凭据配置支持的模型，并使用仓库拥有的句柄进行选择。 |
| 复用原生验证 | 在候选项的实时目标路径上运行仓库自身的验证命令。 |
| 翻译之外复用上下文 | 共享的声音和术语可通过 MCP 和 REST 接口指导新内容和代理集成。 |

## 将仓库作为审查界面

Glossia 专为使用 Git 决定哪些内容已准备发布的团队设计。其本地化配置与生活内容并排，其提议的输出可通过与产品变更相同的流程进行审查。

Weblate 也集成于版本控制。其基于浏览器的翻译界面可能正是贡献者社区所需要的。Glossia 的重点有所不同：保留仓库审查边界并将语言自动化引入其中，而不是让另一个编辑界面成为团队工作的中心。

## 自行引入令牌并使模型选择明确

Glossia 使用根据您的提供商 API 令牌配置的模型。仓库配置引用稳定的模型句柄；密钥保留在账户设置中。您可以根据作用域或目标语言选择不同配置的模型，并在不更改每个仓库的情况下轮换凭据。

这为您的团队明确创建了选择生成其内容的模型的位置。它并不承诺令牌或模型均受支持，或生成可省去人工审查的需要。参见 [配置模型提供商](/docs/how-to/configure-a-model-provider)。

## 复用定义交付变更的检查

Glossia 内置的结构化检查仅是质量边界的一部分。通过 `L10N.md`, 它可以运行仓库的原生验证脚本、解析器、编译器或文档检查，对象位于候选项的实时目标路径。

这在使用翻译内容不仅限于纯字符串时很有用：应用程序特定格式、Markdown 组件、结构化元数据，以及项目已知道如何验证的约束条件。验证和恢复仍与实际发布管线处理的文件保持连接。

执行环境仍需要验证器的依赖项，且结构化验证不能确立语言准确性。参见 [L10N.md](/docs/reference/l10n-md) 和 [翻译恢复](./translation-recovery)。

## 公开源代码是基准，而非全部对比

Glossia 的实现是公开的，可基于 [O'Saasy](https://github.com/glossia/glossia/blob/main/LICENSE.md) 进行审查、修改和自托管。许可证限制竞争托管服务；它与基于 GPL 的 Weblate 开源许可证不同。

如果不受限制的开源许可和现成的网络翻译界面是您的主要标准，那么 Weblate 值得考虑。如果目标是 **您自己的模型凭据、现有的仓库检查以及跟随软件交付的语言工作**，Glossia 将这些选择整合在一个语言操作系统中。

此对比不声称 Weblate 缺乏自动化、验证功能或提供商集成，也不承诺自动迁移或功能对等。参见 [Weblate 的文档](https://docs.weblate.org/) 了解当前能力。
