**当希望语言自动化能够像软件交付的其他部分一样工作时，请选择 Glossia:** 源代码控制指令、您自己的模型令牌、原生仓库检查和用于审核的拉取请求。

[Weblate](https://weblate.org/) 是一个开源的语言本地化系统，具备网页翻译界面、版本控制集成和自托管选项。公开代码和 Git 集成并非 Glossia 独有。选择 Glossia 的原因在于其结合了以仓库为中心的交付、模型驱动的变换，以及适用于人类和代理的可重用语言上下文。

## 为何选择 Glossia

| 您的优先事项 | Glossia 的优势 |
|---|---|
| 将审核保留在产品工作流程中 | 通过仓库变更和拉取请求审核实际的源代码控制输出。 |
| 匹配快速变更的源仓库 | 变更检测和分批发布支持持续的本地化循环，而无需重复翻译未变更的输入。 |
| 自带模型令牌 | 配置支持的使用账户范围提供者凭据的模型，并使用仓库拥有的句柄进行选择。 |
| 复用原生验证 | 在候选项的真实目标路径上运行仓库自身的验证命令。 |
| 复用翻译之外的上下文 | 共享的语调和术语可以通过 MCP 和 REST 接口指导新内容和代理集成。 |

## 将仓库作为审核界面

Glossia 专为那些已经使用 Git 来决定什么准备好发布的团队设计。其本地化配置存在于内容旁边，其提议的输出可以通过与产品变更相同的过程进行审核。

Weblate 同样集成版本控制。其基于浏览器的翻译界面可能正是贡献社区所需。Glossia 的重点有所不同：保留仓库审核边界并将语言自动化引入其中，而不是将另一个编辑界面作为团队工作的中心。

## 自带令牌并使模型选择显式化

Glossia 使用配置有您提供者 API 令牌的支持模型。仓库配置指稳定模型句柄；秘密保留在账户设置中。您可以根据内容范围或目标区域选择不同的配置模型，并在不更改每个仓库的情况下轮换凭据。

这为您的团队提供了一个明确的位置，用于选择编写其内容的模型。它不保证任何令牌或模型得到支持，也不保证生成过程消除了人工审核的必要性。参见 [配置模型提供者](/docs/how-to/configure-a-model-provider)。

## 复用定义可交付变更的检查

Glossia 内置的结构检查仅是质量边界的一部分。通过 `L10N.md`, 它可以在候选项的真实目标路径上运行仓库的原生验证脚本、解析器、编译器或文档检查。

当翻译内容包含多于纯字符串时，这很有用：特定应用程序的格式、Markdown 组件、结构化元数据以及项目已知如何验证的约束。验证和恢复保持与您的流水线将要发布的实际文件相连。

执行环境仍然需要验证器的依赖项，且结构验证并不能确立语言学准确性。参见 [L10N.md](/docs/reference/l10n-md) 和 [翻译恢复](./translation-recovery)。

## 公开源代码是基线，而非整体比较

Glossia 的核心代码使用 [Apache-2.0](https://github.com/glossia/glossia/blob/main/LICENSE-APACHE)，根据其条款允许商业使用、修改、分发、自托管以及提供竞争性托管服务。`ee/` 中的代码适用单独的 [Enterprise 许可证](https://github.com/glossia/glossia/blob/main/ee/LICENSE.md)，生产使用需要签订书面商业协议。这种开放核心模式与 Weblate 基于 GPL 的许可模式不同。

如果无限制的开源许可和成熟的网页翻译界面是您的主要标准，那么 Weblate 值得考虑。如果目标是 **您自己的模型凭据、现有的仓库检查以及遵循软件交付的语言工作**，那么 Glossia 将这些选择在语言操作系统中结合在一起。

此次比较并未声称 Weblate 缺乏自动化、验证功能或提供者集成，也不承诺自动迁移或功能对等。参见 [Weblate 的文档](https://docs.weblate.org/) 以了解当前功能。
