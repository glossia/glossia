**在希望语言自动化工作方式与软件交付的其他部分一致时选择 Glossia：** 版本控制的指令、您的专属模型令牌、原生的仓库检查，以及用于审查的合并请求。

[Weblate](https://weblate.org/) 是一个开源的本地化系统，具有 Web 翻译界面、版本控制集成和自托管选项。公共代码和 Git 集成并非 Glossia 独有。选择 Glossia 的原因在于其结合了以仓库为中心的交付、模型驱动转换以及面向人类和智能体的可复用语言上下文。

## 为何选择 Glossia

| 您的优先级 | Glossia 的优势 |
|---|---|
| 保持审查在产品工作流中 | 通过仓库变更和合并请求审查实际的受版本控制的输出。 |
| 匹配快速迭代的源码仓库 | 变更检测和批量发布支持持续的本地化循环，无需重复翻译未变化的输入。 |
| 自带您的模型令牌 | 使用账户范围的提供商凭据配置支持的模型，并使用仓库拥有的句柄选择它们。 |
| 复用原生验证 | 在其真实目标路径上针对候选对象运行仓库自身的验证命令。 |
| 在翻译之外复用上下文 | 统一的语气和术语可以通过 MCP 和 REST 接口来指导新内容和智能体集成。 |

## 保持仓库作为审查界面

Glossia 专为已使用 Git 决定发布就绪事项的团队设计。其本地化配置与内容并列，其建议的输出可通过与产品变更相同的过程进行审查。

Weblate 也集成版本控制。其基于浏览器的翻译界面可能正是贡献社区所需要的。Glossia 的重点有所不同：保留仓库审查边界并将语言自动化带入其中，而不是让另一个编辑界面成为团队工作的中心。

## 自带您的令牌并使模型选择显式化

Glossia 使用配置了您提供商 API 令牌的支持模型。仓库配置指的是稳定的模型句柄；凭证保留在账户设置中。您可以根据内容范围或目标语言选择不同的配置模型，并在无需更改每个仓库的情况下轮换凭证。

这为您的团队提供了一个明确的位置来选择编写其内容的模型。它不承诺任何令牌或模型受到支持，或声称生成消除了人工审查的需求。参见 [配置模型提供商](/docs/how-to/configure-a-model-provider)。

## 复用定义交付变更的检查

Glossia 内置的结构化检查仅是质量边界的一部分。通过 `L10N.md`，它可以在候选对象的真实目标路径上运行仓库原生的验证脚本、解析器、编译器或文档检查。

当翻译内容包括纯字符串以外的内容时，这非常有用：特定应用格式、Markdown 组件、结构化元数据以及项目本身已知的约束。验证和恢复保持与管道将发布的实际文件相连。

执行环境仍然需要验证器的依赖项，结构化验证无法确立语言准确性。参见 [L10N.md](/docs/reference/l10n-md) 和 [翻译恢复](./translation-recovery)。

## 公开源代码是基线，而非完整对比

Glossia 的实现是公开的，可以在 [O'Saasy](https://github.com/glossia/glossia/blob/main/LICENSE.md) 下进行检查、修改和自托管。许可证限制了竞争的托管服务；它与 Weblate 的基于 GPL 的开源许可证不同。

如果不限制开源许可和成熟的 Web 翻译界面是主要标准，Weblate 值得考虑。如果目标是 **您自己的模型凭证、现有的仓库检查以及遵循软件交付的语言工作**，Glossia 将这些选择集并在一起，形成语言操作系统。

此对比并不声称 Weblate 缺乏自动化、验证功能或提供商集成，也未承诺自动迁移或功能平权。参见 [Weblate 的文档](https://docs.weblate.org/) 了解当前能力。
