**当本地化工作需要跟上软件交付速度时，请选择 Glossia。** 您的仓库已经定义了如何审查、验证和发布变更。Glossia 将语言工作引入该流程，而不是将单独的翻译工作区作为流程的中心。

[Crowdin](https://crowdin.com/) 提供协作式翻译管理、审查工作流、翻译记忆和仓库集成。Glossia 对软件团队的优势在于仓库拥有的内容、可检查的源代码、您自己的模型凭证以及对实际项目的理解验证的组合。

## 为何选择 Glossia

| 您的优先级 | Glossia 的优势 |
|---|---|
| 持续交付 | 翻译运行跟随源代码变更并返回可审查的仓库更新。内容无需独立的、不相关的发布流程。 |
| 掌控实施 | 公共应用、CLI 和部署代码可以根据许可证条款进行检查、修改和自托管。 |
| 自带令牌 | 使用您自己的提供商 API 令牌配置支持的模型。仓库文件引用稳定的模型句柄，而非密钥。 |
| 重用您信任的检查 | 在接收之前，在该候选项的真实目标路径上运行仓库验证命令。 |
| 保持内容归您所有 | 源代码文件、翻译输出、配置和拉取请求历史记录保留在您的仓库中。 |

## 与提交保持同步的本地化

Glossia 依据版本化的 `L10N.md` 说明开展工作并检测哪些内容需要更新。不变的输入无需再次翻译。项目保持一个开放的翻译拉取请求，并在批量发布进度，减少不必要的拉取请求和重复的 CI 运行。

结果是围绕您的团队已经发布的微小、可审查变更设计的语言工作流。持续并不意味着未经审查：审查人员仍决定哪些更改可以安全合并。

Crowdin 也支持 Git 集成和自动化。选择 Glossia 的原因并非 Crowdin 无法连接到仓库，而是仓库交付是 Glossia 工作流的基础，而不仅仅是集成边界。

## 您的令牌，您自己的模型选择

您无需为轮转提供商令牌或更改翻译工作流背后的模型而重新构建仓库配置。Glossia 将凭证存储在账户设置中并向仓库暴露稳定的句柄。不同的内容区域或目标语言区域可以选择不同的配置模型。

这使得您的团队可以控制其使用的支持提供商关系和模型选择。请参阅 [配置模型提供商](/docs/how-to/configure-a-model-provider)。

## 作为产品的一部分验证输出

翻译即使阅读良好也可能破坏文档构建、组件、占位符或应用程序解析器。Glossia 允许您重用仓库检查，而不仅仅停留在编辑对文本的评估。

如果您的仓库已经提供了文档验证脚本，请直接引用它：

```yaml
validation:
  - ./scripts/validate-docs.sh
  - --strict
```

验证器在其实际目标路径处接收候选项，失败时返回非零状态，并在配置的重复尝试预算内运行。其依赖项必须在验证环境中可用。有关合同，请参阅 [L10N.md](/docs/reference/l10n-md)。

## 公开源码，但不放弃仓库

您可以检查 Glossia 计划的工作方式、处理凭据、保留 Markdown 并验证结果。即使语言服务不可用，现有翻译文件仍可通过仓库管道发布。

Glossia 根据 [O'Saasy 许可证](https://github.com/glossia/glossia/blob/main/LICENSE.md) 提供源码，允许自托管但限制竞争性托管服务。它不是非限制性的开源许可证。

Crowdin 仍然适用于以贡献者协调和专用翻译编辑器为中心的项目。对于将优先级设为 **Git 拥有的内容、现有验证和与交付同步的本地化** 的软件团队，Glossia 专为该工作设计。

此比较并未声称 Crowdin 缺乏自动化或所有形式的提供商集成，也未宣称 Glossia 会自动迁移其翻译记忆和历史。有关当前功能，请参阅 [Crowdin 文档](https://support.crowdin.com/)。
