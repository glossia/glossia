**当本地化工作需要紧跟软件交付速度时，请选择 Glossia。** 您的仓库已经定义了如何审查、验证和发布变更。Glossia 将语言工作整合进该循环，而不是让单独的翻译工作区成为您流程的核心。

[Crowdin](https://crowdin.com/) 提供协作式翻译管理、审查工作流、翻译记忆和仓库集成。对于软件团队，Glossia 的优势在于仓库拥有的内容、可检查的源代码、您自己的模型凭证，以及能够理解实际项目的验证。

## 选择 Glossia 的理由

| 您的优先级 | Glossia 的优势 |
|---|---|
| 持续发布 | 翻译运行跟随源代码变化，并返回可审查的仓库更新。内容不需要拥有独立的无关发布流程。 |
| 掌控实现 | 公开的应用程序、CLI 和部署代码可以根据许可条款进行检查、修改以及自托管。 |
| 自带令牌 | 使用您自己的提供商 API 令牌配置支持模型。仓库文件引用稳定的模型句柄，而非密钥。 |
| 重用您信任的检查 | 在接受之前，在候选项的真实目标路径上运行仓库验证命令。 |
| 保持内容自有 | 源文件、翻译输出、配置和拉取请求历史将保留在您的仓库中。 |

## 与提交同步的本地化

Glossia 基于版本化的 `L10N.md` 说明工作，并检测哪些内容需要更新。未更改的输入不需要再次翻译。项目保留一个开放的翻译拉取请求，并以批次发布进度，随着源代码演变，减少不必要的拉取请求和重复的 CI 运行。

结果是围绕您的团队已经发布的相同小型、可审查变更设计的语言工作流。持续并不意味着未经审查：审查人员仍然决定哪些内容可以合并。

Crowdin 也支持 Git 集成和自动化。选择 Glossia 的原因不是 Crowdin 无法连接仓库；而是仓库交付是 Glossia 工作流的基础，而不仅仅是一个集成边界。

## 您的令牌，您的模型选择

您不应该为了轮换提供商令牌或更改翻译工作流背后的模型而重建仓库配置。Glossia 将凭证存储在账户设置中，并向仓库暴露稳定的句柄。不同的内容区域或目标语言可以选择不同的配置模型。

这赋予了您的团队对支持的提供商关系和您所用模型选择的控制权。请参阅 [配置模型提供商](/docs/how-to/configure-a-model-provider)。

## 将输出验证作为产品的一部分

翻译可能读起来很好，但仍会破坏文档构建、组件、占位符或应用解析器。Glossia 允许您复用仓库检查，而不仅仅停留在编辑对文本的评估。

如果仓库已经提供了文档验证脚本，请直接引用：

```yaml
validation:
  - ./scripts/validate-docs.sh
  - --strict
```

验证器会在候选项的实际目标路径接收它，失败时返回非零状态，并在配置的重试预算内运行。其依赖项必须在验证环境中可用。有关合同，请参见 [L10N.md](/docs/reference/l10n-md)。

## 公开代码，而不让渡仓库

您可以检查 Glossia 计划如何运作、处理凭证、保留 Markdown 并验证结果。即使语言服务不可用，现有翻译文件仍可通过您的仓库流水线发布。

Glossia 是开放核心：[Apache-2.0](https://github.com/glossia/glossia/blob/main/LICENSE-APACHE) 覆盖核心并允许自托管和竞争托管服务。在 `ee/` 下的可供源码的 SaaS 代码拥有单独的 [许可证](https://github.com/glossia/glossia/blob/main/ee/LICENSE.md)，要求生产使用时需要书面商业协议。

Crowdin 对于专注于贡献者协调和专用翻译编辑的程序仍然适用。对于优先级是 **Git 拥有内容、现有验证和遵循交付的本地化** 的软件团队，Glossia 专为这项工作而设计。

此比较并未声称 Crowdin 缺乏自动化或每种形式的提供商集成，或声称 Glossia 会自动迁移其记忆和历史。请查阅 [Crowdin 文档](https://support.crowdin.com/) 以了解当前功能。
