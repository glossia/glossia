**当本地化需要跟上软件交付速度时，就选择 Glossia。** 您的仓库已经定义了如何审查、验证和发布变更。Glossia 将语言工作纳入该循环，而不是将单独的翻译工作间作为您流程的中心。

[Crowdin](https://crowdin.com/) 提供协作式翻译管理、审查工作流、翻译记忆和仓库集成。对于软件团队而言，Glossia 的优势在于组合了仓库拥有的内容、可检查的源代码、您自己的模型凭据以及对实际项目的理解验证。

## 为何选择 Glossia

| 您的优先事项 | Glossia 的优势 |
|---|---|
| 持续发布 | 翻译运行跟随源变更并返回可审查的仓库更新。内容不需要其自身不相关的发布流程。 |
| 保持对实现的掌控 | 公开的应用程序、CLI 和部署代码可在许可条款下进行检查、修改和自托管。 |
| 自带令牌 | 使用您自己的提供商 API 令牌配置支持的模型。仓库文件引用稳定的模型句柄，而非秘密。 |
| 重用您信任的检查 | 在接收候选项之前，在其真实目标路径上运行仓库验证命令。 |
| 保持内容属于您 | 源文件、翻译输出、配置和拉取请求历史记录保留在您的仓库中。 |

## 跟上提交记录的本地化

Glossia 根据版本化的 `L10N.md` 指令检测哪些内容需要更新。未变更的输入无需再次翻译。项目保留一个开放的翻译拉取请求，并以批次方式发布进度，减少因源更新而产生的不必要拉取请求和重复的 CI 运行。

这一语言工作流是围绕您的团队已经发布的同样微小、可审查的变更设计的。持续并不意味着未经审查：审查者仍决定哪些内容可以安全合并。

Crowdin 同样支持 Git 集成和自动化。选择 Glossia 的原因不在于 Crowdin 无法连接到仓库，而在于仓库交付是 Glossia 工作流的基础，而不仅仅是集成边界。

## 您的令牌，您的模型选择

您不应不得不重新构建仓库配置来轮换提供商令牌或更改翻译工作流背后的模型。Glossia 将凭据存储在账户设置中，并向仓库暴露稳定的句柄。不同的内容区域或目标本地化区域可以选择不同的配置模型。

这使您的团队能够控制其使用的支持提供商关系和模型选择。请参阅 [配置模型提供商](/docs/how-to/configure-a-model-provider)。

## 将输出验证作为产品的一部分

翻译即使阅读流畅，仍可能导致文档构建、组件、占位符或应用解析器出错。Glossia 允许您复用仓库检查，而不仅仅停留在文本编辑器对文本的评估。

如果您的仓库已经提供了文档验证脚本，请直接引用它：

```yaml
validation:
  - ./scripts/validate-docs.sh
  - --strict
```

验证器在候选项的实际目标路径上接收它，在失败时返回非零状态，并在配置的退避预算范围内运行。其依赖项必须在验证环境中可用。有关合同，请参阅 [L10N.md](/docs/reference/l10n-md)。

## 公开源代码，不丧失仓库

您可以检查 Glossia 的规划方式、凭据处理、Markdown 保留方式以及结果验证方式。即使语言服务不可用，现有的翻译文件仍可通过您的仓库管道发布。

Glossia 在 [O'Saasy 许可证](https://github.com/glossia/glossia/blob/main/LICENSE.md) 下可供源，这允许自托管，但限制竞争托管服务。它不是无限制的开源许可证。

Crowdin 对于以协调贡献者和专用翻译编辑器为中心的计划仍然合适。对于优先事项为 **Git 拥有的内容、现有验证及遵循交付的本地化** 的软件团队，Glossia 是为此设计。

此比较并不声称 Crowdin 缺乏自动化或任何形式的提供商集成，或声称 Glossia 会自动迁移其记忆和历史。请参阅 [Crowdin 的文档](https://support.crowdin.com/) 了解当前功能。
