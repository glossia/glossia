**当本地化需要跟上您的软件交付速度时，选择 Glossia。** 您的仓库已经定义了如何审查、验证和发布更改。Glossia 将语言工作带入该流程，而不是将单独的翻译工作区作为您流程的核心。

[Crowdin](https://crowdin.com/) 提供协作翻译管理、审核工作流、翻译记忆和仓库集成。Glossia 对于软件团队的优势在于结合仓库拥有的内容、可审查的源代码、您自己的模型凭证，以及理解实际项目的验证。

## 为何选择 Glossia

| 您的优先项 | Glossia 的优势 |
|---|---|
| 持续发布 | 翻译执行跟随源代码更改并返回可审查的仓库更新。内容无需其本身独立的发布流程。 |
| 掌控实施 | 公开的应用程序、CLI 和部署代码可在许可证条款下进行检查、修改和自托管。 |
| 自带令牌 | 使用您自己的提供商 API 令牌配置支持模型。仓库文件引用稳定的模型句柄，而非密钥。 |
| 重用您信任的检查 | 在接受候选项之前，在其真实目标路径运行仓库验证命令。 |
| 保留内容归您所有 | 源文件、翻译输出、配置和合并请求历史保留在您的仓库中。 |

## 紧跟提交的本地化

Glossia 基于版本化的 `L10N.md` 指令，并检测哪些内容需要更新。不变的输入无需再次翻译。项目保留一个开放的翻译合并请求，并以批次方式发布进度，随着源文件演变，减少不必要的合并请求和重复的 CI 运行。

结果是一个围绕您的团队已发布的小型、可审查变更设计的语言工作流。持续变更并不意味着未经审查：审查员仍然决定哪些内容可以安全合并。

Crowdin 也支持 Git 集成和自动化。选择 Glossia 的原因并非 Crowdin 无法连接到仓库，而是仓库交付是 Glossia 工作流程的基础，而不仅仅是一个集成边界。

## 您的令牌，您的模型选择

您需要重建仓库配置来轮换提供商令牌或更改翻译工作流背后的模型。Glossia 将凭证存储在账户设置中，并向仓库暴露稳定的句柄。不同的内容区域或目标区域可以选择不同的配置模型。

这让您的团队能够控制其使用的支持提供商关系和模型选择。请参阅 [配置模型提供商](/docs/how-to/configure-a-model-provider)。

## 将输出验证作为产品的一部分

翻译可能可读性良好，但依然会破坏文档构建、组件、占位符或应用程序解析器。Glossia 允许您复用仓库检查，而非止步于编辑对文本的评估。

如果您的仓库已提供文档验证脚本，请直接引用它：

```yaml
validation:
  - ./scripts/validate-docs.sh
  - --strict
```

验证器在其实际目标路径接收候选项，失败时返回非零状态，并在配置的重试预算内运行。其依赖项必须在验证环境中可用。有关协议，请参见 [L10N.md](/docs/reference/l10n-md)。

## 公开源代码，不牺牲仓库

您可以检查 Glossia 计划如何工作、处理凭证、保留 Markdown 并验证结果。现有的翻译文件即使语言服务不可用，仍可通过您的仓库管道发布。

Glossia 在 [O'Saasy 许可证](https://github.com/glossia/glossia/blob/main/LICENSE.md) 下可用，允许自托管，但限制竞争的托管服务。它不是无限制的开源许可证。

Crowdin 对于以协调贡献者和专职翻译编辑为中心的程序仍然合适。对于优先事项是 **Git 拥有的内容、现有验证以及遵循交付的本地化** 的软件团队，Glossia 是为此设计的。

此比较并未声称 Crowdin 缺乏自动化或每种形式的提供商集成，也未声称 Glossia 会自动迁移其记忆和历史。请查阅 [Crowdin 文档](https://support.crowdin.com/) 以了解当前功能。
