**当本地化需要跟上您的软件交付速度时，请选择 Glossia。** 您的仓库已经定义了如何审查、验证和推送变更。Glossia 将语言工作纳入该循环，而不是使独立的翻译工作空间成为您流程的中心。

[Crowdin](https://crowdin.com/) 提供协作式翻译管理、审查工作流、翻译记忆库和仓库集成。Glossia 对软件团队的优势在于组合了仓库所有内容、可检查的源码、您自己的模型凭证，以及了解实际项目的验证。

## 为何选择 Glossia

| 您的优先级 | Glossia 的优势 |
|---|---|
| 持续交付 | 翻译运行跟随源码变更并返回可审查的仓库更新。内容不需要自己的无关发布流程。 |
| 掌握实施的控制权 | 公开的应用、CLI 和部署代码可在许可条款下被检查、修改并自托管。 |
| 自带令牌 | 使用您自己的提供商 API 令牌配置支持的模型。仓库文件引用稳定的模型句柄，而非机密信息。 |
| 复用您可信赖的检查 | 在接受候选文件时，在其真实目标路径上运行仓库验证命令。 |
| 保留内容所有权 | 源文件、翻译输出物、配置和拉取请求历史均保留在您的仓库中。 |

## 跟上提交本地化

Glossia 基于版本化的 `L10N.md` 说明工作，并检测哪些内容需要更新。未变的输入无需再次翻译。项目保持一个开放的翻译拉取请求，并分批发布进度，随着源码演进，减少不必要的拉取请求和重复的 CI 运行。

结果是一个围绕您的团队已推送的相同小型、可审查变更设计的语言工作流。持续并不意味着未经审查：审查人员仍然决定什么是可以安全合并的。

Crowdin 也支持 Git 集成和自动化。选择 Glossia 的原因不在于 Crowdin 无法连接到仓库；而在于仓库交付是 Glossia 工作流的基础，而不仅仅是一个集成边界。

## 您的令牌，您的模型选择

您不必因为轮转提供商密钥或更改翻译工作流背后的模型而重建仓库配置。Glossia 将凭证存储在账户设置中，并向仓库暴露稳定的句柄。不同的内容区域或目标语言区域可以选择不同的已配置模型。

这赋予您的团队对支持的提供商关系及其使用的模型选择的控制权。请参见 [配置模型提供商](/docs/how-to/configure-a-model-provider)。

## 将输出作为产品的一部分进行验证

翻译虽然读起来通顺，仍可能破坏文档构建、组件、占位符或应用解析器。Glossia 让您复用仓库检查，而不是止步于编辑对文本的评估。

如果您的仓库已提供文档验证脚本，请直接引用它：

```yaml
validation:
  - ./scripts/validate-docs.sh
  - --strict
```

验证器在其实际目标路径接收候选文件，失败时返回非零状态，并在配置的重试预算内运行。其依赖必须在验证环境中可用。有关合约，请参见 [L10N.md](/docs/reference/l10n-md)。

## 公开源码，不交出仓库

您可以检查 Glossia 计划如何运作、如何处理凭证、如何保留 Markdown 以及如何验证结果。如果语言服务不可用，现有的翻译文件仍可通过您的仓库管道发布。

Glossia 采用开放核心模式。核心代码使用 [Apache-2.0](https://github.com/glossia/glossia/blob/main/LICENSE-APACHE)，根据其条款允许商业使用、修改、分发、自托管以及提供竞争性托管服务。`ee/` 中的代码可供查看，但并非开源；它适用单独的 [Enterprise 许可证](https://github.com/glossia/glossia/blob/main/ee/LICENSE.md)，生产使用需要签订书面商业协议。

对于以 **Git 所有内容、现有验证以及遵循交付的本地化** 为优先级的软件团队，Glossia 是为该工作而设计的。

本比较并未声称 Crowdin 缺乏自动化或每种形式的提供商集成，或者声称 Glossia 会自动迁移其记忆和历史。请参阅 [Crowdin 文档](https://support.crowdin.com/) 了解当前功能。
