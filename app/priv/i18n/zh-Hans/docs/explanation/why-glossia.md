产品可以持续发布，尽管其翻译版本仍滞留在独立的发布周期中。源内容在 Git 中发生变更，有人将其导出到翻译系统，编辑人员在那里工作，然后有人导入结果。产品和其语言版本逐渐分离。

Glossia 是基于不同前提构建的语言操作系统：语言工作应遵循与产品本身相同的版本化、可审核的交付循环。

## 问题比翻译更广泛

团队需要保留含义、应用术语、匹配受众语调，并随着产品的演变更新内容。这些决策同样影响文档、UI 字符串、营销页面和代理生成的文本。

模型可以生成有用的草稿。但它本身无法了解组织的语言决策，记录短语变更的原因，验证文件格式，或同步下一个源版本。重复提示并不是交付系统。

Glossia 将语言上下文与生成周围的机制相结合：配置、变更检测、验证、失败恢复、修订历史和审核。

## 内容随产品留存

仓库始终是发布内容的权威。源文件、配置、生成的翻译和可审核的变更可以经过 Git 和拉取请求流转。团队无需在交付本地化版本之前，就将托管编辑界面确立为每句话的权威。

这使得语言变更与其所推动的产品变更并列可见。审核员可以审查差异，CI 可以验证输出，同一交付管道可以发布它。

阅读 [连续本地化](./continuous-localization) 了解交付模型和 [内容所有权](./content-ownership) 了解其可移植性影响。

## 语境是输入，而非束缚

语音指导和术语帮助人类和代理以一致的方式写作。它们是可重用的语言决策，而不仅仅是专有源目标片段对的集合。

翻译记忆对于既定的翻译和重复内容仍然有用。重点不在于丢弃它们。重点在于避免让某一个供应商的记忆格式或编辑工作流成为公司语言知识存留的唯一场所。

参见 [语言记忆与翻译记忆](./language-memory-and-translation-memory)。

## 改进是一个循环

Glossia 的渐进细化模型使用内容哈希来避免重复工作，在转换周围运行验证，并暴露失败以便运行时能够恢复。人类的修正可以指导下一次迭代，而不是消失在孤立的生成中。

本地化分析提供另一种输入：了解受众使用的语言和位置可以帮助团队决定投资方向。这是优先级排序的证据，而非翻译将促进增长的承诺。

## 适用对象

Glossia 在开发人员、语言学家和产品团队希望协作管理仓库内容并连续发布时特别适用。这并不是声称每个组织都应放弃其现有的 TMS。如果您的核心需求是一个成熟的基于浏览器编辑器、翻译代理商协调或大型既定记忆，团队可能会偏好其他工作流程。

对 [Crowdin](./glossia-vs-crowdin)、[Lokalise](./glossia-vs-lokalise)、[Phrase](./glossia-vs-phrase) 和 [Weblate](./glossia-vs-weblate) 的对比解释了这些取舍。

## 可检查的实现

Glossia 的代码公开可用，包括其 Phoenix 应用、Rust CLI、Web SDK 和部署基础设施。这使得语言工作的机制可检查，而不是黑盒。

当前仓库使用 [O'Saasy 许可](https://github.com/glossia/glossia/blob/main/LICENSE.md)，允许使用和修改，但限制竞争性托管服务。公共源码可用性与许可自由是截然不同的；在重新分发或运营服务之前，请阅读许可证。
