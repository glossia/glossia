产品可以持续发布，而其翻译却滞留在独立的发布周期中。源代码在 Git 中更改，有人将其导出到翻译系统，翻译人员在那里工作，然后有人导入结果。产品和其语言版本逐渐脱节。

Glossia 是一个语言操作系统，建立于不同的前提之上：语言工作应与产品本身相同的版本化、可审查的交付循环相一致。

## 问题比翻译本身更大

团队需要保持含义、应用术语、匹配受众语气，并随产品演进更新内容。这些决策影响文档、UI 字符串、营销页面以及由代理生成的写作。

模型可以生成有用的草稿。但它自身无法了解组织设置的语言决策、记录为何措辞变更、验证文件格式，或同步下一版源代码。重复提示词不能构成交付系统。

Glossia 将语言上下文与围绕生成的操作结合：配置、变更检测、验证、故障恢复、版本历史和审查。

## 内容随产品留存

仓库是对已发布内容的权威来源。源文件、配置、生成的翻译和可审查的变更都可以通过 Git 和拉取请求进行流转。团队无需在能够发布本地化版本前，让托管编辑界面成为每句话的权威来源。

这使得语言变更与驱动它们的变更一同可见。审查者可以检查差异，CI 可以验证输出，相同的交付管道可以发布它们。

阅读关于交付模式的 [持续本地化](./continuous-localization) 和关于其便携性影响的 [内容所有权](./content-ownership)。

## 上下文是输入，不是限制

语音指导和术语帮助人类和代理保持一致写作。它们是可重用的语言决策，而不仅仅是来源到目标片段对的专有集合。

翻译记忆库对于既定翻译和重复性内容仍然有用。目的不是抛弃它们。目的是避免让单一供应商的记忆格式或编辑工作流成为公司语言知识的唯一存在地。

## 改进是一个循环

Glossia 的渐进式精进模型使用内容哈希避免重复工作，在转换周围运行验证，并暴露失败以便运行可以恢复。人为修正可以指导下一轮迭代，而不是消失在孤立的生成中。

本地化分析提供另一个输入：理解受众使用的语言和地点可以帮助团队决定投资方向。这为优先级排序提供证据，而非承诺翻译将产生增长。

## 这适合谁

当开发人员、语言学家和产品团队希望在仓库管理的协作内容上协作并持续发布时，Glossia 特别相关。这并不是说每个组织都应放弃现有的 TMS。如果团队的核心需求是成熟的浏览器编辑工具、翻译机构协调或庞大的既定记忆，可能更偏好其他工作流。

## 可检查的实现

Glossia 的代码公开可用，包括其 Phoenix 应用、Rust CLI、Web SDK 和部署基础设施。这使得语言工作的机械流程可检查，而非黑色盒子。

Glossia 采用开放核心模式。核心代码使用 [Apache-2.0](https://github.com/glossia/glossia/blob/main/LICENSE-APACHE)，根据其条款允许商业使用、修改、分发、自托管以及提供竞争性托管服务。`ee/` 中的代码可供查看，但并非开源；它适用单独的 [Enterprise 许可证](https://github.com/glossia/glossia/blob/main/ee/LICENSE.md)，生产使用需要签订书面商业协议。
