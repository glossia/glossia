产品可以持续发布，但其翻译版本仍滞留在独立的发布周期中。源内容在 Git 中变更，有人将其导出到翻译系统，编辑在此工作，然后有人导入结果。产品及其语言版本渐行渐远。

Glossia 是一个基于不同理念的语言操作系统：语言工作应遵循与产品本身相同的版本化、可审查的交付循环。

## 问题的范围远超翻译

团队需要保留含义、应用术语、适应受众的语调，并在产品演进时更新内容。这些决策同样影响文档、UI 字符串、营销页面和智能体生成的内容。

模型可以生成有用的初稿。但它自身不知道组织的语言决策，无法记录短语变更的原因，无法验证文件格式，也无法同步下一个源版本修订。重复提示并非一个交付系统。

Glossia 将语言上下文与生成周围的机制相结合：配置、变更检测、验证、失败恢复、版本记录及审查。

## 内容随产品保留

仓库始终是发布内容的权威来源。源文件、配置文件、生成的翻译和可审查的变更均可通过 Git 和拉取请求进行流转。团队无需在每次交付本地化版本前都将托管编辑界面确立为每一句话的权威。

这使得驱动这些变更的产品变更与之并行可见。审查员可以检查差异，CI 可以验证输出，相同的交付管道还可以发布它。

阅读 [持续本地化](./continuous-localization) 了解交付模型，以及阅读 [内容所有权](./content-ownership) 了解其可移植性影响。

## 上下文是一种输入，而非牢笼

语气指导和术语有助于人类和智能体保持一致性写作。它们是可重新使用的语言决策，而不仅仅是源目标片段对的专有集合。

翻译记忆库对于已建立的翻译和重复内容仍然有用。目的不是丢弃它们。目的是避免将某个供应商的记忆格式或编辑工作流程作为公司语言知识的唯一存放地。

## 改进是一个循环

Glossia 的渐进式细化模型利用内容哈希避免冗余工作，在变换周围运行验证，并暴露失败以便一次运行可以恢复。人工修正可以指导下一轮迭代，而不是消失在孤立的生成过程中。

本地化分析提供了另一种输入：了解受众使用的语言和地点可以帮助团队决定投资方向。这是关于优先级的证据，而非翻译能够带来增长的承诺。

## 适用对象

当开发人员、语言学家和产品团队希望在仓库管理的内容上进行协作并持续发布信息时，Glossia 尤为适用。这并不声称每个组织都应当放弃其现有的 TMS。如果团队的核心需求是一个成熟的基于浏览器的编辑器、翻译机构协调或大型已建立的记忆库，他们可能会更偏好另一种工作流。

## 可检查的实现

Glossia 的代码公开可用，包括其 Phoenix 应用、Rust CLI、Web SDK 和部署基础设施。这使得语言工作的机制成为可检查的，而非黑盒。

仓库当前使用 [O'Saasy 许可](https://github.com/glossia/glossia/blob/main/LICENSE.md)，它允许使用和修改，但限制竞争的托管服务。公开源代码可用性和许可自由是截然不同的；在重新分发或运营服务之前阅读许可。
