## 開発者ファースト

Glossia の中核は REST API です。ダッシュボード、CLI、そして [MCP サーバー](/features/mcp-server) これらすべては同じエンドポイントを利用します。機能を追加する際、それはまず API 上に実装され、その後他の全ての場所で公開されます。

これは UI による制限を意味しません。CI/CD インテグレーションからカスタムダッシュボードまで、考えられるあらゆるワークフローは、同じ安定し、ドキュメント化されたインターフェースの上に構築できます。

## 認証

Glossia はすべての API 認証に OAuth 2.1 と PKCE を使用します。このフローは、ファーストパーティとサードパーティのクライアントの双方をサポートします。詳細を [認証および権限のドキュメント](/docs/reference/apis/authentication) 完全なウォークスルーについては。

**動的クライアント登録** -- クライアントはプログラム上で登録されます `/oauth/register` リダイレクト\_URI およびグラントタイプを指定します。手動承認の手順はなく、ポータルを介してクリックする必要はありません。

**PKCE を用いた Authorization code** -- ユーザーはブラウザベースの同意画面を通じてクライアントを承認します。PKCE の拡張により、秘密を保存できない公開クライアントであってもトークンは安全に保たれます。

**トークンのライフサイクル** -- アクセストークンは標準の OAuth エンドポイントで交換、イントロスペクション、および取り消すことができます。トークンエンドポイントのレート制限は総当たり攻撃から保護します。

## 認可

アクセス制御は 2 つの層を使用します。その [認証ドキュメント](/docs/reference/apis/authentication) はスコープ、ロール、および完全な権限マトリックスについて詳しく説明します。

**スコープ** はトークンがアクセスできるリソースカテゴリを定義します。 トークンには `voice:read` ボイス構成を読み取ることができますが、それを変更することはできません。スコープは次の `resource:action` パターン： `account:read`再統合されたドキュメントが以前検証に失敗しました：Markdown テキストリテラルの回復は、等しい長さを有する JSON 文字列配列を返す必要があります `organization:write`指定されたセグメントのみを修正翻訳して返してください。このセグメントに含まれるすべての必須トークンを保持してください。 `glossary:admin` 用語管理など。

**ポリシー** ユーザーと特定のリソースとの関係を検証します。正しいスコープを持つ有効なトークンですら、ユーザーが所属していない組織にはアクセスできません。すべてのリクエストは両方のレイヤーに対してチェックされます。

## ページネーション、フィルタリング、ソート

すべてのリストエンドポイントは、一貫したメタデータと共にページネーションされた結果を返します。

すべてのレスポンスには `total_count`, `total_pages`, `current_page`, `page_size`, `has_next_page?`, そして `has_previous_page?` そのため、クライアントは推測せずにページネーションのコントロールを作成できます。

任意のインデックス化されたフィールドを使用してフィルタリング `filters[field]=value` クエリパラメータ。昇順または降順でソート。 `order_by[]` パラメータ。インターフェイスはすべてのリソースで共通しています。

## OpenAPI とインタラクティブなドキュメント

完全な OpenAPI 3.1 仕様は以下の場所から取得可能です `/api/openapi.json`。この [インタラクティブ API リファレンス](/docs/reference/apis/rest) Scalar で提供され、エンドポイントの探索、スキーマの確認、およびブラウザから直接テストリクエストの作成が可能です。

任意の言語のクライアントライブラリは仕様から生成可能です。この契約はバージョン管理され、安定しています。そのため、新機能のリリース時には、あなたの統合が影響を受けることはありません。
