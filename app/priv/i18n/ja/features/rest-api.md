## 開発者優先

REST API は Glossia の基盤です。ダッシュボード、CLI、[MCP サーバー](/features/mcp-server) はすべて同じエンドポイントを利用します。機能を追加する際は、まず API に実装し、その後、他のすべての場所で展開されます。

つまり、UI に制約されるということは決してありません。CI/CD 統合からカスタムダッシュボードまで、あなたがいずれ構想できるあらゆるワークフローは、同じ安定的かつドキュメント化されたインタフェースの上に構築できます。

## 認証

Glossia は、すべての API 認証に OAuth 2.1 と PKCE を使用します。このフローではファーストパーティとサードパーティのクライアントの両方がサポートされています。完全な手順については [認証と認可のドキュメント](/docs/reference/apis/authentication) を参照してください。

**ダイナミック クライアント登録** - クライアントはリダイレクト URI および委任タイプとともに、プログラムとして `/oauth/register` で登録します。手動承認ステップはありません、ポータルを経由するクリックもありません。

**PKCE を用いた認証コード** - ユーザーはブラウザベースの同意画面を通じてクライアントを承認します。PKCE 拡張機能により、秘密を保存できないパブリック クライアントである場合であっても、トークンの安全性が保証されます。

**トークンのライフサイクル** - アクセストークンは標準 OAuth エンドポイントを通じて交換、検証、および無効化できます。トークンエンドポイントでのレート制限は、ブルートフォース攻撃を防ぎます。

## 認可

アクセス制御は 2 つのレイヤーを使用します。[認証ドキュメント](/docs/reference/apis/authentication) は、スコープ、ロール、および完全な権限マトリックスを詳細に説明しています。

**スコープ** はトークンがアクセスできるリソースのカテゴリを定義します。`voice:read` スコープを持つトークンは音声設定を読み込むことができますが、変更することはできません。スコープは `resource:action` パターンに従います：`account:read`、`organization:write`、用語管理の `glossary:admin` など。

**ポリシー** は、ユーザーと特定のリソースの関係を検証します。正しいスコープを持つ有効なトークンであっても、ユーザーが所属していない組織にはアクセスできません。すべてのリクエストは両方のレイヤーに対してチェックされます。

すべてのレスポンスには `total_count`、`total_pages`、`current_page`、`page_size`、`has_next_page?`、および `has_previous_page?` が含まれているため、クライアントは推測なくページネーション コントロールを構築できます。

インデックス化されているフィールドのいずれかを `filters[field]=value` クエリパラメータでフィルタリングします。`order_by[]` パラメータで昇順または降順にソートします。すべてのリソースでインタフェースは同じです。

## OpenAPI およびインタラクティブ ドキュメント

完全な OpenAPI 3.1 仕様書は `/api/openapi.json` で利用可能です。[インタラクティブ API 参考文献](/docs/reference/apis/rest) は Scalar により提供され、エンドポイントを探索し、スキーマを検証し、ブラウザから直接テストリクエストを送信できます。

あらゆる言語のクライアント ライブラリは仕様から生成できます。契約はバージョン管理され安定しているため、新機能をリリースしても統合が破損することはありません。
