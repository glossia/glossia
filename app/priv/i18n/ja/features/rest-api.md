## 開発者ファースト

REST API は Glossia の中核です。ダッシュボード、CLI、および [MCP サーバー](/features/mcp-server) すべては同じエンドポイントを利用します。新機能が追加された際は、まず API に実装され、その後他の箇所にも反映されます。

UI による制限はありません。CI/CD 統合からカスタムダッシュボードまでのあらゆるワークフローを、同じ安定した文書化されたインターフェースの基盤として構築可能です。

## 認証

Glossia はすべての API 認証に OAuth 2.1 および PKCE を採用しています。このフローはファーストパーティとサードパーティのクライアントの双方をサポートします。詳細は [認証および権限ドキュメント](/docs/reference/apis/authentication) 完全な手順をご覧ください。

**動的クライアント登録** -- クライアントはプログラムにより登録されます `/oauth/register` 自身のリダイレクトURI と言渡タイプを使用して。手動承認ステップはなく、クリックして通るポータルもありません。

**PKCE を使用した認証コード** -- ユーザーはブラウザベースの同意画面を通じてクライアントを認証します。PKCE 拡張機能により、シークレットを保存できない公開クライアントであってもトークンは安全に保たれます。

**トークンライフサイクル** -- アクセストークンは標準の OAuth エンドポイントを通じて交換、イントロスペクション、および取り消しを行うことができます。トークンエンドポイントのレート制限はブルートフォース攻撃から保護します。

## 認可

アクセス制御は 2 つの層を使用します。その [認証ドキュメント](/docs/reference/apis/authentication) は、スコープ、ロール、および完全な権限マトリックスを詳しく説明します。

**スコープは** 定義します。トークン `voice:read` が音声設定を読み取ることができますが、変更することはできません。スコープは `resource:action` パターン： `account:read`, `organization:write`, `glossary:admin` ,用語管理など。

**ポリシー** ユーザーと特定のリソースとの関係を確認します。正しいスコープを持つ有効なトークンであっても、ユーザーが所属していない組織にはアクセスできません。すべてのリクエストは両方のレイヤーでチェックされます。

すべてのリストエンドポイントは、一貫したメタデータを伴うページネーション結果を返します：

すべてのレスポンスには `total_count`" `total_pages`, `current_page`再構成ドキュメントは以前検証に失敗しました：Markdown テキストノードの回復により空の翻訳が生成されました `page_size`再構成ドキュメントの検証が以前失敗しました：Markdown text-node の復元により空の翻訳が生成されました `has_next_page?`、および `has_previous_page?` そのため、クライアントは推測することなくページネーションコントロールを構築できます。

インデックス化されたフィールドを使用してフィルターする `filters[field]=value` クエリパラメータ。昇順または降順でソートし `order_by[]` パラメータ。すべてのリソースでインターフェースは同じです。

## OpenAPI およびインタラクティブドキュメント

完全な OpenAPI 3.1 仕様は、次の場所で利用可能です `/api/openapi.json`。この [インタラクティブ API リファレンス](/docs/reference/apis/rest) Scalar によって提供され、エンドポイントを探索、スキーマを検査し、ブラウザから直接テストリクエストを作成できます。

あらゆる言語のクライアントライブラリは、仕様から生成できます。仕様はバージョン管理され、安定しており、新機能をリリースした際、あなたの統合が破損することはありません。
