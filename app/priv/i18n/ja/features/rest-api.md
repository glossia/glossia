## 開発者ファースト

REST API は Glossia の中核です。ダッシュボード、CLI、および [MCP サーバー](/features/mcp-server) はすべて同じエンドポイントを消費します。新しい機能を追加した場合、それは最初に API に実装され、その後他のすべての場所で利用可能になります。

これにより、UI によってワークフローが制限されることは決してありません。あなたが想像できるあらゆるワークフロー、CI/CD 統合からカスタムダッシュボードまで、同じ安定したドキュメントされたインターフェースの上に構築できます。

## 認証

Glossia はすべての API 認証に OAuth 2.1 と PKCE を使用します。このフローでは、ファーストパーティおよびサードパーティのクライアントの両方をサポートします。詳細な説明については [認証と認可ドキュメント](/docs/reference/apis/authentication) をお読みください。

**動的クライアント登録** -- クライアントはリダイレクト URI と grant types を指定して、`/oauth/register` でプログラム自動的に登録します。手動承認の手順も、ポータルをクリックすることもありません。

**PKCE を伴う認証コード** -- ユーザーはブラウザベースの同意画面を通じてクライアントを認証します。PKCE 拡張により、非公開情報を保存できないパブリッククライアントであってもトークンの安全性を確保できます。

**トークンのライフサイクル** -- アクセストークンは標準的な OAuth エンドポイントを通じて交換、整数化、そして廃棄できます。トークンエンドポイントでのレート制限はブルートフォース攻撃からの保護を提供します。

## 認可

アクセス制御は 2 つのレイヤーを使用します。[認証ドキュメント](/docs/reference/apis/authentication) はスコープ、ロール、完全な許可マトリックスについて詳しく記載しています。

**スコープ** はトークンがアクセスできるリソースのカテゴリを定義します。`voice:read` を含むトークンは音声設定を読み込めますが、変更することはできません。スコープは `resource:action` パターンに従います：`account:read`、`organization:write`、`glossary:admin` は辞書管理のために、などです。

**ポリシー** はユーザーと特定のリソースの関係を検証します。正しいスコープを持つ有効なトークンの場合でも、ユーザーが所属していない組織にはアクセスできません。すべてのリクエストは両方のレイヤーに対してチェックされます。

## ページネーション、フィルタリング、ソート

すべてのリストエンドポイントは一貫したメタデータを含むページネーション結果を返します。

すべてのレスポンスは `total_count`, `total_pages`, `current_page`, `page_size`, `has_next_page?`, および `has_previous_page?` を含み、これによりクライアントは推測することなくページネーションコントロールを構築できます。

`filters[field]=value` クエリパラメータを使用して任意のインデックスフィールドでフィルタリングできます。`order_by[]` パラメータを使用して昇順または降順でソートできます。すべてのリソースではインターフェースは同じです。

## OpenAPI とインタラクティブドキュメント

完全な OpenAPI 3.1 仕様が `/api/openapi.json` で利用可能です。[インタラクティブ API リファレンス](/docs/reference/apis/rest) は Scalar によって提供されており、エンドポイントを探索、スキーマを検査し、ブラウザから直接テストリクエストを作成できます。

どの言語のクライアントライブラリも仕様から生成できます。契約はバージョン化され安定しており、新しい機能をリリースしても統合が破損することはありません。
