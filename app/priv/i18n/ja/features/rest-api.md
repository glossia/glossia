## 開発者第一

REST API は Glossia の中核です。ダッシュボード、CLI、および [MCP サーバー](/features/mcp-server) すべてが同じエンドポイントを利用します。機能を追加すると、まず API に実装され、そこから他の場所でも利用できます。

これにより、UI での制限は一切ありません。CI/CD 統合からカスタムダッシュボードまで、あらゆるワークフローは、同じ安定し、文書化されたインターフェースの上に構築可能です。

## 認証

Glossia はすべての API 認証に OAuth 2.1 と PKCE を使用します。このフローはファーストパーティとサードパーティのクライアントの両方をサポートします。ご参照 [認証と認可のドキュメント](/docs/reference/apis/authentication) 完全な手順の詳細については、

**動的クライアント登録** -- クライアントはプログラム的に、 `/oauth/register` リダイレクト URI およびグラントタイプを伴う。手動承認ステップはなく、クリックを通じてのポータルもない。

**PKCE 付の認証コード** -- ユーザーはブラウザベースの同意画面を通じてクライアントを承認します。PKCE 拡張機能は、秘密情報を保存できない公開クライアントであっても、トークンの安全性が保たれることを保証します。

**トークンのライフサイクル** -- アクセストークンは標準 OAuth エンドポイントで交換、確認、および取り消しが可能です。トークンエンドポイントのレート制限はブルートフォース攻撃から保護します。

## 権限

アクセス制御は 2 つのレイヤーを使用します。特定の [認証ドキュメント](/docs/reference/apis/authentication) スコープ、ロール、および完全な権限マトリックスを詳しく網羅します。

**スコープ** トークンがアクセスできるリソースのカテゴリを定義します。スコープを有するトークンは `voice:read` 特定のボイス設定を読み取れますが、変更できません。スコープは `resource:action` パターン： `account:read`、 `organization:write`、 `glossary:admin` 、用語集の管理、など。

**ポリシー** ユーザーと特定のリソースとの関係を検証します。有効で適切なスコープを持つトークンでも、ユーザーが所属していない組織にはアクセスできません。各リクエストは両方の層でチェックされます。

## ページネーション、フィルタリング、ソート

すべてのリストエンドポイントは、一貫したメタデータを含むページネーション結果を返します:

すべてのレスポンスには `total_count`, `total_pages`, `current_page`, `page_size`, `has_next_page?`, そして `has_previous_page?` そのため、クライアントは推測することなくページネーション制御を構築できます。

任意のインデックスされたフィールドを指定してフィルタリング `filters[field]=value` クエリパラメータを使用し、昇順または降順でソートします。 `order_by[]` パラメータ。すべてのリソースでインターフェースは統一されています。

## OpenAPI とインタラクティブドキュメント

完全な OpenAPI 3.1 仕様は以下の場所で利用可能です `/api/openapi.json`。次の [インタラクティブ API リファレンス](/docs/reference/apis/rest) Scalar によって提供されており、エンドポイントを探索し、スキーマを検証したり、ブラウザから直接テストリクエストを作成できます。

どの言語のクライアントライブラリも仕様から生成できます。契約はバージョン管理されており安定しており、新機能をリリースしてもあなたの統合は破綻しません。
