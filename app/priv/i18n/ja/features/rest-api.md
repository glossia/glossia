## 開発者ファースト

REST API は Glossia の中核です。ダッシュボード、CLI、[MCP server](/features/mcp-server) はすべて同じエンドポイントを消費します。新機能を追加すると、まず API に実装され、その後他のすべての箇所に展開されます。

これにより、UI の制限を受けることはありません。どのワークフローを想像できるときも、CI/CD 統合からカスタムダッシュボードまで、同じ安定したドキュメント付きインターフェースの上に構築可能です。

## 認証

Glossia はすべての API 認証に OAuth 2.1 及び PKCE を用います。フローはファーストパーティおよびサードパーティのクライアントの両方をサポートします。完全な手順については [認証と権限付与ドキュメント](/docs/reference/apis/authentication) をご覧ください。

**動的クライアント登録** -- クライアントはリダイレクト URI とグラントタイプを指定して `/oauth/register` でプログラム的に登録します。手動承認ステップもなく、ポータルを介してクリックする必要もありません。

**PKCE を使用した認可コード** -- ユーザーはブラウザベースの同意画面を通じてクライアントを認可します。PKCE 拡張機能により、秘密を保存できないパブリッククライアントであってもトークンのセキュリティを保証します。

**トークンのライフサイクル** -- アクセストークンは標準 OAuth エンドポイントを介して交換、確認され、使用停止できます。トークンエンドポイントでのレート制限はブルートフォース攻撃から保護します。

## 権限付与

アクセスキontrolは 2 つのレイヤーを使用します。[authentication docs](/docs/reference/apis/authentication) はスコープ、役割、そして完全な権限マトリクスを詳しく説明しています。

**スコープ** はトークンがアクセスできるリソースカテゴリを定義します。`voice:read` を持つトークンは音声構成を読み取れますが、変更できません。スコープは `resource:action` パターンに従います：`account:read`, `organization:write`, `glossary:admin` 向けを含め、その类推。

**ポリシー** はユーザーと特定のリソース間の関係を検証します。正しいスコープを持つ有効なトークンでも、ユーザーが属していない組織にはアクセスできません。どのリクエストも両レイヤーに対してチェックされます。

## ページネーション、フィルタリング、ソート

すべてのリストエンドポイントは一貫したメタデータを伴ったページネーションされた結果を返します。

どのレスポンスも `total_count`, `total_pages`, `current_page`, `page_size`, `has_next_page?`, `has_previous_page?` を含みます。これにより、クライアントは推測の必要なくページネーションコントロールを構築できます。

任意のインデックス済みフィールドを `filters[field]=value` クエリパラメータを使用してフィルタリングします。`order_by[]` パラメータを使用して昇順または降順でソートします。インターフェーはすべてのリソースで同一です。

## OpenAPI とインタラクティブドキュメント

完全な OpenAPI 3.1 スペシフィケーションは `/api/openapi.json` で利用可能です。[インタラクティブ API リファレンス](/docs/reference/apis/rest) は Scalar で動作し、ブラウザから直接リソースを閲覧、スキーマを確認し、テストリクエストを作成できます。

どの言語のクライアントライブラリも性能から生成できます。契約はバージョン管理され安定しており、新機能リリース時に統合が破損することはありません。
