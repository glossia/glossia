## 開発者优先

REST API は Glossia の中核です。ダッシュボード、CLI、そして [MCP サーバー](/features/mcp-server) はすべて同じエンドポイントを利用します。機能追加時には、まず API に実装され、そこから他全ての場所で利用可能になります。

これは UI によって決して制限されないことを意味します。想定できるあらゆるワークフローは、CI/CD インテグレーションからカスタムダッシュボードまで、同じ安定したドキュメント化されたインターフェースの上に構築可能です。

## 認証

Glossia はすべての API 認証に OAuth 2.1 および PKCE を使用します。このフローはファーストパーティおよびサードパーティのクライアントの両方をサポートします。以下の [認証および認可のドキュメント](/docs/reference/apis/authentication) 完全なウォークスルーについては。

**ダイナミック クライアント登録** -- クライアントはプログラムにより以下で登録されます `/oauth/register` リダイレクト URI と グラント タイプを使用します。手動承認のステップはなく、ポータル経由でクリックする必要はありません。

**PKCE を使用した Authorization Code** -- ユーザーはブラウザベースの同意画面を通じてクライアントへの権限を付与します。PKCE 拡張機能により、機密情報が保存できない公開クライアントであってもトークンの安全性が維持されます。

**トークンのライフサイクル** -- 標準の OAuth エンドポイントを使用してアクセストークンを交換、確認、および無効化できます。トークンエンドポイントのレート制限はブルートフォース攻撃から保護します。

## 認証認可

アクセス制御には 2 つの層を使用します。 [認証ドキュメントは](/docs/reference/apis/authentication) スコープ、ロール、および完全なアクセス権限のマトリクスを詳しく説明します。

**スコープは** トークンがアクセスできるリソースのカテゴリを定義します。トークンに `voice:read` 音声設定を読み取り、変更できません。スコープは次の `resource:action` パターン： `account:read`, `organization:write`, `glossary:admin` ,用語の管理、などなど、

**ポリシー** ユーザーと特定のリソースとの関係を確認します。有効なトークンで適切なスコープがあっても、ユーザーが所属していない組織にはアクセスできません。すべてのリクエストは両方のレイヤーでチェックされます。

## ページネーション、フィルタリング、ソート

すべてのリストエンドポイントは一貫したメタデータを含むページネーション結果を返します:

各レスポンスに含まれます `total_count`再構成されたドキュメントが以前検証に失敗しました：マークダウンテキストリテラル復元は一致する長さの JSON 文字列配列を返す必要があります `total_pages`この提供された区間の適切な翻訳だけを返してください。この区間に存在するすべての必須トークンを維持してください。 `current_page`再構成ドキュメントの検証が以前に失敗しました：Markdown テキストリテラルの回復は、一致する長さの JSON 文字列配列を返す必要があります `page_size`, `has_next_page?`、および `has_previous_page?` これにより、クライアントは推測せずにページネーション制御を構築できます。

任意のインデックス化されたフィールドを使用してフィルタリング `filters[field]=value` クエリパラメータ。昇順または降順でソートします。 `order_by[]` パラメータ。すべてのリソースでインターフェースは同じです。

## OpenAPI とインタラクティブドキュメント

完全な OpenAPI 3.1 仕様は以下の場所で利用可能です `/api/openapi.json`。インタ [インタラクティブ API リファレンス](/docs/reference/apis/rest) Scalar で提供され、エンドポイントを探索し、スキーマを検証し、ブラウザから直接テストリクエストを送信できます。

任意の言語のクライアントライブラリを仕様から生成可能です。契約はバージョン管理され、安定しているため、新機能のリリース時にもお客様の統合に影響を及ぼしません。
