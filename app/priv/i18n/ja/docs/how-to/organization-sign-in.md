## Id ntity provider を接続する

組織管理者は、**設定 → 認証** でワークアイデンティティプロバイダーを接続できます。

1. **Google Workspace** または **Okta** を選択し、チームのワークメールドメインを入力します。
2. Okta の場合、[OpenID Connect](https://developer.okta.com/docs/guides/implement-grant-type/authcode/main/) を使用して Web アプリケーションを作成します。その Issuer、クライアント ID、およびクライアントシークレットを入力します。Glossia は標準的な Okta オrganization Issuer および `/oauth2/default` 認証サーバーをサポートしています。シークレットは保存時に暗号化されます。編集時にシークレットを空にすると、保存値が維持されます。
3. Okta の場合、Glossia に表示されているリダイレクトアドレスを Id ntity provider と登録します。Google Workspace の場合、Glossia が Google 接続を管理するため、Google アプリケーションを作成したり、コールバックアドレスを登録する必要はありません。
4. 設定を保存します。ドメインプロバイダーを通じて表示された DNS TXT レコードを追加し、**ドメインの検証** を選択します。メールアドレスドメインを変更すると、新しい検証トークンが作成され、再検証されるまで組織サインインが無効になります。
5. チームメンバーは、ログインページでワークメールを入力し、**組織との続行** を選択します。Google Workspace メンバーも **Google でログイン** を使用できます。

## Google Workspace のセットアップ

Glossia が Google アプリケーションの認証情報を管理します。OAuth アプリケーションを作成したり、Google Admin にカスタム SAML アプリケーションを追加したり、リダイレクトアドレスを登録する必要はありません。既存の Google Workspace ドメインの場合は、セットアップが Glossia および DNS プロバイダーで発生します:

1. **設定 → 認証** で、**Google Workspace** を選択し、ワークメールドメインを入力し、**認証設定の保存** を選択します。
2. DNS をホストするプロバイダーで、ドメインの DNS 設定を開きます。Google Workspace に限られません。**ドメイン所有権の検証** に表示されているレコードを追加します:

   | Field | Value |
   | --- | --- |
   | Type | `TXT` |
   | Name / Host | Glossia で表示されている **レコード名** など、例えば `_glossia-verification.example.com` |
   | Value / Content | Glossia で表示されている **レコード値** で、`glossia-domain-verification=` から始まります |

   一部の DNS プロバイダーはドメインを自動的に追加します。その場合、ホストには `_glossia-verification` だけを記入し、ドメインが重複しないようにします。検証後にはレコードを維持してください。
3. Glossia に戻り、**ドメインの検証** を選択します。検証に失敗した場合は、名前と値を確認し、DNS 変更が反映される時間を待ち、再度お試しください。
4. チームメンバーに、ログインページでワークメールを入力し、**組織との続行** を選択、または **Google でログイン** を使用することを依頼します。

Glossia は Google による検証済みメールと [ホストドメイン声明](https://developers.google.com/identity/openid-connect/openid-connect#an-id-tokens-payload) をチェックします。同じメールサフィックスを持つ個人的な Google アカウントは資格がありません。

### Google がサインインを拒否した場合

通常は Google 側での設定は必要ありません。組織がサードパーティ周辺アプリへのアクセスを制限している場合、Google Workspace 管理者が Glossia を承認する必要がある場合があります:

1. 管理者アカウントを使用して [Google 管理コンソール](https://admin.google.com/) にログインします。
2. **セキュリティ → アクセスおよびデータ制御 → API 制御 → サードパーティアプリへのアクセス管理** に移動します。
3. アクセス済みアプリのリストで Glossia を検索します。リストになければ、新しいアプリの設定 **新規アプリの設定** を使用して、アプリ名または OAuth クライアント ID で検索します。OAuth クライアント ID は Glossia の共有 Google 接続に属しており、作成する必要のあるアプリケーションではありません。
4. 要求されたサインイン权限をレビューし、組織のポリシーに従って関連ユーザーにアクセスを許可します。アクセスレベルおよび管理者要求については、Google の [サードパーティおよび内部アプリが Google Workspace データにアクセスする制御](https://support.google.com/a/answer/7281227) ガイドを参照してください。
5. ポリシー変更の有効後、ワークアカウントでサインインを再試行します。

## 登録と権限の管理

検証済みのプロバイダー ID に正確な照合ワークメールドメインは自動的に組織に参加します。既存の Glossia アカウントが初めて Okta に接続する場合、組織サインインを開始する前に既存の方法でログインしてください。これでプロバイダーを安全にリンクでき、他の Glossia アカウントを Okta 管理者に引き渡すことはありません。他のプロバイダーを通じた公開登録は引き続き興味フォームを使用します。プロバイダーを無効化すると、既存のメンバーシップを削除せずに組織サインインが停止します。

新メンバーは、アカウント、組織、プロジェクト、ボイス、辞書、ディスカッション、およびチケットへの基本的な読み取りアクセスを受け取ります。加入後に追加アクセスを許可するには [メンバー権限の管理](/docs/how-to/member-permissions) を参照してください。

## アクセス保護

ドメイン所有権検証は 30 日有効で、毎日自動的にチェックされます。検証レコードを維持してください。消滅した場合、最後の成功した検証の有効期限に達するとサインインが停止します。レコードを復元し、認証設定から再度検証してください。プロバイダーの変更または組織サインインの無効化は検証をクリアし、前のプロバイダーの資格を削除します。未検証の声明はドメインを予約しません。

既存アカウントの場合は、まず既存の方法でログインし、`/auth/login` にアクセスしてワークメールサインインを開始し、ワーク ID を接続します。Google は同じプロバイダー部分を持つ既にリンクされた Google ID を使用することもできます。メールアドレス単体の照合で既存アカウントに接続することは決してありません。

メンバーの削除は自動再登録をブロックします。そのワーク ID がアクティブであっても、管理者が明示的に追加または招待して初めてアクセスを復元できます。

メンバー招待管理、アクセスクレデンシャル、言語モデル編集、および組織削除は管理者の任務です。これらの権限はメンバースコープチェックボックスを通じて委任できません。認証設定、ドメイン検証、およびスコープ変更は監査イベントを放出します。
