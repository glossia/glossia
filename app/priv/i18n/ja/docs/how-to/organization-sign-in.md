## あなたのアイデンティティプロバイダーを接続

組織管理者はワークアイデンティティプロバイダーを以下で接続できます **設定 → 認証**.

1. 選択 **Google Workspace** または **Okta** 、チームの仕事用メールアドレスのドメインを入力してください。
2. Okta の場合、以下を使用し、Web アプリケーションを作成 [OpenID Connect](https://developer.okta.com/docs/guides/implement-grant-type/authcode/main/)、発行元、クライアント ID、クライアントシークレットを入力してください。Glossia は標準的な Okta オルガナライゼーション発行元および `/oauth2/default` 認証サーバー。シークレットは暗号化され保存されます。編集時にシークレットを空にすると、保存済みの値が維持されます。
3. Okta の場合、Glossia に表示されたリダイレクトアドレスをアイデンティティプロバイダーに登録してください。Google Workspace の場合、Glossia が Google 接続を管理するため、Google アプリケーションの作成やコールバックアドレスの登録は不要です。
4. 設定を保存してください。表示された DNS の TXT レコードをドメインプロバイダーから追加し、その後選択 **ドメインを検証**. 電子メールドメインを変更すると、新しい確認トークンが作成され、再認証されるまで組織サインインが無効化されます。
5. チームメンバーはログインページで勤務先メールを入力し、 **この組織で続ける**. Google Workspace のメンバーは、以下を使用することもできます。 **Google でのログイン**.

## Google Workspace を設定

Glossia は Google アプリケーションの認証情報を管理します。Google Cloud で OAuth アプリケーションを作成する必要はありません、Google Admin にカスタム SAML アプリケーションを追加する必要もありません、またはリダイレクトアドレスを登録する必要はありません。既存の Google Workspace ドメインの場合、設定は Glossia と DNS プロバイダーの両方で行われます：

1. 設定 **設定 → 認証**, 選択 **Google Workspace**, 業務用メールアドレスのドメインを入力し、選択 **認証設定を保存**。

2. ドメインの DNS 設定を開き、DNS をホストするプロバイダーのドメインにアクセスしてください（必ずしも Google Workspace でなくてもよい）。表示されたレコードを追加 **ドメイン所有権の検証**:
   
   | 項目 | 値 |
   | --- | --- |
   | タイプ | `TXT` |
   | 名称 / ホスト | その **レコード名** Glossia で表示され、例えば `_glossia-verification.example.com` |
   | 値 / 内容 | 該当 **レコード値** Glossia で表示され、最初から `glossia-domain-verification=` |
   
   一部の DNS 事業者はドメインを自動的に追加する場合があります。その場合、のみ入力 `_glossia-verification` ホストとして、ドメインが重複して含まれないようにしてください。検証後、記録は変更せずに置きます。

3. Glossia に戻って選択してください **ドメインを検証**. 検証に失敗した場合は、名前と値を確認し、DNS 変更が反映されるまで時間を置いてから再度お試しください。

4. チームメンバーにログインページで勤務用メールアドレスを入力してもらい、選択してください **所属組織で続ける**, または使用する **Google でログイン**。

Glossia は Google の検証済み emailAddress を [ホストドメインの主張も確認します](https://developers.google.com/identity/openid-connect/openid-connect#an-id-tokens-payload)；同じメールサフィックスを持つ個人用 Google アカウントは条件を満たしません

### Google でログインがブロックされた場合

通常は Google 側の設定は不要です。組織がサードパーティ製アプリケーションへのアクセスを制限している場合、Google Workspace 管理者が Glossia を承認する必要がある場合があります：

1. 管理者アカウントで Google 管理コンソールに [サインインしてください](https://admin.google.com/) 管理者アカウントを使用します
2. へ移動 **セキュリティ → アクセスとデータ管理 → API 管理 → サードパーティ製アプリへのアクセス管理**.
3. アクセス済アプリ一覧で Glossia を探してください。一覧にない場合は、 **新アプリを設定** アプリ名または OAuth クライアント ID で検索します。この ID は Glossia の共有 Google 接続に属し、作成する必要のあるアプリケーションではありません。
4. 要求されたサインイン権限を確認し、組織のポリシーに従って関連ユーザーにアクセスを許可します。Google の [Google Workspace データにアクセスするサードパーティ製アプリと内部アプリを管理する](https://support.google.com/a/answer/7281227) アクセスレベルと管理者要件のガイド。
5. ポリシー変更生效后、勤務先アカウントでサインインを再試行してください。

## 登録と権限の管理

正確な一致する勤務先メールアドレスドメインを持つ検証済みプロバイダー ID は自動的に組織に参加します。既存の Glossia アカウントが初めて Okta を接続する場合、組織サインインを開始する前に既存の方法でサインインしてください。これによりプロバイダーが安全にリンクされ、Okta 管理者が別の Glossia アカウントを乗っ取るのを防ぎます。他のプロバイダーを通じた公開登録は引き続き関心フォームを使用します。プロバイダーを無効にすることは既存のメンバーシップを削除せずに組織サインインのみを停止します。

新しいメンバーは、アカウント、組織、プロジェクト、声、用語集、ディスカッション、およびチケットに対する基本的な読み取りアクセス権を受け取ります。追加のアクセス権を付与するには、[メンバーの権限管理](/docs/how-to/member-permissions) を参照してください。

## アクセスの安全策

ドメイン所有権検証は 30 日間有効で、毎日自動的に確認されます。検証記録を維持してください。記録が消失すると、最後の成功した検証が期限切れになるとサインインが停止します。記録を復元し、認証設定から再度検証を行ってください。プロバイダーの変更または組織サインインの無効化は検証を解除し、前回のプロバイダーに属する認証情報を削除します。未検証の証明はドメインを予約しません。

既存のアカウントの場合、まず既存の方法でサインインし、`/auth/login` に移動して勤務先メールアドレスのサインインを開始し、勤務先 ID を接続してください。Google は同じプロバイダーサブジェクトを持つ既にリンクされた Google ID も使用可能です。メールアドレスの一致だけでは既存のアカウントを接続することは決してできません。

メンバーの削除は自動的な再登録をブロックします。勤務先 ID が引き続き有効であっても、アクセスを復元するには、管理者が明示的に再度追加または招待する必要があります。

メンバー招待管理、アクセス認証情報、言語モデル編集、および組織削除については、管理者の責任に留まります。これらの権限はメンバーのスコープチェックボックスを通じて委任することはできません。認証構成、ドメイン検証、およびスコープ変更は監査イベントを生成します。
