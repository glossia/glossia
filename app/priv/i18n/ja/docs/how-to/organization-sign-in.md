## ID プロバイダを接続

組織管理者は **設定 → 認証** で業務用アイデンティティプロバイダーを接続できます。

1. **Google Workspace** または **Okta** を選択し、チームの業務上のメールアドレスドメインを入力してください。
2. Okta の場合、[OpenID Connect](https://developer.okta.com/docs/guides/implement-grant-type/authcode/main/) を使用してウェブアプリケーションを作成してください。発行元、クライアント識別子、およびクライアントシークレットを入力します。Glossia は標準の Okta 組織発行元と `/oauth2/default` 認証サーバーをサポートしています。シークレットは保存された状態で暗号化されています。編集時にシークレットを空のままにすると、保存された値は維持されます。
3. Okta の場合、Glossia で表示されているリダイレクトアドレスを ID プロバイダに登録してください。Google Workspace の場合、Glossia が Google の接続を管理するため、Google アプリケーションの作成やコールバックアドレスの登録は不要です。
4. 設定を保存してください。表示されている DNS TXT レコードをドメインプロバイダを通じて追加し、その後 **ドメインの確認** を選択してください。メールアドレスドメインの変更には新しい検証トークンが作成され、再度検証されるまで組織のサインインは無効になります。
5. チームメンバーはログインページで業務上のメールアドレスを入力し、**この組織で続行** を選択します。Google Workspace メンバーは **Google でログイン** も使用することが可能です。

## Google Workspace のセットアップ

Glossia は Google アプリケーションの認証情報を管理します。Google Cloud で OAuth アプリケーションを作成したり、Google Admin でカスタム SAML アプリを追加したり、リダイレクトアドレスを登録する必要はありません。既存の Google Workspace ドメインの場合、セットアップは Glossia とドメインのプロバイダで行われます：

1. **設定 → 認証** で、**Google Workspace** を選択し、業務上のメールアドレスドメインを入力し、**認証設定の保存** を選択してください。
2. DNS をホストしているプロバイダ（必ずしも Google Workspace ではない）のドメイン DNS 設定を開いてください。表示されている **ドメイン所有権の確認** で示されているレコードを追加してください：

   | フィールド | 値 |
   | --- | --- |
   | タイプ | `TXT` |
   | 名前 / ホスト | Glossia で表示されている **レコード名**、例えば`_glossia-verification.example.com` のように |
   | 値 / コンテンツ | Glossia で表示されている **レコード値** を始め、`glossia-domain-verification=` のように |

   一部の DNS プロバイダーはドメインを自動的に付与します。その場合、ドメインが 2 回含まれないようにホストには `_glossia-verification` のみ入力してください。検証後に記録を維持してください。
3. Glossia へ戻り、**ドメインの確認** を選択してください。検証に失敗した場合は、名と値を確認し、DNS の変更が反映される時間を待ってから再試行してください。
4. チームメンバーにログインページで業務上のメールアドレスを入力し、**この組織で続行** を選択するか、また **Google でログイン** を利用してもらうようお願いしてください。

Glossia は Google の検証済みのメールアドレスと [ホストドメインの主張](https://developers.google.com/identity/openid-connect/openid-connect#an-id-tokens-payload) を確認します；同じメールアドレス末尾を持つ個人 Google アカウントは条件を満たしません。

### Google によるサインインのブロック時

Google 側での設定は通常不要です。組織がサードパーティのアプリケーションへのアクセスを制限している場合、Google Workspace アドミニストレーターが Glossia の承認を行う必要がある場合があります：

1. 管理アカウントを使用して [Google アドミンプレイス](https://admin.google.com/) にサインインしてください。
2. **セキュリティ → アクセスとデータ制御 → API 制御 → サードパーティアプリのアクセス管理**を選択してください。
3. アクセスされたアプリのリストで Glossia を探してください。リストされていない場合は、アプリ名または OAuth クライアント ID で検索するために **新しいアプリの設定** を使用してください。OAuth クライアント ID は、作成する必要のあるアプリケーションではなく、Glossia の共有 Google 接続に属しています。
4. 要求されたサインイン権限を確認し、組織のポリシーに従ってアクセスを許可してください。アクセスレベルと管理者の要件については、Google の [サードパーティおよび内部アプリによる Google Workspace データへのアクセスの制御](https://support.google.com/a/answer/7281227) ガイドを参照してください。
5. ポリシーの変更が効力を発揮した後、作業アカウントでサインインを再試行してください。

## 入会と権限の管理

正確に一致するメールアドレスドメインを持つ検証済みのプロバイダ識別子は、自動的に組織に参加します。最初の Okta 接続を行う既存の Glossia アカウントの場合、組織サインインを開始する前に既存の方法でサインインしてください。これでプロバイダは安全にリンクされ、Okta 管理者が別の Glossia アカウントを占有する可能性は阻止されます。他のプロバイダを通じた公開登録は、引き続き-interest 形式を使用します。プロバイダの無効化は、既存のメンバーシップを削除せずに組織のサインインを停止させます。

新メンバーは、アカウント、組織、プロジェクト、声、用語集、議論、チケットに対して基本的な読取アクセスを受けます。追加のアクセスを付与するには、[メンバー権限の管理](/docs/how-to/member-permissions) を参照してください。

## アクセス safeguards

ドメイン所有権の検証は 30 日間有効であり、毎日自動的にチェックされます。検証記録を維持してください。記録が消失した場合、最終的な検証の有効期限が切れた時点でサインインが停止します。記録を復元し、\_authentication\_ から再度検証してください。プロバイダーの変更や組織サインインの無効化は、検証をクリアし、以前のプロバイダーに所属する認証情報を削除します。未検証のクレームはドメインを予約しません。

既存のアカウントの場合、最初に既存の方法でサインインし、その後 `/auth/login` を訪問して業務上のメールアドレスのサインインを開始し、業務上の ID を接続してください。Google は、同じ組織主題を持つ既にリンクされた Google アイデンティティを使用することもできます。メールアドレスの一致のみは決して既存のアカウントを接続しません。

メンバーの削除は自動的な再登録をブロックします。アクセスを復元するには、管理者が明示的に再度追加または招待を行う必要があります。彼らの業務上の ID が依然として有効であっても同様です。

メンバー招待の管理、認証アクセス権限、言語モデルの編集、および組織の削除は管理者の責任です。これらの権限は、メンバースコープのチェックボックスを介して委任することはできません。認証設定、ドメインの検証、およびスコープの変更は監査イベントを発します。
