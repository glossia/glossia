## アイデンティティプロバイダーを接続する

組織管理者は **設定 → 認証** でワークアイデンティティプロバイダーを接続できます。

1. **Google Workspace** または **Okta** を選択し、チームのワークエメールドメインを入力してください。
2. Okta の場合、[OpenID Connect](https://developer.okta.com/docs/guides/implement-grant-type/authcode/main/) を使用して Web アプリケーションを作成します。発行元、クライアント ID、クライアントシークレットを入力してください。Glossia は標準の Okta 組織発行元と `/oauth2/default` 認証サーバーをサポートしています。シークレットは静的に暗号化されています。編集时にシークレットを空白のままにする場合、保存された値は維持されます。
3. Okta の場合、Glossia で表示されるリダイレクト先アドレスをアイデンティティプロバイダーに登録してください。Google Workspace の場合、Glossia が Google 接続を管理するため、Google アプリケーションの作成やコールバックアドレスの登録は不要です。
4. 設定を保存してください。ドメインプロバイダーから表示された DNS TXT レコードを追加し、**ドメインを検証** を選択します。エメールドメインの変更は新しい検証トークンを生成し、再検証まで組織へのサインインを無効にします。
5. チームメンバーはログインページでワークエメールを入力し、**組織から続ける** を選択してください。Google Workspace メンバーは **Google でログイン** も利用できます。

## Google Workspace のセットアップ

Glossia が Google アプリケーションの認証情報を管理します。Google Cloud で OAuth アプリを作成したり、Google Admin にカスタム SAML アプリを追加したり、リダイレクト先アドレスを登録する必要はありません。既存の Google Workspace ドメインでは、セットアップは Glossia およびドメインネームサーバープロバイダー（Google Workspace で必要ない場合があります）で行われます。

1. **設定 → 認証** で **Google Workspace** を選択し、ワークエメールドメインを入力し、**認証設定を保存** をクリックします。
2. 指定された DNS プロバイダーでドメインの DNS 設定を開きます。Glossia で表示される **ドメイン所有権の確認** に記載されたレコードを追加します。

   | 項目 | 値 |
   | --- | --- |
   | タイプ | `TXT` |
   | 名前 / ホスト | Glossia で表示される **Record name** など、例えば `_glossia-verification.example.com` |
   | 値 / コンテンツ | Glossia で表示される **Record value** で `glossia-domain-verification=` から始まる |

   一部の DNS プロバイダーはドメインを自動的に追加します。その場合、ドメインが二重に含まれないようにホストには `_glossia-verification` のみを入力してください。検証後、レコードを維持します。
3. Glossia に戻り、**ドメインを検証** を選択します。検証が失敗した場合は、名前と値を確認し、DNS 変更の伝播に時間が必要なため再試行の前に待機してください。
4. チームメンバーにログインページでワークエメールを入力してもらい、**組織から続ける** または **Google でログイン** を選択してお試しください。

Glossia は Google の検証済みメールアドレスと [ホストドメインの声明](https://developers.google.com/identity/openid-connect/openid-connect#an-id-tokens-payload) を確認します。同じメールアドレスのサフィックスを持つ個人 Google アカウントは資格がありません。

### Google がサインインをブロックした場合

通常、Google 側の設定は不要です。組織がサードパーティアプリケーションのアクセスを制限している場合、Google Workspace 管理者が Glossia を承認する必要がある場合があります。

1. 管理者アカウントで [Google 管理コンソール](https://admin.google.com/) にサインインします。
2. **セキュリティ → アクセスとデータコントロール → API コントロール → サードパーティ aplicação のアクセス管理** を選択します。
3. アプリのアクセスリストで Glossia を探してください。リストされていない場合は、アプリ名または OAuth クライアント ID で **新規アプリの設定** を使用して検索します。OAuth クライアント ID は Glossia の共有 Google 接続に属しており、新規作成が必要なものではありません。
4. 要求されたサインイン権限を確認し、組織ポリシーに従って関連ユーザーにアクセスを許可してください。Google の [Google Workspace データへのサードパーティおよび内部アプリのアクセスを制御](https://support.google.com/a/answer/7281227) ガイドでアクセスレベルと管理者要件を確認してください。
5. ポリシー変更が有効化されたら、ワークアカウントで再試行してください。

## 登録と権限の管理

検証済みのプロバイダーアイデンティティで正確に一致するワークエメールドメインの場合、自動的に組織に参加します。既存の Glossia アカウントで初めて Okta を接続する場合、組織サインインを開始する前に既存のメソッドでサインインしてください。これにより、Okta 管理者は他の Glossia アカウントを管理する権利がないように安全にプロバイダーをリンクします。他のプロバイダーを通じた公開登録は引き続き関心フォームを使用します。プロバイダーを無効にしても、既存のメンバーシップは削除されません。

新規メンバーは、アカウント、組織、プロジェクト、音声、用語集、ディスカッション、チケットに基本的な読み取りアクセス権がある状態を確認できます。追加のアクセス権は参加後に [メンバーの権限を管理](/docs/how-to/member-permissions) を参照してください。

## アクセスの保護

ドメイン所有権の検証は 30 日間有効で、毎日自動的にチェックされます。検証レコードを維持してください。もし消去された場合、最後の成功した検証の有効期限切れでサインインが停止します。レコードを復元し、認証設定から再度検証してください。プロバイダーの変更或は組織サインインの無効化は検証をクリアし、前プロバイダーの認証情報を削除します。未検証のクレームはドメインを予約しません。

既存のアカウントでは、まず既存のメソッドでサインインし、その後 `/auth/login` にアクセスしてワークエメールサインインを開始してください。Google は既存のプロバイダーサブジェクトで既に連携された Google アイデンティティも使用できます。メールアドレスの一致だけでも既存アカウントは接続されません。

メンバーを削除すると自動再登録がブロックされます。アクセスを復元するには、そのメンバーを明示的に追加するか招待し 복구する必要があります。

メンバー招待管理、アクセス権限、言語モデル編集、組織削除は管理者の責任です。これらの権限はメンバースコープチェックボックスを介して委任できません。認証設定、ドメイン検証、スコープ変更は監査イベントを生成します。
