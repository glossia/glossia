Glossia はプロジェクトごとに 1 つのオプニングな翻訳プルリクエストを保っていきます。新しいデフォルトブランチのコミットは、ソースコミットごとにプルリクエストを開くのではなく、そのブランチの続きとして動作します。前のものがマージまたはクローズされた後に新しいプルリクエストが作成されます。

公開とセッション置換は、データベース 後端 による プロジェクト ロックを共有しており、異なるアプリケーション リプロクアまたは分離された実行機を含む場合も同様です。もし実行機がプルリクエストを作成したがメタデータを保存できなかった場合、次の公開は別のもので作成する前に GitHub 上のオプニングな Glossia プルリクエストを回復します。オプニングなプルリクエストは、ソースと cunt とのブランチの競合またはソース履歴のリサイドによって放棄されることはありえず、セッションは失敗しますが、解決のために既存の公開を保持します。

## プッシュ制限

制限は固定されており、**プロジェクトごとの 1 時間あたり 4 回のプッシュ**、セッションおよびレプリカで共有されます。現在では設定できません。

プッシュは均等の間隔に配置され、固定の時間ブロックのバケットでカウントされません。ブランチの更新は少なくとも 15 分ごとに実行されます。次のインターバルは公開試行が終了するときに始まり、そのため遅いバッチの直後に速いバッチが続くことができません。ソース ブランチマージ、中間バッチ、リトライ、そして最終フラッシュはすべて同じ予算を共有します。不明確な失敗試行もスロットを消費します。これは、接続が失敗する前に GitHub が既にブランチを進めた可能性があるからです。予算は PostgreSQL に保存され、新しいセッションまたはプロセスの再起動でリセットされません。

## バッチ処理

実行は検証済みの変更ファイルを収集し、25 ファイルまたは 15 分後に公開を要求します。これらの閾値はプッシュ制限の回避を許さないでしょう。冷却期間の間、追加の完了ファイルは保留中のバッチに参加し、同じパスの反復変更は最後のコンテンツを保持します。

実行終了時、最終フラッシュは同じ予算を待機します。セッションはアクティブなまま残り、待機中はハートビートを送ります。定期的にキャンセルと許可の再確認を行い、休止中にデータベース トランザクションを開いたままにしません。
