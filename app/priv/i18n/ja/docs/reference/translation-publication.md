Glossia はプロジェクトごとに 1 つのオープンな翻訳プルリクエストを保持します。新しいデフォルトブランチコミットは、個別のソースコミットごとにプルリクエストを開くのではなく、そのブランチを継承します。前のものがマージまたはクローズされた後、新しいプルリクエストが作成されます。クローズされた公開は、同じソースコミットを再試行する場合も含めて、新しいブランチ名を取得します。拒否された出力は完了した作品として再利用されません。

ソース同期はアセスメント前の破棄可能なローカルチェックアウトで発生し、オープンブランチの完了翻訳とロックファイルを保持します。結果が出力またはロックファイルの変更を見つけないランは、デフォルトブランチとの追跡のために単にリモートブランチを進化させることも、公開スロットを消費することもありません。バッチが準備完了すると、ソース同期と検証済みの変更は、1 つの強制されないブランチ更新に一括して公開されます。そのコミットは、以前の公開と評価されたソースコミットを両方祖先として保持します。

公開とセッション置換は、データベースに基づくプロジェクトロックを共有し、アプリケーションレプリカまたは分離ランナーで実行される場合にも同様です。ランナーがプルリクエストを作成したがメタデータを保存できなかった場合、次の公開は別のものを 1 つ作成する前に GitHub からオープンな Glossia プルリクエストを回復します。オープンなプルリクエストは、そのブランチがソースと競合する場合やソース履歴が書き換えられた場合でも放棄されません。セッションは失敗し、解決のために既存の公開を残します。

## プッシュ制限

制限は **1 プロジェクトあたり 1 時間に 4 回のプッシュ** に固定され、セッションおよびレプリカ間で共有されます。現在では設定はできません。

プッシュは時間 バケットに数えられず、均等に間隔を置かれます。ブランチ更新は少なくとも 15 分以上隔てられます。次の間隔は公開試行完了を待って始まるため、遅いバッチの後にすぐに速いバッチが来ることがありません。中間バッチ、再試行、および最終フラッシュはすべて同じ予算を共有します。不明な失敗試行もスロットを消費します。これは、接続失敗の前に GitHub がブランチを進めた可能性があるためです。予算は PostgreSQL に保存され、新しいセッションまたはプロセス再起動によってリセットされません。

公開する前に、Glossia はリモートヘッドを再読み込みし、セッションのソースをローカルで再度マージします。これにより、以前のバッチは保護され、ブランチを動かさずに競合が検出されます。もし以前に更新は成功したもののレスポンスが失われた場合、すでに存在する変更は再度コミットされません。公開メタデータおよびプルリクエストは、別のブランチ更新なしで回復されます。もし参照が作成されたがランナーがプルリクエスト作成前に停止した場合、ノッチンジ検証は欠落したプルリクエストを作成しますが、ブランチ更新スロットを消費しません。

予期せぬリモートの更新は、その差が期待された同期ツリーの予期せぬ変更が待機中のバッチに含まれている 부분에のみ存在する場合のみ受け入れられます。検証中に生成された他の編集は上書きされたり、旧い入力を検証した翻訳が公開したりせず、公開が失敗します。既存のプルリクエストは解決のために保持されます。

## バッチ処理

ランは検証済みのファイル変更を収集し、25 ファイルまたは 15 分後に公開をリクエストします。これらの閾値はプッシュ制限バイパスしません。冷却中、追加の完了ファイルは待機中のバッチに追加され、同じパスへの重複変更は最新コンテンツを保持します。

ランが終了すると、最終フラッシュは同一予算を待機します。セッションは待機中もアクティブのまま残り、ハートビートを送信します。休止中はデータベース トランザクションを開きながら、定期的にキャンセルと許可の再確認を行います。
