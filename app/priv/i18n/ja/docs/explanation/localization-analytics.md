次の翻訳先言語の選択は賭けと言えます。それは時間と金銭のコストが必要であり、そのリターンは通常では見えない需要に依存します。 ローカライゼーション・アナリティクスは、その需要を可視化します。

## 「意思決定」であり、ダッシュボードではない。

ここで収集するアナリティクスの目的は狭く、意図的です。「言語 X にローカライズすべきか？」という問いを答えるためです。指標は、汎用的な分析スイートになるために選ばれたのではなく、その質問に答えるために選ばれたものです。

決定を動かすのは 3 つの要素です:

1. **需要。** ドレだけの訪問者がこの言語を望んでいますか？ ブラウザの設定言語と国は、関心がある場所を示します。
2. **ギャップ。** その需要は既に満たされていますか。 ユーザーの好む言語をプロジェクトのターゲット言語、ページの言語、および公開されている翻訳と比較し、壁にぶつかったトラフィックの割合が明らかになります。
3. **価値。** ローカライゼーションで成果を得ますか？ ロケールギャップによるエンゲージメント、未対応のトラフィックが到達するページ、そしてそのトラフィックの発生源は、新しいロケールが変換につながる可能性を示します。

## なぜギャップは読み込み時に計算されるのか

`served_locale` は実際のページ言語（`<html lang>` に宣言されたもの）を記録します。訪問者が受け取ったと推定する言語ではありません。`has_locale_gap` は、ブラウザの言語設定をプロジェクトのターゲット言語、ページの言語、および`hreflang` リンクで提供される翻訳と比較します。両者は訪問時にその通りであった形まま、イベントごとに保存されます。これは履歴データが当時の直面機会の反映であり、現在のターゲットに対する再計算ではありません。来月にポルトガル語を追加しても、先月のギャップは遡って縮小されません。どれだけ需要が供給されなかったかの正直な記録を保持します。

## 特にクッキーレスについて

「ユニークな訪問者」を求めたときの本能は Cookie を設定するか、ブラウザの指紋化することです。どちらも長期にわたる ID を生み出しますが、多くのプライバシー規制では指紋化の削除は Cookie よりも困難です。どちらもここでは必要ではありません。

1 日間のユニーク訪問者には、その ID が *1 日以内* の安定しているものだけで十分です。IP と User-Agent のハッシュを毎日回転させ、プロジェクトごとに範囲限定することで、日次訪問者数をサポートしつつ、日またはサイトを超えて訪問者を識別することを不可能にします。これは、長期の再訪トラッキングを提供しません。

この設計は、分析システムによって保持される識別子を制限します。特定のウェブサイトが同意を必要とするかどうかを確立するものではありません。サイトが分析をどのように利用するか、およびそれに適用されるルールによって異なります。
