Glossia はリポジトリの指示をモデルプロバイダーの認証情報から分離します。リポジトリは翻訳すべき内容を決め、アカウントは使用する [大規模言語モデル](https://en.wikipedia.org/wiki/Large_language_model) 作業を行います。

## なぜモデルはアカウントに属するのか

チームは同じプロバイダー連携のもとで、しばしば複数のリポジトリを翻訳します。アカウントスコープのモデルにより、管理者はすべてのリポジトリを編集せずに、一度にプロバイダーキーのローテーション、または基盤モデルの切り替えが可能になります。

この境界は認証情報をバージョン管理から除外します。リポジトリには読みやすいハンドル、例えば `translation-default`、プロバイダーキーではありません。

## ハンドルは安定した意図を提供します。

この `model` フィールド in `L10N.md` がアカウントモデルのハンドルを指します:

```yaml
model: translation-default
```

ハンドルはリポジトリの意図を表します。管理者は後で、リポジトリ構成が安定している間、そのハンドルが選択するプロバイダーモデルを変更できます.

## 複数のモデルがどのように使われるか

Glossia は各ドキュメントの翻訳に 1 つの設定済みモデルを使用します。複数のモデルを追加しても、アンサンブル、フォールバックチェーン、または自動品質ティアは作成されません。リポジトリの作成者は安定したハンドルを通じて目的を選択します。例えば、 `translation-default`再構成ドキュメント以前に検証に失敗しました：マークダウンテキスト文字列回復は一致する長さの JSON 文字列配列を返す必要があります。&#10;この供給されたセグメントのみを修正された翻訳で返してください。このセグメントに存在するすべての必要なトークンを保持してください。 `long-form`再構成された文書は以前検証に失敗しました：マークダウンテキストリテラルの復元は、一致する長さを持つ JSON 文字列配列を返す必要があります `japanese-specialist`.

選択はドキュメントおよび対象ロケールのコンテキスト階層に従います：

1. 最も近い `L10N/<locale>.md` ロケールを宣言するファイル `model` そのロケールで優先されます。
2. そうでなければ、最も近い `L10N.md` ロケールを宣言するファイル `model` そのディレクトリで優先されます。
3. 親 `L10N.md` より近いファイルがモデルを宣言していない場合、設定は継承されます。
4. 適用可能なコンテキストファイルがハンドルを宣言しない場合、Glossia はアカウントのデフォルトを使用します。

明示的に構成されたハンドルが存在する必要があります。Glossia は不明なハンドルについてはアカウントのデフォルトへ無音で切り替えるのではなく、エラーを報告します。

## デフォルトの選択

リポジトリが independen のモデルを持つ前に、プロジェクト設定はモデルを必要とします `L10N.md`. Glossia はしたがって、アカウントのデフォルトを選択します。アカウントに最初に追加されたモデルがデフォルトとなり、管理者は設定ページから別のモデルをデフォルトとして設定できます。

一旦リポジトリが `L10N.md`, 明示的なハンドルを使用することで、その選択がレビュアーに明確になります。省略は `model` リポジトリをアカウントのデフォルトのままで維持します。

## 人によるレビューの境界

モデル出力は提案された作業であり、自動マージではありません。セットアップおよび翻訳の活動は Glossia 内で表示され、リポジトリの変更はチームのレビューのためにプルリクエストとして公開されます。これにより、チームが既存のコードに使用している品質および所有権の境界が維持されます。
