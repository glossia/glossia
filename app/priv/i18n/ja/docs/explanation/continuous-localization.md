継続交付が機能するのは、小さな変更が反復可能なパイプラインを通過するからです：バージョン管理、レビュー、検証、そしてデプロイ。ローカライゼーションは、そのパイプラインに適合させるべきであり、無関係の記録システムを導入するのではなく。

## 切断されたループ

切断されたワークフローでは、製品変更がエクスポートをトリガーし、別のツールで作業が行われ、翻訳されたコンテンツは最終的に返ってきます。そのステップの間、ソースは再び変更されることがあります。チームはバージョンを整合させ、翻訳が古くなったか判断し、別のリリースを調整する必要があります。

問題はウェブエディターが本質的に誤っている点ではありません。問題は、独立して権威ある編集システムが、それらが含まれるコードとコンテンツ改修から言語の決定を分離できる点にあります。

## リポジトリループ

Glossia のリポジトリワークフローでは、ソースファイルとローカライゼーション設定を Git に保持します。接続されたリポジトリはコンテンツと目標言語を提供します。翻訳の変更はレビュー可能なリポジトリ変更として返されるため、チームは既存のプルリクエストおよび公開の慣習を適用できます。

一般的なループは以下の通りです:

1. チームは製品のソースコンテンツを変更します。
2. Glossia は翻訳または改善が必要なコンテンツを特定します。
3. 言語ガイダンスと用語は変換の文脈を提供します。
4. 検証は結果をチェックし、失敗は実行可能です。
5. レビューアーは公開パイプラインがそれらを配信する前に変更を確認します。

[漸進的改善](./progressive-refinement) はハッシュ化と検証がこのループにどう適合するかを説明します。[翻訳の回復](./translation-recovery) は、生成または検証が失敗した場合に何が起きるかを説明します。

## 継続的とはレビューなしを意味しません

継続的に配信可能な変更は、必ずしも自動的に承認された変更とは限りません。法的な文言、製品の約束、文化的配慮が必要な素材には専門家のレビューが必要な場合があります。そのレビューを配信ループに維持することで、チームは別々の公開権限を維持せずに適切なゲートを選択できます。

継続的なローカライゼーションは、コミットごとにリポジトリ全体を翻訳することを意味しません。変更されていないコンテンツは、同じ資源を繰り返し消費するべきではありません。

## 実用的な境界

Glossia は言語の文脈とローカライゼーションのメカニズムを提供します。リポジトリのチェックとデプロイメントのプロセスは、変更を安全に公開できるタイミングを定義し続けます。Glossia はアプリケーションテストの代替手段でも、編集者の正確性に関する責任の代わりでもありません。

他のプラットフォームも Git 連携と CI オートメーションを提供しています。区別は意図された重心にあります：Glossia はリポジトリ内のコンテンツ所有権とレビューを中心に構築されています。継続的な編集権限をホストされた翻訳ワークスペースに移すことを要求するものではありません。
