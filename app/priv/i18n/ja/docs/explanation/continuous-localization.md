継続的デリバリーが機能する理由は、小さな変更がバージョン管理、レビュー、検証、およびデプロイという反復可能なパイプラインを通過するためです。ローカライゼーションは、そのパイプラインに適合させ、独立したレコードシステムを導入する必要はありません。

## ## 非接続ループ

非接続ワークフローでは、製品の変更がエクスポートをトリガーし、別のツールで作業が行われ、翻訳済みのコンテンツが最終的に戻ります。それらのステップの間、ソースは再度変更される可能性があります。チームはバージョンの整合、翻訳が古くなったかの判断、および別のリリースの調整を行う必要があります。

問題点は、ウェブエディタが本質的に間違っていることではないということです。問題は、権限を有する独立した編集システムが、言語の決定を、それらが記述するコードやコンテンツの改修から分離できるということです。

## ## リポジトリ・ループ

Glossia のリポジトリワークフローは、ソースファイルとローカライゼーション設定を Git に保持します。接続されたリポジトリは、コンテンツとターゲット言語を供給します。翻訳の変更はレビュー可能なリポジトリ変更として戻され、チームは既存のプルリクエストと出版の慣習を適用できます。

典型的なループは以下の通りです:

1. チームは製品と並行してソースコンテンツを変更します。
2. Glossia は、翻訳または改善が必要なコンテンツを特定します。
3. 言語ガイダンスと用語は、変換のコンテキストを提供します。
4. 検証は結果を確認し、失敗は修正可能な状態に保たれます。
5. レビューヤーが公開パイプラインによってデリバリーされる前に変更を確認します。

[漸進的改善](./progressive-refinement) はハッシュ化と検証がこのループにどのように適合するかを説明します。[翻訳回復](./translation-recovery) は生成または検証が失敗した場合に何が起こるか説明します。

## ## 継続的とはレビューされていないことを意味するわけではありません

継続的に配送可能な変更は、必ずしも自動的に承認された変更を意味するわけではありません。法的な言語、製品の約束、および文化的感受性の高い資料には専門家のレビューが必要な場合があります。そのレビューを配信ループに保持することで、チームは独立した出版権限を維持せずに適切なゲートを選ぶことができます。

また、継続的ローカライゼーションはコミットごとにリポジトリ全体を翻訳することを意味するわけではありません。変更されていないコンテンツは、繰り返し同じリソースを使用すべきではありません。

## ## 実用的な境界

Glossia は言語コンテキストとローカライゼーションのメカニズムを提供します。リポジトリのチェックとデプロイメントプロセスが変更を安全に公開する時期を依然として定義しています。Glossia はアプリケーションテストやエディタの正確性の責任の代わりではありません。

他のプラットフォームも Git 統合と CI 自動化を提供します。区別の鍵は意図された重心にあり、Glossia はリポジトリ内のコンテンツ所有権とレビューを中核として構築されています。これは、継続的な編集権限をホストされた翻訳ワークスペースに移動することを必要とするものではありません。
