継続的配送は、小さな変更が反復可能なパイプライン（バージョン管理、レビュー、検証、そして展開）をとおして移動するからこそ機能します。ローカライゼーションは、そのパイプラインに適合させているべきであり、関連のない記録システムを導入していてはいけません。

## 断絶されたループ

断絶されたワークフローでは、製品の更新がエクスポートをトリガーし、作業は別のツールで行われ、翻訳されたコンテンツが結果的に戻るようになります。そのステップの間、ソースは再び変更される可能性があります。チームはバージョンを統合し、翻訳が古くなっているか判断し、別のリリースを調整する必要があります。

問題点は、ウェブエディターが本質的に間違っているためではないということです。それは、独立した権威ある編集システムが、コードとコンテンツの改訂を行なう言語決定をそれらから分離できるためです。

## リポジトリ・ループ

Glossia のリポジトリ・ワークフローは、ソースファイルとローカライゼーション設定を Git に保持します。接続されたリポジトリはコンテンツとターゲット言語を供給します。翻訳の変更はレビュー可能なリポジトリの変更として戻されるため、チームは既存のプルリクエストおよび公開の慣習を適用できます。

一般的なループは次の通りです:

1. チームは製品とともにソースコンテンツを変更します。
2. Glossia は翻訳または改善が必要なコンテンツを特定します。
3. 言語ガイダンスと用語は、その変換のコンテキストを提供します。
4. 検証は結果をチェックし、失敗は依然として対処可能なままです。
5. レビュアーは、公開パイプラインがそれらを配信する前に変更を検査します。

[漸進的改善](./progressive-refinement) はハッシングと検証がこのループにどのように適合するかを説明します。[翻訳回復](./translation-recovery) は生成または検証が失敗した場合に何が起きるかを説明します。

## 継続は未審査を意味しません

継続的に配送可能な変更は、必ずしも自動的に承認された変更とは限りません。法的文章、製品の約束、および文化的に敏感な素材には専門家のレビューが必要な場合があります。そのレビューを配送ループに保つことは、別々の発行権限を維持することなく、チームが適切なゲートを選択することを可能にします。

継続的なローカライゼーションは、すべてのコミットでリポジトリ全体を翻訳することを意味するものではありません。変更のないコンテンツは、同じリソースを繰り返し消費してはいけません。

## 実践的な境界

Glossia は言語コンテキストとローカライゼーションのメカニズムを供給します。リポジトリのチェックとデプロイメントプロセスは、変更が安全に公開されるタイミングを依然として定義します。Glossia はアプリケーションテストの代替品でも、編集者の精度に対する責任の代替品でもありません。

他のプラットフォームも Git 統合や CI 自動化を提供します。区別は意図された重心です：Glossia はコンテンツ所有権とリポジトリ内のレビューを中心に構築されており、進行中の編集権限をホスティングされた翻訳作業スペースに移動する必要があるものではありません。
