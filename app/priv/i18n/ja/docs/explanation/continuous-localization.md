継続的デリバリーは小さな変更がバージョン管理、レビュー、検証、デプロイという反復可能なパイプラインを通過するため機能します。ローカライゼーションは、そのパイプラインに適応すべきであり、関係のないレコードシステムを導入するのではなく。

## 切断されたループ

孤立したワークフローでは、製品の変更がエクスポートをトリガーし、別のツールで作業が行われ、翻訳内容が最終的に返されます。その間のステップで、ソースが再度変更される可能性があります。チームはバージョンを整合させ、翻訳が陳腐化しているかどうかを判断し、別のリリースを調整する必要があります。

問題点は、ウェブエディターが本質的に間違っていることではありません。問題は、独立して権威ある編集システムが、それら記述するコードとコンテンツ改定から言語の決定を分離できるという点です。

## リポジトリループ

Glossia のリポジトリワークフローでは、ソースファイルとローカライゼーション設定を Git に保持します。接続されたリポジトリはコンテンツとターゲット言語を供給します。翻訳変更はレビュー可能なリポジトリ変更として返されるため、チームは既存のプルリクエストおよび公開の慣習を適用できます。

典型的なループは以下の通りです：

1. チームは製品と共にソースコンテンツを変更します。
2. Glossia は翻訳または洗練が必要なコンテンツを特定します。
3. 言語ガイダンスと用語は、変換の文脈を提供します。
4. 検証は結果を確認し、失敗箇所は引き続き対処可能です。
5. レビューアーは、公開パイプラインがそれらを配信する前に変更を確認します。

[漸進的な洗練](./progressive-refinement) は、ハッシュと検証がこのループにどのように適合するかを説明します。[翻訳回復](./translation-recovery) は、生成または検証が失敗した場合に何が起きるかを説明します。

## 継続的とは未確認を意味しません

継続的デリバリー可能な変更とは、必ずしも自動的に承認された変更を意味するわけではありません。法的な言語、製品の約束、文化的に敏感な素材は専門家のレビューを必要とする場合があります。そのレビューを配信ループ内に維持することで、別途出版権限を管理することなく、チームは適切なゲートを選択できます。

また、継続的ローカライゼーションは各コミットでリポジトリ全体を翻訳することを意味するわけではありません。変更されていないコンテンツは同じリソースを繰り返し消費してはなりません。

## 実用的な境界

Glossia は言語コンテキストとローカライゼーションのメカニズムを提供します。リポジトリのチェックおよびデプロイプロセスは、変更が安全に公開されるタイミングを依然として定義します。Glossia はアプリケーションテストや、編集者の正確性への責任の代わりにはなりません。

他のプラットフォームも Git インテグレーションと CI 自動化を提供しています。区別のポイントは意図された重心です：Glossia はリポジトリ内でのコンテンツ所有権とレビューを中心に構築されており、継続的な編集権限をホストされた翻訳ワークスペースに移動させることを必要とするものではありません。
