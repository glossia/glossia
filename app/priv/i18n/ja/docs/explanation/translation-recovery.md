Glossia は公開前に翻訳されたコンテンツを検証します。リカバリーはその要件を維持します：再試行は依然としてソース構造と必要なプレースホルダーを保持し、すべてのアセンブル済みファイルは設定された検証コマンドを通過します。

## Markdown 翻訳

Glossia は翻訳された Markdown ドキュメントを再レンダリングしません。ソースはテキストのみを見つけるためにのみ解析されます：段落、目次、リスト項目、テーブルセル、コンポーネントおよび HTML(`title`, `details`, `alt`, `label`, `description`, `summary`, `placeholder`, `aria-label`, `caption`) の読者向け属性、および HTML `<summary>` のテキスト。各翻訳はソース占拠の正確なバイトにもう一度書き戻されます。コード、リンク先、コンポーネント、GitHub アラート、明示的な見出しアンカー `{#install}`、リストマーカー、および空行はバイト単位のままで相同します。

各段落または見出しは完全な文として翻訳されます。インラインフォーマットは番号付きタグに変わります：リンクまたは強調された単語 `<gN>...</gN>` の周りと、変えることができないコンテンツ `<gN/>`、例えばインラインコードやコンポーネント。モデルは 、ターゲット言語の単語順に従うためにタグを移動させることができますが、すべてのタグを正確に 1 回ずつ保持する必要があります。すべてのリクエストも周囲のソースドキュメント、および同じファイルからの最新の翻訳を、参照のために持っています。

タグを欠落または発明するユニットは、原因と共に、独自に再び送られます。最大 3 回。有効なユニットは保持されます。組み立て後、Glossia は結果を解析し、その構造をソースと比較します。単独で見出し、リスト、または強調に転換される翻訳は、プローツをエスケープします、これにはさらなるモデル呼び出しは不要です

## カタログ翻訳

Gettext コーテロは翻訳前に文字列として解析されます。リクエストは最大で 8 つの文字列を持ち、8,000 バイトのバッチ化ターゲットがあります。単一のより大きな文字列はそのまま残ります。モデルは同じ順序の同じ数の文字列を持つ配列を返します。Glossia はインターポレーション変数を確認し、空の翻訳を却下します。

ヘッダーはターゲットローカルの複数形ルールを使用してコードで構築されます。ソースメッセージ識別子、コメント、およびカタログ構造は解析されたソースからきます。バッチが不正確なコンテンツを返す場合、Glossia は一度リトライし、その後それをより小さなバッチに分割します。成功した隣接バッチは改めて翻訳する必要はありません。

## プロバイダー スロットリング

Glossia は同じ認証情報とモデルを使用する翻訳リクエストを調整します。レート制限 レスポンスは共有クールタイムを延長し、新しいリクエスト間の間隔を増加させてます。成功したトラフィックは 1 分後にスロットリングなしでその間隔を徐々に低下させます。現在実行中のリクエストは完了することを許可されます。

プロバイダー リトライ ヒントは最小の遅延です。繰り返す失敗はバックオフも増加させ、最大で 30 秒のベース遅延にジッター。より長いプロバイダー ヒントは優先され、最大 5 分未満。Together の `x-ratelimit-reset` ヘッダーは `retry-after` とともに認識されます。

変更のミス、リクエスト tesi 試行後、リポジトリ実行は新しいファイル開始を停止します。遅延継続は翻訳ブランチを継承し、未完了の仕事を再開します。前の試行はセッション履歴に残り、継続によってリンクされます。遅延は 1 分から 5 分まで増加し、最大 6 回の自動継続。新しいアクティブセッションが優先され、キャンセルセッションは再開されません。検証失敗のみはプロバイダー回復はスケジュールしません。

## エンジン リリース後の回復

セッションには 2 つの独立したバージョンがあります：翻訳されているリポジトリコミットと、それを発生す翻訳エンジン画像。Kubernetes では、各ジョブは実行した Web レプレスの正確なイメージディジェストをピン留めします。ジョブは Web ロールアウトを生き残り、翻訳の半道でコードを切り替えることは決してありません。実行は接続が完了した直前に、Web アプリケーションの更新後でも、前にエンジンですます可能性があります。セッション詳細はエンジンディジェストを表示し、このプレブンネーのない古いセッションは "Not recorded." を表示します。

5 分ごとに、Glossia はそのデプロイメントが完全にロールアウトされたかどうかを確認します。唯一のワーカーから healthy release からのみ、エンジニアリカバリースケジュールできます。プロジェクトの最期のセッションは、そのロールアウトが完了する前にキューイングされ、より古い記録されたエンジンディジェストで実行され、その後 6 時間以内に失敗した場合は、Glossia は現在のリリースで継続を作成できます。キュー時間を使用するのは容量を待機しているジョブをロールアウト後にブートのみをカバーします。別のイメージディジェットは、無関係のデプロイメント後の通常の失敗のリトライのトリガーされません。完了ファイルとオープン翻訳プルリクエストは携わります；未完了の仕事のみが再翻訳されます。キューされるリリース継続はロールアウト中のachievement 15 分钟待機。Kubernetes API または権限の失敗はクエリーサービスのエラー止と、進行中のロールアウトと誤認されません。

回復は意図的に狭く：セッションは最終的に記録されたアイテム検証エラーで終了し、最新の試行のすべての失敗アイテムは Markdown 構造、保持されたコンテンツ、または Markdown ユニットエラーをレポートする必要があります。中断または部分的にキャンセルされた試行は資格に含むものではありません。プロバイダーエラー、使い切りされたクレジット、却下された認証情報、出版失敗、ソース読み取りエラー、外部検証コマンド失敗、および不明瞭な原因はデプロイによって再試行されません。成功、アクティブ、キャンセル、置換、および非バージョン化セッションも放置されます。新しいセッションは常に優先され、ユーザーがキャンセルしても。

セッションは異なるエンジンのリリースで最大 1 回の継続を受け、系譜に最大 3 回のリリース継続があります。新しいエンジンが依然として失敗する場合、同じイメージ上では再試行されません、ロールバックを含む。系譜は以前試見たエンジンディジェストを保持し、ランチャーはキューイングされたジョブを作成する前にそれらを再チェックします。既存のプロバイダー回復制限はリリース継続で保存されます。変更可能なイメージタグと設定済みのリリース ID に欠けるデプロイメントは自動的なエンジン回復を有効にしません。

## 耐久の進捗

完了したファイルとそのロックファイルは、バッチとして翻訳ブランチに公開されます：25 ファイルごともしくは 15 分ごとに 1 つのコミット、そして実行が終了した時には最終コミット。各プッシュはリポジトリのプルリクエストチェックを実行するため、バッチ化により大規模な実行がファイル 1 つあたり 1 つのチェック実行を開始しないようにします。プロジェクトには単一の翻訳プルリクエストがあり、デフォルトブランチの新しいコミットは開かれているものを続行し、以来変更されたもののみ翻訳します。そのプルリクエストがマージまたは閉じられると、次の実行は新しいものから開始されます。未完ファイル内では、ローカル検証されたセグメントと回復バッチもデータベースに 7 日間保存されます。これらのチェックポイントはワーカープロセスの停止後も残存します。それらはアカウント、プロジェクト、ドキュメント入力、有効な認証情報とモデル、コンテキスト、およびセグメントまたは修復試行にスコープ設定されます。

再開された実行は、入力がまだ一致するときにのみセグメントを再使用できます。最終組み立てドキュメントは常に再検証されます。却下されたモデル応答はチェックポイントではありません。ドキュメントレベルの検証失敗は、検証器が単一の責任セグメントを特定できない可能性があるため、別々の修復試行を開始します。

期限切れのチェックポイントと非アクティブなプロバイダーペースレコードは、スケジュールされたセッション回復ワーカーによって削除されます。それらは運用レコードであり、ユーザーはそれらをリポジトリに追加する必要も、`L10N.md` に設定する必要もありません。
