Glossia は公開前に翻訳済みのコンテンツを検証します。リカバリーはその要件を維持します：再試行は依然としてソース構造と必要なプレースホルダーを保持し、組み立てられた各ファイルは構成された検証コマンドに合格する必要があります。

## Markdown 翻訳

Glossia は翻訳済みの Markdown ドキュメントを再レンダリングしません。プロース：パラグラフ、見出し、リスト項目、テーブルセル、コンポーネントと HTML のユーザー向けの属性 (`title`, `details`, `alt`, `label`, `description`, `summary`, `placeholder`, `aria-label`, `caption`)、および HTML の `<summary>` の 텍스트 を探すためにソースを解析するだけです。各翻訳はソースが占めていた正確なバイトに書き込まれるため、コード、リンク宛先、コンポーネント、GitHub アラート、明示的な見出しアンカー（`{#install}`）、リストマーカー、および空白行はバイト単位の完全一致を保ちます。

各パラグラフまたは見出しは全体として一つの文で翻訳されます。インラインフォーマットは番号付きタグになります：リンク済みの単語または強調された単語の周りに `<gN>...</gN>`、 Inline コードやコンポーネントなどの変えてはならないコンテンツには `<gN/>` を使用します。モデルはターゲット言語の語順に従ってタグを移動できても、各タグは正確に一度だけ保持する必要があります。各リクエストも surrounding ソースドキュメントと同一ファイルからの最も新しい翻訳を参照として持ちます。

タグを落として発明するユニットは、理由とともに最大 3 回単独で再送されます。有効に戻ってきたユニットは保持されます。スパイシング後に Glossia は結果を解析し、ソースとの構造を比較します。独立して見出し、リスト、または強調になる翻訳はプロースがエスケープされ、追加のモデル呼出が必要ありません。

## カタログの翻訳

Gettext カタログは翻訳前に文字列に解析されます。リクエストは最大 8 つの文字列を持ち、8,000 バイトのバッチング目標があります。単一の大きな文字列はそのままになります。モデルは同じ数の文字列を同じ順序で配列として返します。Glossia はインターポーレーション変数をチェックし、空の翻訳を拒否します。

見出しはターゲットロケールの複数形式ルールを使用してコードで構築されます。ソースメッセージ ID、コメント、およびカタログ構造は解析されたソースから取得されます。バッチが不正なコンテンツを返した場合は、Glossia は一度再試行した後、より小さなバッチに分割します。成功した隣接するバッチは再度翻訳する必要はありません。

## プロバイダーのスロットリング

Glossia は同じ資格情報とモデルを使用する転送リクエストを調整します。レート制限応答は共有のクールダウンを延長し、新しいリクエスト間の間隔を増加させます。スロットリングなしで成功したトラフィックは 1 分後に徐々にその間隔を減少させます。既に実行中のリクエストは完了を許可されます。

プロバイダーの再試行ヒントは最小の遅延です。繰り返された失敗もバックオフを増加させ、最大 30 秒の基本遅延 plus jitter がありますが、長いプロバイダーヒントは優先され、5 分で上限になります。Together の `x-ratelimit-reset` ヘッダーは `retry-after` と同時に認識されます。

8 回の unsuccessful リクエスト試行後、レポジトリ実行は新しいファイルの開始を停止します。遅延される続行は翻訳ブランチを継承し、未完成の仕事を再開します。前の試行は続行を通じてセッション履歴に表示され、引き続き表示されます。遅延は 1 分から 5 分まで増加し、最大 6 回の自動的な続行があります。新しいアクティブなセッションは優先され、キャンセルされたセッションは jamais revival です。検証失敗のみでプロバイダーの回復をスケジュールしません。

## エンジンリリース後の回復

セッションには 2 つの独立したバージョンがあります：翻訳されているレポジトリコミットとこれを実行する翻訳エンジンイメージ。Kubernetes では、各ジョブはそのスケジュールした Web リプリカかの正確なイメージダイジェストをピン留めします。ジョブは Web ロールアウトを生き残り、翻訳の途中で決してコードを半期に切り替えることはありません。ロールアウトの直前にスケジュールされたジョブは、Web アプリケーションが更新されても前のエンジンで完成することができます。セッション詳細にはエンジンダイジェストが表示され、このプロシエンスがない古いセッションは「Not recorded」を表示します。

5 分ごとに、Glossia はそのDeployment が完全なロールアウトに達したかどうかをチェックします。その健全なリリースからのワーカーのみがエンジン回復をスケジュールできます。プロジェクトの最新セッションがそのロールアウト完了前にキューに入れられ、古い記録されたエンジンダイジェストで実行され、その後数時間以内に失敗した場合、Glossia は現在のリリースで続けることができます。キュー時間を使用してカバーされるのは、キャパシティを待ってロールアウト後に Boot するジョブです。異なるイメージダイジェスト単体は関係ない Deployment 後に通常の失敗の再試行をトリガーしません。完了したファイルと開かれた翻訳プルリクエストは引き継がれ、未完成の作業のみが再度翻訳されます。キューされたリリース继续はロールアウトが進行中の間待機し、最大 15 分。Kubernetes API または権限失敗は、進行中のロールアウトと誤解されるのではなく、明確なエラーで起動を停止します。

回復约而同的なに制限されています：セッションは記録されたアイテム検証失敗で終了している必要があり、最新の試行中の各失敗したアイテムは Markdown 構造、保存中コンテンツ、または Markdown ユニット失敗を報告する必要があります。中断または部分的にキャンセルされた試行は対象外です。プロバイダーエラー、消耗したクレジット、拒否された資格情報、公開失敗、ソース読み取りエラー、外部検証コマンド失敗、および不明瞭な原因はDeployment で再試行されません。成功、アクティブ、キャンセル、代替、およびバージョン付きセッションも一般的な扱いではありません。新しいセッションは常に優先されます、ユーザーがキャンセルした場合でも。

セッションは異なるエンジンリリースで最大 1 回の続行を受け、 lineage は最大 3 つのリリース继续を取得します。新しいエンジンが依然として失敗しても、同じイメージで再試行されません、ロールバック後を含めて。Lineage は以前に試行されたエンジンダイジェストを保持し、ランチャーはキューされたジョブを作成する前にそれらを 다시チェックします。既存のプロバイダー回復制限はリリース继续を通じて維持されます。可変イメージタグとリリースアイデンティティが構成されていないDeployment は自動的エンジン回復を有効にしません。

## 耐久的な進捗

公開済みファイルとそのロックファイルはバッチで翻訳ブランチに公開されます：25 ファイルごとに 1 ツのコミット、または 15 分ごとに、実行終了時には最終コミット。各プッシュはリポジトリのプルリクエストチェックを実行するため、バッチ化により大規模な実行が各ファイルごとにチェック実行を開始しないようにします。プロジェクトには単一の翻訳プルリクエストがあり、デフォルトブランチの新しいコミットは開いているものを継続し、以降の変更のみ翻訳されます。そのプルリクエストがマージまたはクローズされると、次の実行は新しいものを開始します。未完了のファイル内には、ローカル検証セグメントと回復バッチも 7 日間データベースに保存されます。これらのチェックポイントはワーカープロセスの停止でも存続します。これらのは、アカウント、プロジェクト、ドキュメント入力、有効な資格情報とモデル、コンテキスト、およびセグメントまたは修理試行に基づいたスコープを持ちます。

再開した実行は入力値が一致している場合のみセグメントを再利用できます。最終組み立てドキュメントは常に再度検証されます。拒否されたモデル応答はチェックポイントではありません。ドキュメントレベルの検証失敗は、検証器が単一の責任セグメントを特定できない可能性があるため、別の修理試行を開始します。

期限切れのチェックポイントと非アクティブなプロバイダーペース調整記録は、スケジュールされたセッション回復ワーカーによって削除されます。これらは運用記録であり、ユーザーはこれらをリポジトリに追加したり、`L10N.md` に設定する必要はありません。
