企業がすでに作成したコンテンツやそのコンテンツを配信する能力を失うことなく、言語ツールを変更できるようにすべきです。

## 所有権はエクスポートボタン以上のものです

翻訳されたファイルをエクスポートすることは有用ですが、持ち運びやすさはレビュー履歴、言語ガイダンス用語集、そして作業を続けるために必要な構成も含まれます。それらが単一の専用ワークスペースの中だけであれば、会社は出力を保持しながら、それを生み出プロセスを失う可能性があります。

Glossia のリポジトリワークフローでは、公開されたソースと翻訳されたファイルを Git に保持します。プルリクエストの履歴はリポジトリに残り、ファイルベースの構成はブラウザの編集セッションとは独立して変換を記述します。

## 言語決定は再利用可能であるべきです

ベイスと用語集ガイダンスは組織の意図を捕捉します。Glossia はそれらのコンテキストを人間と統合プロジェクトに提供します、これには MCP を通じてエージェントも含まれます。これは以前に翻訳されたセグメントを検索するといった再利用とは異なる種類の再利用です: メモリに一致する文がない場合でも、新しいコンテンツをガイドすることができます。

これはセグメントベースの翻訳メモリを廃墟にするものではありません。チームは価値のあるレビューされた翻訳と、専門的なワークフローを保持したい場合があります。Glossia の姿勢は、そのようなリソースは compan の配信プロセスを補完するであり、それを管理する専用権限になるべきではありません。

## 公開ソースは利点がありますが、魔法的な exit プランではありません

実装を検証し変更できるようにすることは、チームが彼らのコンテンツがどのように処理されるかを理解するのを助けます。これはすべての運用依存関係が消失することを意味しません。公開された Glossia インスタンスは依然としてデータベース、関連ワークフローのためのモデルプロバイダーへのアクセス、認証情報、インフラストラクチャが必要です。ダッシュボードで管理された言語コンテクストも、チームがシステムを変更する場合は明示的な移行計画が必要です。

現在の O'Saasy ライセンスは競合するホストサービスを変動します。公開ソースの可用性とは不制限のオープンソースライセンスや、代替サービスがどのようなビジネスモデルの下で運用されるかを保証するのとは異なります。リポジトリの [license](https://github.com/glossia/glossia/blob/main/LICENSE.md) を参照してください。

## 使い道の持ち運びテスト

言語サービスが利用できない場合でも、チームは依然として既存の翻訳コンテンツを検証しレビューし、公開できるかを問いかけます。リポジトリ所有の出力では、最新のファイルを取り出すために専用のエディターを再度開くことなく公開できます。

次に、言語ガイダンス、認証情報、オートメーションが別のシステムに移るかどうかを問いかけます。それらは別々の質問であり、それらを明示的に保つことは「ロックインなし」を約束することよりも有用です。
