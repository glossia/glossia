製品は、翻訳が別のリリースサイクルに停滞したままでも継続的に出荷されることができます。ソースコンテンツは Git で変更され、誰かがそれを翻訳システムにエクスポートし、編集者がそこで作業し、誰かが結果をインポートします。製品とその言語バージョンは互いに離れていきます。

Glossia は、別の前提に基づいて構築された言語 OS です。言語作業は、製品そのものと同じようなバージョン管理可能で見直しが可能な配送サイクルに従うべきです。

## 問題の範囲は翻訳を超えています

チームは意味を保持し、用語を適用し、視聴者のトーンに合わせてコンテンツを調整し、製品が進化するに伴って更新する必要があります。これらの決定は、ドキュメント、UI ストリング、マーケティングページ、エージェント生成のテキストなどにも影響します。

モデルは有用な草案を生成できます。しかし、単独では、あなたの組織の言語決定を知り、フレーズが変更された理由を記録することも、ファイルフォーマットを検証することも、次のソースリビジョンを同期することもできません。プロンプトを繰り返すことは、配送システムではありません。

Glossia は言語コンテキストと生成メカニズムを組み合わせます：設定、変更検出、検証、障害回復、リビジョン履歴、レビューなど。

## コンテンツは製品と一緒になります

リポジトリは公開コンテンツにおける権威です。ソースファイル、設定、生成された翻訳、レビュー可能な変更は Git とプルリクエストを通じて移動できます。チームは、ローカライズされたリリースをデリバリーする前に、ホスティングされた編集インターフェイスをすべての文の権威にする必要はありません。

これにより、それらを引き起こした製品変更と並んで言語変更が見えます。レビュアーは差分を確認でき、CI は出力を検証し、同じ配送パイプラインで公開できます。

配信モデルについては [継続的なローカリゼーション](./continuous-localization) を、ポータビリティの影響については [コンテンツの所有権](./content-ownership) を参照してください。

## コンテキストは入力であり、枷ではありません

トーンガイドと用語は、人間とエージェントの両方が一貫して執筆するのを助けます。それらは単なるソース・ターゲットのセグメント対の固有コレクションではなく、再利用可能な言語決定です。

翻訳メモリは、確立された翻訳や反復的なコンテンツにおいても引き続き有用です。それを捨てることではありません。会社の言語知識が住みつくことができる場所を、単一のベンダーのメモリ形式や編集ワークフローに限定しないことです。

## 改善はループです

Glossia の段階的改善モデルは、冗長な作業を避けるためにコンテンツハッシュを使用し、トランスフォーマーション周りの検証を実行し、実行が回復できるように障害を公開します。人間の訂正は孤立した生成に消えるのではなく、次の反復に反映されます。

ロカリゼーション分析は別の入力を提供します：オーディエンスが使用する言語と場所を理解することは、チームが投資先を決定するのに役立ちます。それは優先順位付けの証拠であり、翻訳が成長をもたらすという約束ではありません。

## この対象となるチーム

Glossia は、開発者、言語専門家、プロダクトチームがリポジトリ管理のコンテンツを共同で作業し、継続的にリリースしたい場合に特に役立ちます。すべての組織が既存の TMS を放棄すべきだという主張ではありません。成熟したブラウザベースのエディタや翻訳仲介の調整、または大規模な確立されたメモリを中央要件とするチームは、別のワークフローを好む可能性があります。

## 検査可能な実装

Glossia のコードは公開されており、Phoenix アプリケーション、Rust CLI、Web SDK、デプロイインフラを含みます。言語作業のメカニズムはブラックボックスではなく、検査可能になります。
