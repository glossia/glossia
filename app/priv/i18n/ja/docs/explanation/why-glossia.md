製品は継続的にリリースされる一方で、その翻訳は別のリリースサイクルで停滞することがあります。ソースコンテンツが Git 内で変更され、誰かがそれを翻訳システムにエクスポートし、編集者がそこで作業を行い、誰かが結果をインポートします。製品とその言語バージョンは次第に乖離していきます。

Glossia は、言語作業が製品自体と同じようにバージョン管理され、レビュー可能なデリバリーサイクルに従うべきだ、という異なる前提に基づいた言語 OS です。

## 問題は翻訳だけではありません

チームは、意味を保全し、用語を適用し、視聴者のトーンに合わせ、製品が進化するにつれてコンテンツを更新する必要があります。それらの決定はドキュメント、UI スリング、マーケティングページ、エージェント生成のライティングにも影響します。

モデルは有用なドラフトを生み出せます。しかし、それ単独では、あなたの組織の言語決定を理解し、フレーズが変更された理由を記録し、ファイル形式を検証し、次回のソースリビジョンを同期することはできません。プロンプトを繰り返すことはデリバリースイステムではありません。

Glossia は、設定、変更検知、検証、失敗回復、リビジョン履歴、レビューといった生成周辺のメカニクスと、言語コンテキストを組み合わせます。

## コンテンツは製品と共に存在します

リポジトリは公開されたコンテンツの権威となります。ソースファイル、構成、生成された翻訳、およびレビュー可能な変更は Git とプルリクエストを介して移動できます。チームは、ローカライズリリースを配信する前に、ホスティングされた編集インターフェースをすべての文章の権威とすることはいりません。

これにより、言語の変更点は、それらを動機化した製品の変更点と並んで可視化されます。レビュワーは差分を確認でき、CI は出力を検証でき、同じ配信パイプラインがそれを公開できます。

デリバリーモデルについては [継続的ローカライゼーション](./continuous-localization)、ポータビリティの影響については [コンテンツ所有権](./content-ownership) をご覧ください。

## コンテキストは入力であり、檻ではありません

音声ガイダンスと用語は、人間とエージェントの両方が一貫して書くのを助けます。それらは再利用可能な言語決定であり、単なるソースとターゲットのセグメントペアの所有権コレクションではありません。

翻訳メモリーは確立された翻訳と反復コンテンツにとって依然として有益です。それらを破棄するわけではありません。企業の言語知識が唯一の場所に生きるのを、特定のベンダーのメモリー形式や編集ワークフローに置くこととすることを避けるためのポイントです。

[言語メモリーと翻訳メモリー](./language-memory-and-translation-memory) をご覧ください。

## 改善にはループが必要です

Glossia の進化的な洗練モデルは、内容ハッシュを使って無駄な作業を避け、変換周りに検証を実行し、失敗が露見するようになっています。これにより再実行が回復できます。人間の訂正は孤立した生成に消えるのではなく、次の反復に情報を提供します。

ロカライゼーション分析は別の入力を提供します：オーディエンスが使用する言語と場所を理解することは、チームが投資先を決定するのに役立ちます。これは翻訳が成長を生むという約束ではなく、優先付けのための証拠です。

## この手的な対象は誰か

開発者、言語学者、および製品チームがリポジトリ管理されたコンテンツで協力し、継続的にリリースしたい場合、Glossia は特に重要です。すべての組織が既存の TMS を放棄すべきであると主張しているわけではありません。中央要件が成熟したブラウザベースのエディター、翻訳エージェントとの調整、または大規模な確立されたメモリーであるチームは、別のワークフローを好むかもしれません。

[Crowdin](./glossia-vs-crowdin)、[Lokalise](./glossia-vs-lokalise)、[Phrase](./glossia-vs-phrase)、および [Weblate](./glossia-vs-weblate) の比較はこれらのトレードオフを説明します。

## 確認可能な実装

Glossia のコードは公共で利用可能です。Phoenix アプリケーション、Rust CLI、Web SDK、およびインフラストラクチャが含まれます。これにより、言語作業の実行メカニズムは確認可能となり、ブラックボックスではなくなります。
