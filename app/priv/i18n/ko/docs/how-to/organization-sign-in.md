## 인증 제공업체 연결

조직 관리자는 **설정 → 인증** 에서 작업 인증 제공업체를 연결할 수 있습니다.

1. **Google Workspace** 또는 **Okta** 를 선택하고 팀의 작업 이메일 도메인을 입력하세요.
2. Okta 의 경우 [OpenID Connect](https://developer.okta.com/docs/guides/implement-grant-type/authcode/main/) 를 사용하여 웹 애플리케이션을 생성하세요. 해당 발행자, 클라이언트 식별자 및 클라이언트 기밀을 입력하세요. Glossia 는 표준 Okta 조직 발행자와 `/oauth2/default` 인증 서버를 지원합니다. 기밀은 정지 상태에서 암호화됩니다. 편집 시 기밀을 비워두면 저장된 값이 유지됩니다.
3. Okta 의 경우 Glossia 에 표시된 리디렉션 주소를 인증 제공업체와 연결하세요. Google Workspace 의 경우 Glossia 가 Google 연결을 관리하므로 Google 애플리케이션을 생성하거나 콜백 주소를 등록할 필요가 없습니다.
4. 설정을 저장하세요. 도메인 제공업체를 통해 표시된 DNS TXT 기록을 추가한 다음 **도메인 확인** 을 선택하세요. 이메일 도메인을 변경하면 새 인증 토큰이 생성되며 재확인될 때까지 조직 로그인 기능이 비활성화됩니다.
5. 팀원들은 로그인 페이지에서 작업 이메일을 입력하고 **조직으로 계속** 을 선택하세요. Google Workspace 관리자는 또한 **Google 로 로그인** 을 사용할 수 있습니다.

## Google Workspace 설정

Glossia 는 Google 애플리케이션 자격 증명을 관리합니다. Google Cloud 에서 OAuth 애플리케이션을 생성하거나 Google Admin 에서 사용자 지정 SAML 애플리케이션을 추가하거나 리디렉션 주소를 등록할 필요가 없습니다. 이미 있는 Google Workspace 도메인의 경우 설정은 Glossia 와 DNS 제공업체에서 수행됩니다:

1. **설정 → 인증** 에서 **Google Workspace** 를 선택하고 작업 이메일 도메인을 입력한 후 **인증 설정 저장** 을 선택하세요.
2. Google Workspace 가 아닌 DNS 를 호스팅하는 제공업체의 도메인 DNS 설정을 엽니다. **도메인 소유권 확인** 에 표시된 기록을 추가합니다:

   | 필드 | 값 |
   | --- | --- |
   | 유형 | `TXT` |
   | 이름 / 호스트 | Glossia 에 표시된 **기록 이름**, 예를 들어 `_glossia-verification.example.com` |
   | 값 / 콘텐츠 | Glossia 에 표시된 **기록 값**, `glossia-domain-verification=` 로 시작합니다. |

   일부 DNS 제공업체는 도메인을 자동으로 추가합니다. 이 경우 도메인이 두 번 포함되지 않도록 호스트에 `_glossia-verification` 만 입력하세요. 확인 후에도 기록을 유지해 주세요.
3. Glossia 로 돌아가서 **도메인 확인** 을 선택합니다. 확인이 실패하면 이름과 값을 확인하고 DNS 변경 사항 전파 시간을 허용한 후 다시 시도하세요.
4. 팀원들에게 로그인 페이지에서 작업 이메일을 입력하여 **조직으로 계속** 을 선택하도록 하거나 **Google 로 로그인** 를 사용하세요.

Glossia 는 Google 의 확인된 이메일과 [호스트 도메인 주장](https://developers.google.com/identity/openid-connect/openid-connect#an-id-tokens-payload) 을 확인합니다. 동일한 이메일 접미사를 가진 개인 Google 계정엔 자격이 없습니다.

### Google 로그인이 차단된 경우

보통 Google 측 설정은 필요하지 않습니다. 조직이 제 3 측 애플리케이션 액세스를 제한할 경우 Google Workspace 관리자도 Glossia 를 승인해야 할 수 있습니다:

1. 관리자 계정으로 [Google Admin 콘솔](https://admin.google.com/) 에 로그인하세요.
2. **보안 → 액세스 및 데이터 제어 → API 제어 → 3 차 애플리케이션 액세스 관리**
3. 액세스된 앱 목록에서 Glossia 를 찾습니다. 표시되지 않은 경우 앱 이름 또는 OAuth 클라이언트 ID 로 검색하려면 **새로운 앱 구성** 을 사용하세요. OAuth 클라이언트 ID 는 Glossia 의 공유 Google 연결에 속하며, 생성해야 하는 애플리케이션에는 해당하지 않습니다.
4. 요청된 로그인 권한을 검토하고 조직 정책에 따라 관련 사용자에게 액세스 권한을 허용합니다. 액세스 수준 및 관리자 요구 사항은 Google 의 [제 3 측 및 내부 앱의 Google Workspace 데이터 액세스 제어](https://support.google.com/a/answer/7281227) 가이드를 참조하세요.
5. 정책이 적용된 후 작업 계정으로 로그인 재시도하세요.

## 입학 및 권한 관리

정확한 일치하는 작업 이메일 도메인을 가진 인증 제공업체 식별자는 자동으로 조직에 가입합니다. 기존 Glossia 계정은 처음 Okta 연결 시 기존 방법으로 로그인하여 조직 로그인을 시작하기 전에 안전하게 연결합니다. 이 방법은 Okta 관리자가 다른 Glossia 계정을 장악하지 않도록 합니다. 다른 제공업체를 통한 공개 등록은 여전히 관심 양식을 사용합니다. 제공업체를 비활성화하면 기존 조직을 삭제하지 않고 조직 로그인을 중지합니다.

새 구성원은 계정, 조직, 프로젝트, 음성, 사전, 토론 및 티켓에 기본 읽기 액세스를 받습니다. 추가 액세스 권한을 부여하려면 [구성원 권한 관리](/docs/how-to/member-permissions) 를 확인하세요.

## 액세스 보장사항

도메인 소유권 인증은 30 일간 유지되며 매일 자동으로 확인됩니다. 인증 기록을 유지하세요. 사라지면 마지막 성공 인증만료 시 로그인 중지; 기록 복원 및 인증 설정에서 다시 확인합니다. 제공업체 변경 또는 조직 로그인 비활성화는 검증을 지우고 이전 제공업체의 자격을 제거합니다. 검증되지 않은 주장은 도메인을 예약하지 않습니다.

기존 계정을 전환하는 경우 먼저 기존 방법으로 로그인한 다음 `/auth/login` 를 방문하여 작업 인증 연결을 위해 작업 이메일 로그인을 시작하세요. Google 은 또한 동일한 제공업체 주체를 가진 이미 연결된 Google 아이디를 사용할 수도 있습니다. 단순히 이메일 주소만 일치로는 기존 계정 연결을 절대 수행할 수 없습니다.

구성원 제거는 자동 재등록을 차단합니다. 기존 작업 인증만으로도 액세스 복구를 위해 관리자가 명시적으로 추가하거나 초대해야 합니다.

구성원 초대 관리, 액세스 자격 증명, 언어 모델 편집 및 조직 삭제는 관리자의 책임입니다. 구성원 범위 체크박스를 통해 직접 위임할 수 없습니다. 인증 설정, 도메인 검증 및 범위 변경은 감사 이벤트를 발생시킵니다.
