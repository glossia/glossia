## 신원 제공자 연결

조직 관리자는 **설정 → 인증**에서 근무 신원 제공자를 연결할 수 있습니다.

1. **Google Workspace** 또는 **Okta**를 선택하고 팀의 근무 이메일 도메인을 입력하세요.
2. Okta 사용의 경우 [OpenID Connect](https://developer.okta.com/docs/guides/implement-grant-type/authcode/main/)를 사용하여 웹 애플리케이션을 생성하세요. 발급자, 클라이언트 식별자 및 클라이언트 시크릿을 입력하세요. Glossia 는 표준 Okta 조직 발급자와 `/oauth2/default` 인증 서버를 지원합니다. 시크릿은 저장 상태에서 암호화됩니다. 편집 시 시크릿을 비워 두면 저장된 값을 유지합니다.
3. Okta 의 경우 Glossia 에 표시됩니다 리디렉션 주소를 신원 제공자에 등록하세요. Google Workspace 의 경우, Glossia 가 Google 연결을 관리하므로 Google 애플리케이션을 생성하거나 콜백 주소를 등록할 필요가 없습니다.
4. 설정을 저장하세요. 도메인 제공자를 통해 표시된 DNS TXT 기록을 추가한 다음 **도메인 확인**을 선택하세요. 이메일 도메인을 변경하면 새로운 검증 토큰이 생성되고 재검증될 때까지 조직 로그인 능력이 비활성화됩니다.
5. 팀 구성원은 로그인 페이지에서 근무 이메일을 입력하고 **조직으로 계속하기**를 선택하세요. Google Workspace 구성원은 **Google 로 로그인**도 사용할 수 있습니다.

## Google Workspace 설정

Glossia 는 Google 애플리케이션 자격 증명을 관리합니다. Google Cloud 에서 OAuth 애플리케이션을 만들거나 Google Admin 에서 사용자 지정 SAML 애플리케이션을 추가하거나 리디렉션 주소를 등록할 필요가 없습니다. 기존 Google Workspace 도메인의 경우 설정은 Glossia 와 DNS 제공자에서 수행:

1. **설정 → 인증**에서 **Google Workspace**를 선택하고 근무 이메일 도메인을 입력한 다음 **인증 설정 저장**을 선택하세요.
2. DNS 호스팅하는 제공자로 도메인의 DNS 설정을 여세요. Google Workspace 여야 하는 것은 아닙니다. **도메인 소유권 확인**에 표시된 기록을 추가:

   | 필드 | 값 |
   | --- | --- |
   | 형식 | `TXT` |
   | 이름/호스트 | Glossia 에서 **기록 이름**으로 표시되며, 예를 들어 `_glossia-verification.example.com`처럼. |
   | 값/내용 | Glossia 에서 **기록 값**으로 표시되며 `glossia-domain-verification=`로 시작합니다. |

   일부 DNS 제공자는 도메인을 자동으로 추가합니다. 해당 경우 도메인이 두 번 포함되지 않도록 `_glossia-verification` 만 호스트로 입력하세요. 검증 후 기록을 그대로 유지하세요.
3. Glossia 로 돌아와서 **도메인 확인**을 선택하세요. 검증이 실패한 경우 이름과 값을 확인하고 DNS 변경 사항이 전파될 시간을 두었다가 다시 시도하세요.
4. 팀 구성원에게 로그인 페이지에서 근무 이메일을 입력하고 **조직으로 계속하기**를 선택하거나 **Google 로 로그인**을 사용하도록 요청하세요.

Glossia 는 Google 의 검증된 이메일과 [호스팅 도메인 주장](https://developers.google.com/identity/openid-connect/openid-connect#an-id-tokens-payload)을 확인합니다. 같은 이메일 접미사를 가진 개인 Google 계정도 제외됩니다.

### Google 이 로그인을 차단할 경우

일반적으로 Google 측 설정이 필요하지 않습니다. 조직이 제 3 자원 애플리케이션 접근을 제한하는 경우 Google Workspace 관리자가 Glossia 를 승인해야 할 수 있습니다:

1. 관리자 계정을 사용하여 [Google 관리자 콘솔](https://admin.google.com/)에 로그인하세요.
2. **보안 → 액세스 및 데이터 제어 → API 제어 → 타사 앱 액세스 관리**로 이동하세요.
3. 접근한 앱 목록에서 Glossia 를 찾아보세요. 목록에 없는 경우 앱 이름 또는 OAuth 클라이언트 ID 로 검색하려면 **새 앱 구성**을 사용하세요. OAuth 클라이언트 ID 는 생성해야 할 애플리케이션이 아닌 Glossia 의 공유 Google 연결에 속합니다.
4. 요청된 로그인 권한을 검토하고 조직 정책에 따라 관련 사용자에게 접근 권한을 허용하세요. 액세스 수준 및 관리자 요구 사항을 확인하려면 Google 의 [Google Workspace 데이터에 액세스하는 타사 및 내부 앱 제어](https://support.google.com/a/answer/7281227) 가이드를 참조하세요.
5. 정책 변경 후 효과를 발휘한 후 작업 계정으로 다시 로그인하세요.

## 등록 및 권한 관리

작업 이메일 도메인이 정확히 일치하는 검증된 제공자 신원은 자동으로 조직에 가입합니다. 기존 Glossia 계정이 Okta 를 처음 연결하는 경우 조직 로그인 시작 전에 기존 방법으로 로그인하세요. 이는 Okta 관리자가 다른 Glossia 계정을接管하지 않도록 안전하게 연결합니다. 기타 제공자를 통한 공개 등록은 계속 한편 사용을 위해 이용 신청 양식을 사용합니다. 제공자를 비활성화하면 기존 멤버십을 삭제하지 않고 조직 로그인을 중지합니다.

신규 구성원에게는 계정, 조직, 프로젝트, 성우, 용어집, 토론 및 티켓에 대한 기본 읽기 권한이 부여됩니다. 추가 액세스를 부여하려면 [멤버 권한 관리](/docs/how-to/member-permissions)를 따르세요.

## 접근 보안 조치

도메인 소유권 검증은 30 일 동안 유효하며 매일 자동으로 확인됩니다. 검증 기록을 유지하세요. 사라지면 마지막 성공적인 검증이 만료되는 즉시 로그인 속이 중지됩니다. 기록을 복원하고 인증 설정에서 다시 확인하세요. 제공자 변경 또는 조직 로그인 비활성화는 검증을 지우고 이전 제공자의 자격 증명을 제거합니다. 검증되지 않은 주장은 도메인을 예약하지 않습니다.

기존 계정의 경우 먼저 기존 방법으로 로그인한 다음 `/auth/login` 를 방문하고 근무 이메일 로그인을 시작하여 근무 신원을 연결하세요. Google 은 또한 동일한 제공자 주체로 이미 연결된 Google 신원을 사용할 수 있습니다. 이메일 주소 일치만으로는 기존 계정을 연결할 수 없습니다.

성원 제거는 자동 재등록을 차단합니다. 근무 신원이 여전히 활성 상태라도 관리자가 명시적으로 다시 추가하거나 초대해야 액세스를 복구할 수 있습니다.

성원 초대 관리, 기존 접근 자격 증명, 언어 모델 편집 및 조직 삭제는 관리자의 책임입니다. 이 권한은 멤버 스코프 체크박스를 통해 위임할 수 없습니다. 인증 구성, 도메인 검증 및 스코프 변경은 감사 이벤트를 생성합니다.
