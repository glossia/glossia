지속적 배포는 작은 변경 사항이 버전 관리, 검토, 검증, 배포를 거쳐 통과하는 반복 가능한 파이프라인을 기반으로 작동합니다. 현지화는 해당 파이프라인에 부합하도록 하는 것이 관련 없는 레코드 시스템을 도입하는 것보다 우선되어야 합니다.

## 연결이 끊긴 루프

연결이 끊긴 워크플로우에서는 제품 변경 사항이 내보내기를 트리거하고, 작업은 다른 도구에서 이루어지며, 번역된 콘텐츠는 결국 돌아옵니다. 그 사이에 소스가 다시 변경될 수 있습니다. 팀은 버전 충돌을 해결하고 번역이 낙후되었는지 판별하며 또 다른 릴리스를 조정해야 합니다.

웹 에디터가 본질적으로 잘못되었다는 것이 문제점은 아닙니다. 문제는 독립적으로 권한을 가진 편집 시스템이 언어 결정을 설명하는 코드와 콘텐츠의 수정과 분리할 수 있다는 점입니다.

## 저장소 루프

Glossia 의 저장소 워크플로우는 소스 파일과 현지화 설정을 Git 에 보존합니다. 연결된 저장소는 콘텐츠와 대상 언어를 공급합니다. 번역 변경 사항은 검토 가능한 저장소 변경 사항으로 귀환하므로, 팀은 기존 pull request 와 발행 관행을 적용할 수 있습니다.

일반적인 루프는 다음과 같습니다:

1. 팀이 제품과 함께 소스 콘텐츠를 변경합니다.
2. Glossia 는 번역 또는 향상이 필요한 콘텐츠를 식별합니다.
3. 언어 지침과 용어는 변환에 대한 맥락을 제공합니다.
4. 검증은 결과를 확인하며 실패 사항은 조치 가능하게 남아 있습니다.
5. 리뷰어는 발행 파이프라인이 이를 전달하기 전에 변경 사항을 검사합니다.

[점진적 개선](./progressive-refinement) 은 해싱과 검증이 이 루프에 어떻게 적합하게 맞는지 설명합니다. [번역 복구](./translation-recovery) 는 생성 또는 검증이 실패할 때 발생하는 상황을 설명합니다.

## 지속적은 검토되지 않음을 의미하지 않습니다.

지속적으로 배포 가능한 변경 사항이 반드시 자동으로 승인된 변경 사항인 것은 아닙니다. 법적 용어, 제품 약속, 및 문화적으로 민감한 자료는 전문가 검토를 필요로 할 수 있습니다. 해당 검토를 배포 루프에 유지하면 별도의 출판 권한을 유지하지 않아도 팀이 적절한 게이트를 선택할 수 있습니다.

지속적인 현지화는 모든 커밋마다 전체 저장소를 번역한다는 의미는 아닙니다. 변경되지 않은 콘텐츠는 반복적으로 동일한 리소스를 소비해서는 안 됩니다.

## 실용적 한계

Glossia 는 언어 컨텍스트와 현지화 메커니즘을 제공합니다. 저장소의 체크 및 배포 프로세스는 여전히 변경 사항이 안전하게 발행될 때를 정의합니다. Glossia 는 애플리케이션 테스트 혹은 에디터의 정확성 책임을 대체할 수 없습니다.

다른 플랫폼 또한 Git 통합과 CI 자동화를 제공합니다. 구별점은 의도된 중심입니다: Glossia 는 저장소에서의 콘텐츠 소유권과 검토를 중심으로 만들어졌으며, 지속적인 편집 권한을 호스팅된 번역 워크스페이스로 이동해야 하는 필수 사항이 아닙니다.
