Glossia 는 게시하기 전에 번역된 콘텐츠를 검증합니다. 복구는 이 요구 사항을 유지합니다: 재시도는 여전히 소스 구조와 필요한 플레이스홀더를 보존해야 하며, 모든 조합된 파일은 구성된 유효성 검사 명령을 통과해야 합니다.

## 마크다운 번역

Glossia 는 번역된 마크다운 문서를 다시 렌더링하지 않습니다. 소스는 본문 (단락, 헤딩, 목록 항목, 표 셀, 컴포넌트 및 HTML 의 사용자 노출 속성 (`title`, `details`, `alt`, `label`, `description`, `summary`, `placeholder`, `aria-label`, `caption`), 및 HTML `<summary>` 의 텍스트를 찾기 위해만 파싱합니다. 각 번역은 소스가 차지했던 정확한 바이트로 다시 기록되므로, 코드, 링크 목적지, 컴포넌트, GitHub 경고, 명시적 헤딩 앵커 (`{#install}`), 목록 마커 및 빈 줄은 바이트 단위로 동일하게 유지됩니다.

각 단락이나 제목은 전체 문장으로 번역됩니다. 인라인 포맷팅은 번호가 매겨진 태그로 변환됩니다: 연결되거나 강조된 단어 주변의 `<gN>...</gN>` 와 변경하지 않아야 하는 콘텐츠, 예를 들어 인라인 코드나 컴포넌트를 위한 `<gN/>`. 모델은 목표 언어의 단어 순서를 따라 태그 위치를 이동할 수 있지만, 모든 태그를 정확히 한 번씩만 유지해야 합니다. 또한 모든 요청은 참조용으로 주변 소스 문서와 동일한 파일에서 가장 최근 번역을 포함합니다.

태그를 누락하거나 새로 만든 단위는 이유와 함께 최대 3 회까지 별개로 다시 전송됩니다. 유효한 결과가 반환된 단위는 보존됩니다. 스플라이싱 후 Glossia 는 결과를 파싱하고 소스와 구조를 비교합니다. 스스로 헤딩, 목록, 또는 강조가 될 가능성이 있는 번역은 본문을 이스케이프 처리하여 추가 모델 호출이 필요 없게 합니다.

## 카탈로그 번역

Gettext 카탈로그는 번역 전에 문자열로 파싱됩니다. 요청은 최대 8 개의 문자열을 가지며, 8,000 바이트 배치 목표가 있습니다. 단일 더 큰 문자열은 그대로 유지됩니다. 모델은 동일한 수의 문자열을 동일한 순서로 배열을 반환합니다. Glossia 는 격자 변수를 확인하고 빈 번역을 거부합니다.

헤더는 목표 로cales 의 복수 규칙을 사용하여 코드로 생성됩니다. 소스 메시지 식별자, 주석, 및 카탈로그 구조는 파싱된 소스에서 옵니다. 배치에 잘못된 콘텐츠가 반환되면 Glossia 는 한 번 다시 시도한 다음 더 작은 배치로 분리합니다. 성공적인 인접 배치에는 다시 번역할 필요가 없습니다.

## 제공업체 속도 제한

Glossia 는 동일한 자격 증명과 모델을 사용하는 번역 요청을 조정합니다. 속도 제한 응답은 공유 쿨다운을 연장하고 새로운 요청 간의 간격을 증가시킵니다. 성공적인 트래픽은 속도 제한 없이 1 분 후 점진적으로 그 간격을 줄입니다. 이미 실행 중인 요청은 완료될 수 있습니다.

제공자 재시도 힌트는 최소 지연 시간을 의미합니다. 반복 실패는 또한 백오프를 증가시키며, 최대 30 초 기본 지연 시간과 자터지 (jitter) 까지 적용됩니다. 더 긴 제공자 힌트는 우선 적용되지만 최대 5 분을 초과하지 않습니다. Together 의 `x-ratelimit-reset` 헤더 는 `retry-after` 와 함께 인식됩니다.

8 번의 실패한 요청 시도 후, 저장소 실행은 새로운 파일을 시작하는 것을 중단합니다. 지연된 지속은 번역 브랜치를 계승하여未完작업을 재개합니다. 이전 시도는 지속을 통해 세션 이력에 가시적으로 유지됩니다. 지연은 1 분에서 5 분으로 증가하며, 최대 6 번 자동 지속으로 제한됩니다. 더 새로운 활성 세션이 우선권을 가지며, 취소된 세션은 결코 다시 시작되지 않습니다. 유효성 검사 실패만으로는 제공업체 복구를 예약하지 않습니다.

## 엔진 릴리스 후 복구

세션은 두 개의 독립적인 버전이 있습니다: 번역 중인 저장소 커밋과 실행 중인 번역 엔진 이미지. Kubernetes 에서 각 작업은 예약한 웹 복제본의 정확한 이미지 디지스트를 고정합니다. 작업은 웹 배포를 견뎌며 번역의 절반에서 코드를 전환하지 않습니다. 배포 직전에 예약된 작업은 결과적으로 웹 애플리케이션이 업데이트 된 후에도 이전 엔진에서 완료될 수 있습니다. 세션 세부 사항에는 엔진 디지스트가 표시됩니다; 이전 세션에서는 이러한 출처가 없으므로 "Not recorded."를 표시합니다.

매 5 분마다 Glossia 는 배포가 완전히 배포되었는지 확인합니다. 그 정상 릴리스의 작업자 만 엔진 복구를 예약할 수 있습니다. 프로젝트의 마지막 세션이 해당 배포 완료 전에 대기열에 있었고, 오래된 기록된 엔진 디지스트에서 실행되었으며 배포 후 6 시간 이내에 실패한 경우, Glossia 는 현재 릴리스에서 지속을 생성할 수 있습니다. 대기렬 시간 또한 용량을 기다리는 작업을 포함하며 배포 후에만 부팅됩니다. 다른 이미지 디지스트 하나로는 관련 없는 배포 후 일반 실패의 재시도를 유발하지 않습니다. 완료된 파일 및 열린 번역 풀 요청은 계속 됩니다; 완료되지 않은 작업만 다시 번역됩니다. 대기열 릴리스 지속은 배포 진행 중 최대 15 분 동안 대기합니다. Kubernetes API 나 권한 실패는 명시적인 오류 로 시작을 중단하여 진행 중인 배포로 오인하지 않도록 합니다.

복구는 의도적으로 제한적입니다: 세션은 기록된 항목-유효성 검 실패로 종료하며, 최신 시도내의 각 실패 항목은 마크다운 구조, 보존된 콘텐츠 또는 마크다운 단 실패를 보고해야 합니다. 중단되거나 부분적으로 취소된 시도는 자격이 없습니다. 제공업체 오류, 고갈된 크레딧, 거부된 자격 증명, 게시 실패, 소스 읽기 오류, 외부 유효성 검사 명령 실패 및 미확인 원인은 배포에서 재시도하지 않습니다. 성공, 활성, 취소, 대체, 버전 없는 세션도 그대로 둡니다. 사용자 취소하더라도 더 새로운 세션은 항상 이깁니다.

세션은 다른 엔진 릴리스에서 최대 하나의 지속을 받으며, 계통에서 최대 세 개의 릴리스 지속을 가집니다. 새 엔진이 여전히 실패하면 동일한 이미지, 롤백 뒤 포함하여 다시 재시도하지 않습니다. 계통은 이전에 시도된 엔진 디지스트를 유지하며, 실행기는 잡을 저장하기 전에 다시 확인합니다. 기존 제공업체 복구 제한은 릴리스 지속을 유지합니다. 가변 이미지 태그 및 설정되지 않은 릴리스 식별자 없이 있는 배포는 자동 엔진 복구를 활성화하지 않습니다.

## 견고한 진행

완료된 파일과 해당 잠금 파일은 배치로 번역 브랜치에 게시됩니다. 25 개의 파일마다 한 번 커밋하거나 15 분마다 한 번 커밋하고, 런이 종료되면 최종 커밋을 합니다. 각 푸시는 저장소의 풀 리퀘스트 확인을 실행하므로, 배치는 큰 런에서 파일당 하나의 확인 작업을 시작하는 것을 방지합니다. 프로젝트에는 단일 번역 풀 리퀘스트가 있습니다. 기본 브랜치에 새 커밋이 이어지며,从那以来 변경된 부분만 번역됩니다. 해당 풀 리퀘스트가 병합되거나 닫히면, 다음 런은 새로운 것을 시작합니다. 완료되지 않은 파일 내에서는 로컬 유효성 검사된 세그먼트와 복구 배치도 데이터베이스에 7 일 동안 저장됩니다. 이 체크포인트는 워크러 프로세스가 정지되어도 유지됩니다. 이는 계정, 프로젝트, 문서 입력, 유효한 자격 증명과 모델, 컨텍스트, 그리고 세그먼트 또는 수리 시도에 범위가 적용됩니다.

재개된 런은 입력이 여전히 일치할 때만 세그먼트를 재사용할 수 있습니다. 항상 최종 조립된 문서를 다시 유효성 검사합니다. 거부된 모델 응답은 체크포인트가 아닙니다. 문서 수준의 유효성 검사 실패는 검증자가 단일 책임 세그먼트를 식별할 수 없을 수 있으므로 별도의 수리 시도를 시작합니다.

만료된 체크포인트 및 비활성 제공자 속도 제한 기록은 예약된 세션 복구 워크러에 의해 제거됩니다. 이들은 운영 기록이며, 사용자가 저장소에 추가하거나 `L10N.md` 에 설정할 필요가 없습니다.
