Glossia 는 출판하기 전에 번역된 콘텐츠를 검수합니다. 회복 작업은 그 요구사항을 유지합니다: 재시도는 여전히 출처 구조와 필수 플레이스홀더를 보존해야 하며, 조립된 모든 파일이 설정된 검수 명령을 통과해야 합니다.

## 마크다운 번역

Glossia 는 번역된 Markdown 문서를 다시 렌더링하지 않습니다. 소스는 문장을 찾아 파싱하기만 합니다: 단락, 제목, 목록 항목, 표 셀, 컴포넌트 및 HTML 의 사용자 노출 속성 (`title`, `details`, `alt`, `label`, `description`, `summary`, `placeholder`, `aria-label`, `caption`), 그리고 HTML `<summary>` 의 텍스트입니다. 각 번역은 소스가 보장한 정확한 바이트로 다시 쓰이므로 코드, 링크 목적지, 컴포넌트, GitHub 경고, 명시적 제목 앵커 (예: `{#install}`), 목록 마커, 및 공백 줄은 바이트 단위로 동일하게 유지됩니다.

각 단락이나제목은 문장 전체로 번역됩니다. 인라인 포맷팅은 번호가 붙은 태그로 바뀝니다: 링크되거나 강조된 단어 주변에 `<gN>...</gN>` 와, 변경해서는 안 되는 콘텐츠 (인라인 코드나 컴포넌트 등) 에 `<gN/>` 를 위해. 모델은 태그를 이동하여 대상 언어의 단어 순서를 반영할 수 있지만, 모든 태그를 정확히 한 번씩만 유지해야 합니다. 또한 모든 요청은 참조용으로 주위 소스 문서 및 동일한 파일의 최신 번역을 포함합니다.

태그를 누락하거나 발명하는 유닛은 사유에 따라 개별적으로 최대 3 회 다시 보냅니다. 유효한 결과를 반환한 유닛은 유지됩니다. 스플라이싱 후, Glossia 는 결과를 파싱하여 소스 구조와 비교합니다. 스스로 제목, 목록, 또는 강조가 될 번역은 그 문법이 의도 없이 이스케이프 처리되어 추가 모델 호출이 필요 없습니다.

## 카탈로그 번역

Gettext 카탈로그는 번역 전 문자열로 파싱됩니다. 요청은 최대 8 개 문자열을 포함하며, 8,000 바이트 배치 대상입니다. 단일 더 긴 문자열은 그대로 유지됩니다. 모델은 순서대로 동일한 수의 문자열을 가진 배열을 반환합니다. Glossia 는 내삽 변수를 확인하고 빈번번역 내용을 거부합니다.

헤더는 코드를 통해 타겟 로케일의 복수 규칙을 사용하여 구축됩니다. 소스 메시지 식별자, 주석 및 카탈로그 구조는 파싱된 소스에서 나옵니다. 배치에서잘못된 내용이되면 Glossia 는 한 번 다시 시도한 뒤에 더 작은 배치로 나눕니다. 성공한 인접 배치는 다시 번역할 필요가 없습니다.

## 제공자 스로틀링

Glossia 는 동일한 자격증명과 모델을 사용하는 번역 요청을 조정합니다. 레이트리미트 응답은 공유 쿨다운을 확장하고 새 요청 사이의 간격을 증가시킵니다. 성공적인 트래픽은 1 분 동안 스로틀링 없이 그 간격을 서서히 줄입니다. 이미 실행 중인 요청은 완료하는 것이 허용됩니다.

제공자 재시도 힌트는 최소 지연 시간입니다. 반복 실패도 후속 지연을 늘립니다: 최대 30 초 기본 지연 시간 및 잡음. 더 긴 제공자 힌트가 우선권이 주어지며, 최대 5 분까지 제한됩니다. Together 의 `x-ratelimit-reset` 헤더 는 `retry-after` 헤더 와 함께 인식됩니다.

실패한 요청 시도가 8 회되면 저장소 런치는 새로운 파일을 시작하는 것을 멈춥니다. 지연된 시도는 번역 브랜치를 이어받고 미완료 작업을 재개합니다. 이전 시도는 다음을 통해 세션 역사에 연결되어 여전히 표시됩니다. 지연은 1 분에서 5 분으로 증가하며, 최대 6 회 자동재연이 가능합니다. 최신 활성 세션이 우선이 되며, 취소된 세션은 절대 다시 활성화되지 않습니다. 검증 실패만으로는 제공자 회복을 예약하지 않습니다.

## 지속적인 진행

완료된 파일과 그들의 잠금 파일은 배치로 번역 브랜치에 게시됩니다: 파일당 25 개마다 한 커밋 또는 15 분마다 커밋되며, 런치가 종료될 때 마지막 커밋이 있습니다. 각 푸시는 저장소의 풀 요청 검사를 실행하므로, 배치 처리는 큰 런치가 파일당 하나의 검사 런치로 시작되는 것을 방지합니다. 프로젝트는 단일 번역 풀 요청을 가지고 있습니다: 기본 브랜치에 새로운 커밋은 열린 요청을 계속하며, 오직 변경된 부분만 번역합니다. 그 풀 요청이 병합되거나 닫히면, 다음 런치는 새로운 하나를 시작합니다. 미완료 파일 내에서, 로컬로 검증된 세그먼트 와 회복배치는 또한 7 일 동안 데이터베이스에 저장됩니다. 이 체크포인트 는 근로자 프로세스가 중지되더라도 생존합니다. 그들은 계정에, 프로젝트, 문서 입력, 유효 자격 증명 및 모델, 컨텍스트, 및 세그먼트 또는 수리 시도에 대해 범위를 지정됩니다.

재개된 런치는 입력이 여전히 일치할 때만 세그먼트 를 재사용할 수 있습니다. 그것은 항상 최종 조립 문서를 다시 검수합니다. 거부된 모델 응답은 체크포인트가 아닙니다. 문서 수준검증 실패는 검증자가 단일 responsabilità 세그먼트 를 식별할 수 없기 때문에 별도의 수리 시도를 시작합니다.

만료된 체크포인트 와 비활성 제공자 페이싱 기록은 예정된 세션 복구 근로자에 의해 삭제됩니다. 이들은 운영 기록이므로, 사용자가 저장소에 추가하거나 `L10N.md` 에서 구성할 필요가 없습니다.
