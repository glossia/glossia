Glossia 는 게시하기 전에 번역된 콘텐츠를 유효성 검사합니다. 복구는 이러한 요구사항을 유지합니다: 재시도는 소스 구조와 필요한 플레이스홀더를 반드시 보존해야 하며, 구성된 유효성 검사 명령을 모두 통과하는 각 조립된 파일은 있어야 합니다.

## 마크다운 번역

Glossia 는 번역된 마크다운 문서를 다시 렌더링 하지 않습니다. 소스를 파싱하여 문구를 찾습니다: 단락, 제목, 목록 항목, 표 셀, 컴포넌트와 HTML 의 리더 전용 속성 (`title`, `details`, `alt`, `label`, `description`, `summary`, `placeholder`, `aria-label`, `caption`), 및 HTML `<summary>` 의 텍스트. 각 번역은 소스가 차지한 정확한 바이트만큼 다시 작성되므로, 코드, 링크 목적지, 컴포넌트, GitHub 경고, 명시적 제목 앵커 (예: `{#install}`), 목록 마커, 및 빈 줄은 바이트 단위로 완전히 동일하게 유지됩니다.

각 단락이나 제목은 하나의 문장 전체로 번역됩니다. 라인은 연결되거나 강조된 단어 주변 번호 태그 (`<gN>...</gN>`), 불변해야 하는 내용을 위한 태그 (`<gN/>`) 로 변경됩니다. 모델은 대상 언어의 단어 순서를 따르도록 태그를 이동할 수 있지만, 모든 태그를 정확히 한 번씩 유지해야 합니다. 모든 요청은 또한 주변 소스 문서와 같은 파일의 최신 번역을 함께 전달하여 참조합니다.

TAG 가 누락되거나 고안되는 단일 이미 재전송되어, 사유를 함께 최대 3 회까지 실행됩니다. 확인된 유효한 단일 이미 유지됩니다. 스플라이싱 후 Glossia 는 결과를 파싱하여 소스와 구조를 비교합니다. 스스로 제목, 목록, 또는 강조가 되는 번역에서 모든 문구는 이스케이프 되며, 이는 추가 모델 호출이 필요 없습니다.

## Gettext 카탈로그 번역

Gettext 카탈로그는 번역 전에 문자열로 파싱됩니다. 요청은 최대 8 개의 문자열을 포함하며, 8,000 바이트 배치 목표를 가집니다. 단일 더 큰 문자열은 기본 유지됩니다. 모델은 동일한 수의 문자열을 동일한 순서로 배열한 배열을 반환합니다. Glossia 는 보간 변수를 검사하고 비어 있는 번역을 거부합니다.

헤더는 코드에서 대상 로케일의 복수 규칙을 사용하여 구축됩니다. 소스 메시지 식별자, 주석, 및 카탈로그 구조는 파싱된 소스 정보에서 가져옵니다. 배치가 잘못된 콘텐츠를 반환하면 Glossia 는 한 번 재시도한 다음 더 작은 배치로 나눕니다. 성공한 인접 배치는 다시 번역할 필요가 없습니다.

## 제공자 스로틀링

Glossia 는 동일한 인증정보와 모델을 사용하는 번역 요청을 조정합니다. 레이트 제한 응답은 공유 쿨다운 기간을 늘리고 새 요청 간격을 늘립니다. 성공적인 트래픽은 스로틀링이 없는 한 분 간격 후 그 간격을 점진적으로 줄입니다. 이미 실행 중인 요청은 완료할 기회를 허용합니다.

Provider 재시도 힌트는 최소 지연 시간을 의미합니다. 반복 실패는 또한 재를 늘려, 최대 30 초 기준 지연과 지터를 반영하며, 제공자 힌트가 더 긴 경우 우선순위로 처리되며 최대 5 분으로 제한됩니다. Together 의 `x-ratelimit-reset` 헤더는 `retry-after` 와 함께 인식됩니다.

8 번의 요청 실패 시 저장소 실행은 새 파일 시작을 중단합니다. 지연된 연쇄는 번역 브랜치를 상속받고未完 작업을 재개합니다. 이전 시도는 세션 히스토리에서 연쇄를 통해 남아 있습니다. 지연은 1 분에서 5 분으로, 최대 6 번의 자동 연쇄 증가합니다. 최신 활성 세션이 우선이며, 취소된 세션은 절대 소생되지 않습니다. 유효성 검사 실패만으로는 제공자 복구를 예약할 수 없습니다.

## 엔진 릴리스 후 복구

세션은 두 개의 독립 버전이 있습니다: 번역 중인 저장소 커밋과 실행하는 번역 엔진 이미지. Kubernetes 에서 각 작업은 스케줄한 웹 리플리카의 정확한 이미지 디지스트를 고정합니다. 작업은 웹 롤아웃을 생존하며 번역 중간에 코드를 바꿀 수 없습니다. 웹 애플리케이션이 업데이트된 후에도 롤아웃 직전 스케줄링 한 작업은 이전 엔진에서 완료할 수 있습니다. 세션 세부 사항은 엔진 디지스트를 표시하며, 이 출처 없이 이전 세션은 "Not recorded."를 표시합니다.

매 5 분마다 Glossia 는 배포가 완전히 롤아웃되었는지 확인합니다. 건강 상태 배포의 작업만이 엔진 복구를 예약할 수 있습니다. 프로젝트의 최신 세션이 해당 롤아웃 이전 큐에 머물렀고 이전 기록된 엔진 디지스트에서 실행되었으며, 이후 6 시간 이내에 실패한 경우 Glossia 는 현재 릴리스에서 연쇄를 생성할 수 있습니다. 큐 시간 역시 용량 대기 후 롤아웃 후 시작하는 작업을 포함합니다. 다른 이미지 디지스트는 배포 실패와 관련 없는 일반 실패 재시도는 트리거하지 않습니다. 완료된 파일 및 열린 번역 Pull Request 는 이어지고, 없는 작업만 다시 번역됩니다. 큐잉된 릴리스 연쇄는 진행 중인 롤아웃 동안 최대 15 분 동안 기다립니다. Kubernetes API 또는 권한 실패는 명시적 오류로 계속해서 롤아웃 진행 중으로 오인되지 않도록 중단합니다.

복구는 의도적으로 좁습니다: 세션은 기록된 항목 유효성 검사 실패로 끝나야 하며, 최신 시도 내의 모든 실패 항목은 마크다운 구조, 보존된 콘텐츠, 또는 마크다운 단위 실패를 보고해야 합니다. 차단되거나 부분 취소된 시도에는 자격이 없습니다. 제공자 오류, 소진된 크레딧, 거부된 인증정보, 게시 실패, 소스 읽기 오류, 외부 유효성 검사 명령 실패, 및 원인부는 배포에서 재시도되지 않습니다. 성공적, 활성, 취소, 중복, 및 비버전 세션은 또한 방치됩니다. 최신 세션은 항상 우세하며, 사용자로 취소된 경우에도 마찬가지입니다.

세션은 다른 엔진 릴리스에서 최대 하나의 연쇄만을 확보하며, 선계에 최대 3 개의 릴리스 연쇄를 가질 수 있습니다. 새 엔진이 여전히 실패하면, 롤백 후에도 동일한 이미지에서 재시도되지 않습니다. 선계는 이전에 시도한 엔진 디지스트를 유지하며, 로uncer 는 큐잉된 작업을 생성하기 전에 다시 확인합니다. 기존 제공자 복구 제한은 릴리스 연쇄를 거치며 유지됩니다. 변경 가능 이미지 태그 및 릴리스 스태블처를 구성하지 않은 배포는 자동 엔진 복구를 활성화하지 않습니다.

## 영속적 진행

완료된 파일과 락 파일은 배치로 번역 브랜치에 게시됩니다: 25 개의 파일마다 한 커밋 또는 15 분마다 한 커밋이며, 실행이 종료될 때 최종 커밋이 생성됩니다. 각 푸시는 저장소의 풀 리퀘스트 검사를 실행하므로, 배치는 대규모 실행이 파일 하나당 하나의 검사 실행을 시작하는 것을 방지합니다. 프로젝트에는 단일 번역 풀 리퀘스트가 있습니다: 기본 브랜치에 새 커밋은 열린 것을 이어주며, 변경된 것만 번역합니다. 해당 풀 리퀘스트가 병합되거나 닫히면 다음 실행은 새로운 것을 시작합니다. 완료되지 않은 파일 안에서는 로컬로 검증된 세그먼트와 복구 배치는 또한 데이터베이스에 7 일 동안 저장됩니다. 이러한 체크포인트는 워커 프로세스 정지에도 견딥니다. 이는 계정, 프로젝트, 문서 입력, 유효한 인증 정보 및 모델, 컨텍스트, 그리고 세그먼트 또는 수리 시도에 적용됩니다.

재개된 실행은 입력이 여전히 일치할 때만 세그먼트를 재사용할 수 있습니다. 그것은 항상 최종 조립된 문서를 다시 검증합니다. 거부된 모델 응답은 체크포인트가 아닙니다. 문서 수준의 검증 실패는 검증자가 단일 책임 세그먼트를 식별하지 못할 수 있으므로 별도의 수리 시도를 시작합니다.

만료된 체크포인트와 비활성 제공자 페이싱 기록은 일정된 세션 복구 워커에 의해 제거됩니다. 이들은 운영적 기록이며, 사용자는 저장소에 이를 추가하거나 `L10N.md` 에서 구성할 필요가 없습니다.
