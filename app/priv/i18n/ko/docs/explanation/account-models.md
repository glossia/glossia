Glossia 는 저장소 지시사항과 모델 제공자 자격 증명을 분리합니다. 저장소는 번역해야 할 내용을 정의하며, 계정은 어떤 [대형 언어 모델](https://en.wikipedia.org/wiki/Large_language_model)이 이를 처리할지 결정합니다.

## 계정에 모델을 할당하는 이유

팀이 동일한 제공자 관계를 가진 여러 저장소를 번역하는 경우가 많습니다. 계정 범주의 모델은 관리자가 모든 저장소를 수정하지 않고도 제공자 키를 회전하거나 기본 모델을 한 번 변경할 수 있게 합니다.

이 경계는 또한 자격 증명을 버전 관리 외부로 유지합니다. 저장소는 `translation-default`와 같은 읽을 수 있는 핸들을 포함하며, 제공자 키는 아닙니다.

## 핸들은 안정된 의도를 제공합니다.

`model` 필드는 `L10N.md` 에서 계정 모델 핸들을 참조합니다:

```yaml
model: translation-default
```

핸들은 저장소의 의도를 표현합니다. 나중에 관리자는 저장소 설정이 안정된 상태로 유지되는 동안 해당 핸들이 선택하는 제공자 모델을 업데이트할 수 있습니다.

## 여러 모델 사용 방법

Glossia 는 각 문서 번역마다 하나의 구성된 **생성형** 모델을 사용합니다. 여러 모델을 추가해도 앙상블, 폴백 체인 또는 자동 품질 등급이 생성되지 않습니다. 저장소 작성자는 `translation-default`, `long-form`, 또는 `japanese-specialist`와 같은 안정적인 핸들을 통해 목적을 선택합니다.

선택은 문서 및 대상 로케일의 컨텍스트 계층 구조를 따릅니다:

1. 해당 로케일에 대해 `L10N/<locale>.md` 파일이 `model`를 선언한 가장 가까운 파일이 우선합니다.
2. 그렇지 않으면 `L10N.md` 파일에서 `model`를 선언한 가장 가까운 파일이 해당 디렉토리에 우선합니다.
3. 더 가까운 파일에서 모델이 선언되지 않을 때 부모 `L10N.md` 설정은 상속됩니다.
4. 적용 가능한 컨텍스트 파일이 핸들을 선언하지 않으면 Glossia 는 계정 기본 생성형 모델을 사용합니다.

명시적으로 구성한 핸들이 존재해야 합니다. Glossia 는 계정 기본값으로 무작정 전환하는 대신 알려지지 않은 핸들에 대해 오류를 보고합니다.

## 기본 선택

저장소에 자체 `L10N.md` 가 되기 전에 프로젝트 구성이 모델을 필요로 합니다. 따라서 Glossia 는 계정 기본값을 선택합니다. 각 카테고리에 추가된 첫 번째 모델은 해당 카테고리의 기본 모델이 되며, 관리자는 설정 페이지에서 다른 모델을 기본 모델로 만들 수 있습니다.

저장소에 `L10N.md` 가 있으면 명시적 핸들을 사용하는 것이 검토자의 선택을 명확하게 합니다. `model` 를 생략하면 저장소는 계정 기본값으로 남습니다.

## 생성형과 결정 모델

모델 구성에는 두 가지 카테고리가 있습니다:

- **생성형** 모델은 번역을 작성하고 프로젝트 구성을 구동합니다. 저장소 모델 핸들 및 로케일 라우팅 규칙은 이 카테고리만 선택합니다.
- **결정** 모델은 고정된 품질 기준에 따라 번역을 평가합니다. 계정이 결정 모델을 보유하고 있으면 기본 결정 모델은 구조적 검증 후 콘텐츠 엔드포인트의 완전한 단일 문서 번역을 평가합니다. 생성 기본 원리로 사용된 프래그먼트 요청은 조립된 결과를 평가합니다.

각 카테고리는 독립적인 기본값을 가집니다. Jev 를 추가해도 번역을 작성하는 모델을 변경하지 않습니다. 첫 번째 결정 모델은 이후 번역 실행 기간에 평가를 활성화하며, 마지막 모델을 삭제하면 평가 기능이 비활성화됩니다. 결정 모델을 갖지 않은 계정은 기존 동작을 유지합니다.

Glossia 는 현재 [TypeSafe Jev](https://docs.typesafe.ai/introduction) 을 결정 제공자로서 지원합니다. Jev 는 문장 대신 사전 정의된 선택지와 점수를 반환합니다. Glossia 는 약점 선택지를 수정 제안으로 변환하지만, 이를 위치되거나 독립적으로 검증된 오류로 제시하지 않습니다.

## 품질 점검 및 수정

평가기는 소스, 번역, 대상 로케일, 콘텐츠 형식, 프로젝트 지시사항 및 해결된 조직 컨텍스트를 받습니다. 의미 보존, 완성도, 전문 용어, 유창성, 문서 일관성, 목적 및 대상 적합성, 그리고 로케일 적절성을 평가합니다. 목소리, 프로젝트 또는 문서 가이드가 가용할 경우 목소리와 레지스터가 평가됩니다.

각 차원은 설정된 최소 점수에 도달해야 하며, 기본값은 10 점 만점 중 7 점입니다. 중요하거나 치명적인 오류는 점수에 관계없이 항상 수정을 요청합니다. 신뢰도는 실시간 평가 이벤트에 포함되어 있되 승인 결과를 변경하지 않습니다. 이러한 이벤트는 현재 대시보드에 보유되거나 표시되지 않습니다. 10 점 임계값은 완벽한 가중 점수를 요구하며 일반적으로 너무 엄격합니다.

실패한 차원은 사전 정의된 수정 힌트를 다음 번역 시도에 제공합니다. 저장소의 기존 `retries` 설정이 이러한 수정을 제한하며, 콘텐츠 엔드포인트는 0 에서 3 까지 `retries` 필드를 통해 수정 재시도를 가능하게 합니다. 완성된 수정된 문서는 승인되기 전에 구조적 검증 및 품질 평가를 다시 통과해야 합니다.

일시적 제공자 오류는 최대 3 회 지수적 백오프로 재시도하며, 잘못된 자격 증명 및 잘못된 형식의 응답은 즉시 실패합니다. 소진된 제공자 오류는 파일의 번역을 중단하며, 확인되지 않은 출력은 절대 수용되지 않습니다. 평가는 완전한 문서를 사용하며 과도한 평가 입력은 절단되어 거부됩니다. 직렬화된 입력은 상태 및 가장 긴 질문에 대해 30,000 바이트, 전체 요청에서 60,000 바이트로 보수적으로 제한되며 [Jev 의 컨텍스트 한도](https://docs.typesafe.ai/models) 를 준수합니다. 자동 점수는 모델 판단이며 여전히 양국어 인간 검토와 비교하여 보정이 필요합니다.

평가기 구성 및 규칙 버전은 번역 lock 파일에 포함됩니다. 평가 활성화, 모델 또는 임계값 변경, 또는 평가 제거는 이전 번역을 다음 실행을 위해 변질된 상태로 만듭니다. 제공자 키는 lock 파일에 포함되지 않습니다.

## 인간 검토 경계

모델 출력은 제안된 작업이며 자동 병합이 아닙니다. 설정 및 번역 활동은 Glossia 에서 계속 가시적으로 유지되며, 저장소 변경 사항은 팀이 검토할 수 있는 pull request 를 통해 게시됩니다. 이는 이미 코드에 사용하는 동일한 품질 및 소유권 경계를 유지합니다.
