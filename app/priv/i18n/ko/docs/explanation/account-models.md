Glossia 는 저장소 지침과 모델 공급자 인증 정보를 분리합니다. 저장소는 번역해야 할 대상이 무엇인지 기술하고, 계정은 어떤 [대규모 언어 모델](https://en.wikipedia.org/wiki/Large_language_model) 작업을 수행합니다.

## 모델이 계정에 속하는 이유

팀이 종종 동일한 공급자 관계를 통해 여러 저장소를 번역합니다. 계정 범위의 모델은 관리자가 모든 저장소를 수정하지 않고 한 번에 공급자 키를 회전하거나 기반 모델을 전환할 수 있게 합니다.

이 경계는 또한 인증 정보를 소스 코드 관리에서 제외합니다. 저장소는 읽기 가능한 핸들, 예를 들어 `translation-default`, 공급자 키가 아닙니다.

## 핸들은 안정적인 의도를 제공합니다.

이 `model` 필드에서 `L10N.md` 는 계정 모델 핸들의 값을 나타냅니다:

```yaml
model: translation-default
```

핸들은 저장소의 의도를 표현합니다. 관리자는 나중에 해당 핸들이 선택하는 제공자 모델을 업데이트할 수 있으며, 저장소 구성은 안정적으로 유지됩니다.

## 여러 모델의 사용 방법

Glossia 는 하나의 설정된 **생성형** 모델로 각 문서 번역을 수행합니다. 여러 모델을 추가하더라도 앙상블, 페일백 체인, 또는 자동 품질 계층을 생성하지는 않습니다. 저장소 작성자는 안정적인 핸들, 예를 들어를 통해 목적을 선택합니다. `translation-default`, `long-form`, 또는 `japanese-specialist`.

선택은 문서 및 대상 로케일의 컨텍스트 계층을 따릅니다:

1. 가장 가까운 `L10N/<locale>.md` 선언하는 파일 `model` 해당 로케일에서 우선됩니다.
2. 그렇지 않으면, 가장 가까운 `L10N.md` 선언하는 파일 `model` 해당 디렉터리에서 우선 적용됩니다.
3. 상위 `L10N.md` 더 가까운 파일에서 모델이 선언되지 않으면 설정이 상속됩니다.
4. 적용 가능한 컨텍스트 파일에서 핸들을 선언하지 않은 경우, Glossia 는 계정 기본 생성 모델을 사용합니다.

명시적으로 구성된 핸들은 반드시 존재해야 합니다. 알 수 없는 핸들의 경우 Glossia 는 계정 기본값으로 전환하는 대신 오류를 보고합니다.

## 기본 선택

프로젝트 설정은 저장소가 자체 모델을 갖기 전에 모델을 갖춰야 합니다. `L10N.md`. Glossia 는 따라서 계정 기본 모델을 선택합니다. 각 카테고리에 추가된 첫 번째 모델이 해당 카테고리의 기본 모델이 되며, 관리자는 설정 페이지에서 다른 모델을 기본 모델로 지정할 수 있습니다.

만일 저장소가 `L10N.md`명시적인 핸들을 사용하면 검토자에게 선택 이 명확 합니다. 생략 `model` 계정 기본값 으로 저장소를 유지합니다.

## 생성 및 의사결정 모델

모델 설정은 두 가지 범주로 구분됩니다.

- **생성** 모델은 번역을 작성하고 프로젝트 설정을 구동합니다. 저장소 모델 핸들과 로케일 라우팅 규칙은 이 카테고리만 선택합니다.
- **결정** 모델은 고정된 품질 평가 기준에 따라 번역을 평가합니다. 계정이 결정 모델을 보유하면 기본 결정 모델이 구조적 유효성 검증 후 컨텐츠 엔드포인트에서 완성된 단일 문서 번역의 각 저장소 문서를 자동으로 확인합니다. 프래그먼트 요청은 생성 기본 단위이며, 저장소 실행은 조립된 결과를 평가합니다.

카테고리는 독립적인 기본값을 가집니다. Jev 를 추가해도 번역 작성 모델을 변경하지 않습니다. 첫 번째 결정 모델은 이후 번역 실행에 evaluations 를 활성화하며, 마지막 모델을 삭제하면 평가를 비활성화합니다. 결정 모델이 없는 계정은 기존 동작을 유지합니다.

Glossia 는 현재 지원합니다 [TypeSafe Jev](https://docs.typesafe.ai/introduction) 결정 제공자로 사용합니다. Jev 는 문구 대신 사전 정의된 선택지와 점수를 반환합니다. Glossia 는 약점 선택지를 교정 힌트로 변환하며, 해당 결과를 위치가 지정되거나 독립적으로 검증된 오류로 표현하지 않습니다.

## 품질 점검 및 수정

평가자는 소스, 번역, 대상 로케일, 컨텐츠 형식, 프로젝트 지침 및 해결된 조직 컨텍스트를 받습니다. 평가자는 의미 보존, 완결성, 용어, 유창성, 문서 일관성, 목적 및 대상 적합성, 로케일 적절성을 평가합니다. 음성, 프로젝트 또는 문서 지침이 사용 가능한 경우 음성과 레지스터가 평가됩니다.

각 차원은 설정된 최소 점수에 도달해야 하며 기본값은 10 점 중 7 점입니다. 주요하거나 심각한 오류는 점수 여부에 관계없이 항상 수정을 요청합니다. 신뢰도는 실시간 평가 이벤트에 포함되지만 승인 조건을 변경하지는 않습니다. 이러한 이벤트는 현재 대시보드에 보존되거나 표시되지 않습니다. 10 점 임계점은 완벽한 가중 점수를 요구하며 실제로 너무 엄격합니다.

실패한 차원들은 사전 정의된 수정 단서를 다음 번역 시도 에 제공합니다. 저장소의 기존 `retries` 설정은 이를 제한하며, 콘텐츠를 관리하는 엔드포인트는 해당 필드인 `retries` 를 통해 0 에서 3 까지 수정 재시도를 허용합니다. 완전하게 다시 검토된 문서는 승인되기 전에 다시 구조적 검토 및 품질 평가를 통과해야 합니다.

일시적 제공자 오류는 지수적 백오프를 사용하여 최대 3 회까지 재시도됩니다. 자격 증명 오류 또는 형식이 잘못된 응답은 즉시 실패합니다. 제공자 오류가 소진되면 파일 번역이 중단되며, 검증되지 않은 출력은 절대 승인되지 않습니다. 평가는 완성된 문서를 기반으로 하며, 과도하게 큰 입력은 잘라내기 대신 거절됩니다. 직렬화된 입력은 상태와 가장 긴 질문을 위해 보수적으로 30,000 바이트로 제한되며, 전체 요청 범위 내에서는 60,000 바이트로 제한되어 [Jev 의 컨텍스트 제한](https://docs.typesafe.ai/models)을 준수합니다. 자동 점수는 모델의 판단이며 여전히 이국어에 능숙한 사람과 비교하여 교정이 필요합니다.

평가자 구성 및 평가 기준 버전은 번역 락파일에 반영됩니다. 평가를 활성화하거나 모델을 변경하거나 임계값을 조정하거나 평가를 제거하면 이전 번역은 다음 실행에서 유효하지 않게 됩니다. 제공자 키는 락파일에 제외됩니다.

## 인간 검토의 경계

모델 출력은 제안된 작업이며 자동 병합이 아닙니다. 설정 및 번역 활동은 Glossia 에서 유지되지만, 저장소 변경 사항은 팀의 검토를 위해 pull request 를 통해 게시됩니다. 이는 팀이 이미 코드에 사용하는 것과 같은 품질과 소유권 경계를 유지합니다.
