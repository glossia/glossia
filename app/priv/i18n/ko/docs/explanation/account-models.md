Glossia는 저장소 지침과 모델 제공업체 자격 증명을 분리합니다. 저장소는 번역할 대상을 정의하고, 계정은 작업을 수행할 [대규모 언어 모델](https://en.wikipedia.org/wiki/Large_language_model)을 결정합니다.

## 모델이 계정에 속해야 하는 이유

팀은 동일한 제공업체 관계를 사용해 여러 저장소를 번역하는 경우가 많습니다. 계정 범위 모델을 사용하면 관리자가 모든 저장소를 수정하지 않고도 제공업체 키를 교체하거나 기반 모델을 한 번에 변경할 수 있습니다.

또한 이 경계를 통해 자격 증명이 소스 제어에 포함되지 않도록 할 수 있습니다. 저장소에는 제공업체 키가 아니라 `translation-default` 같은 식별 가능한 핸들이 포함됩니다.

## 핸들로 안정적인 의도 유지

`GLOSSIA.md`의 `model` 필드는 계정 모델 핸들을 참조합니다.

```yaml
model: translation-default
```

핸들은 저장소의 의도를 나타냅니다. 관리자는 저장소 구성을 그대로 유지하면서 나중에 해당 핸들이 선택하는 제공업체 모델을 변경할 수 있습니다.

## 여러 모델의 사용 방식

Glossia는 각 문서 번역에 구성된 모델 하나를 사용합니다. 여러 모델을 추가해도 앙상블, 대체 체인 또는 자동 품질 등급이 생성되지 않습니다. 저장소 작성자는 `translation-default`, `long-form`, `japanese-specialist` 같은 안정적인 핸들을 통해 각 모델의 용도를 선택합니다.

선택은 문서와 대상 로케일의 컨텍스트 계층 구조를 따릅니다.

1. `model`을 선언한 가장 가까운 `GLOSSIA/<locale>.md` 파일이 해당 로케일에 적용됩니다.
2. 그렇지 않으면 `model`을 선언한 가장 가까운 `GLOSSIA.md` 파일이 해당 디렉터리에 적용됩니다.
3. 더 가까운 파일에서 모델을 선언하지 않은 경우 상위 `GLOSSIA.md` 설정을 상속합니다.
4. 적용 가능한 컨텍스트 파일에 핸들이 선언되어 있지 않으면 Glossia는 계정 기본값을 사용합니다.

명시적으로 구성한 핸들은 반드시 존재해야 합니다. Glossia는 알 수 없는 핸들을 계정 기본값으로 자동 전환하지 않고 오류를 보고합니다.

## 기본값 선택

프로젝트 설정에는 저장소 자체의 `GLOSSIA.md`이 생성되기 전에 모델이 필요합니다. 따라서 Glossia는 계정 기본값을 선택합니다. 계정에 처음 추가된 모델이 기본값이 되며, 관리자는 해당 모델의 설정 페이지에서 다른 모델을 기본값으로 지정할 수 있습니다.

저장소에 `GLOSSIA.md`이 생성된 후에는 명시적 핸들을 사용하여 검토자가 선택 사항을 명확하게 파악할 수 있습니다. `model`을 생략하면 저장소에서 계정 기본값을 계속 사용합니다.

## 사람의 검토 경계

모델 출력은 제안된 작업이며 자동으로 병합되지 않습니다. 설정 및 번역 활동은 Glossia에서 계속 확인할 수 있으며, 저장소 변경 사항은 팀이 검토할 수 있도록 풀 리퀘스트를 통해 게시됩니다. 이를 통해 팀이 코드에 이미 적용하고 있는 것과 동일한 품질 및 소유권 경계를 유지할 수 있습니다.
