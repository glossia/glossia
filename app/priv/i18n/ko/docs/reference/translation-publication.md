Glossia 는 프로젝트당 하나의 열린 번역 풀 리퀘스트를 유지합니다. 새 기본 브랜치 커밋은 각 소스 커밋마다 풀 리퀘스트를 개설하는 대신 해당 브랜치를 계속 이어갑니다. 이전 풀 리퀘스트가 병합되거나 닫힌 후 새 풀 리퀘스트가 생성됩니다.

배포 및 세션 교체는 서로 다른 애플리케이션 리플리카 또는 분리된 러너에서 실행되더라도 데이터베이스 기반 프로젝트 잠금을 공유합니다. 러너가 풀 리퀘스트를 생성했으나 메타데이터를 저장하지 못한 경우, 다음 배포는 먼저 GitHub 에서 열린 Glossia 풀 리퀘스트를 복원한 후에 또 다른 풀 리퀘스트를 생성합니다. 소스와 충돌하거나 소스 기록이 다시 작성되는 경우 열린 풀 리퀘스트는 방치되지 않으며 세션은 실패하고 기존 배포를 해결을 위해 유지합니다.

## 푸시 제한

제한은 **프로젝트당 1 시간당 4 푸시** 로 고정되어 있으며 세션 및 리플리카 간에 공유됩니다. 현재는 구성할 수 없습니다.

푸시는 고정된 시계 시간대별로 카운트하지 않고 균등하게 간격이 두릅니다. 브랜치 업데이트는 최소 15 분마다 이루어집니다. 다음 간위 예정 시도가 완료될 때 시작하므로 느린 배치 다음에 즉시 빠른 작업이 이어지지는 않습니다. 소스 브랜치 병합, 중간 배치, 재시도, 및 최종 플러시는 모두 동일한 예산을 공유합니다. 모호한 실패 시도는 슬롯도 소비합니다. 연결 실패 전에 GitHub 가 브랜치를 발전시킬 수 있기 때문입니다. 예산은 PostgreSQL 에 저장되며 새로운 세션이나 프로세스 재시작으로 재설정되지 않습니다.

## 배치

런은 검증된 파일 변경을 수집하고 25 개 파일 또는 15 분 후 배포를 요청합니다. 이 임계값은 푸시 제한을 우회하지 않습니다. 쿨링 기간 동안 추가된 완료된 파일들은 대기 중인 배치에 합류하며 같은 경로에 대한 반복된 변경은 최신 내용을 유지합니다.

런이 끝나면 최종 플러시는 동일한 예산을 기다립니다. 세션은 여전히 활성이며 대기 동안 심상을 보냅니다. 잠자고 있는 동안 데이터베이스 트랜잭션을 열어두지 않고 주기적으로 취소 및 승인을 다시 확인합니다.
