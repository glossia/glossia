Glossia 는 프로젝트당 하나의 열린 번역 풀 리퀘스트를 유지합니다. 새로운 기본 브랜치 커밋은 소스 커밋마다 풀 리퀘스트를 여는 것보다 해당 브랜치를 계속 진행합니다. 이전 풀 리퀘스트가 머지되거나 닫힌 후 새 풀 리퀘스트가 생성됩니다. 폐기된 발행 에는 새 브랜치 이름이 부여되며, 동일한 소스 커밋을 재시도 하는 경우 포함되며; 거절된 출력물은 완료된 작업으로 재사용되지 않습니다.

소스 동기화는 평가 전 임시 로컬 체크아웃 에서 수행되어 열린 브랜치의 완료된 번역과 락 파일 을 보존합니다. 출력이 없거나 락 파일 변경 이 없는 경우, 런 은 기본 브랜치와 포착하기 위해 원격 브랜치를 단순히 이동하지 않으며, 발행 슬롯 을 소모하지 않습니다. 배치가 준비되면, 소스 동기화와 검증된 변경 사항 들은 비강제 브랜치 업데이트 하나로 함께 발행됩니다. 해당 커밋 은 이전 발행 과 평가된 소스 커밋 을 조상으로 모두 보유합니다.

발행 및 세션 교체 는 데이터베이스 기반 프로젝트 락 을 공유하며, 다른 애플리케이션 리플리카 또는 분리된 러너 에서 실행되는 경우도 포함됩니다. 러너 가 풀 리퀘스트 를 생성했으나 메타데이터 저장 에 실패한 경우, 다음 발행 은 생성하기 전에 GitHub 에서 열린 Glossia 풀 리퀘스트 를 복원합니다. 열린 풀 리퀘스트 는 브랜치와 소스 충돌 시 또는 소스 히스토리 재작성 시에도 버려지지 않으며, 세션 실패 시 기존 발행을 충돌 해결을 위해 유지합니다.

## 푸시 한도

한도는 **프로젝트당 시간당 4 회 푸시** 로 고정되어 있으며, 세션 과 리플리카 전체 로 공유됩니다. 현재 설정할 수 없습니다.

푸시는 고정된 시간 단위 에 의해 집계되지 않고 일정 간격으로 배치됩니다. 브랜치 업데이트 는 최소 15 분 간격입니다. 발행 시도가 완료될 때 다음 인터벌 이 시작되면서, 느린 배치 는 즉시 빠른 배치 전에 이어질 수 없습니다. 중간 배치, 재시도 및 최종 플러시 는 모두 동일한 예산 을 공유합니다. 모호한 실패 시도 역시 슬롯 을 소모하며, 연결 실패 전에 GitHub 가 브랜치를 진행했을 수 있기 때문입니다. 예산 은 PostgreSQL 에 저장되며 새 세션 또는 프로세스 재부팅 으로 초기화되지 않습니다.

발행 전, Glossia 는 원격 HEAD 를 다시 읽어서 세션의 소스를 로컬에 다시 병합합니다. 이렇게 하면 이전 배치를 보존하고 브랜치를 이동하지 않고 충돌을 탐지할 수 있습니다. 이전 업데이트 가 성공했으나 응답 이 손실된 경우, 이미 존재하는 변경 사항은 다시 커밋하지 않으며, 발행 메타데이터 와 풀 리퀘스트 는 다른 브랜치 업데이트 없이 복원됩니다. ref 가 생성되었으나 러너 가 자신의 풀 리퀘스트 를 생성하기 전에 중단한 경우, 변경 사항이 없는 평가 는 여전히 누락된 풀 리퀘스트 를 생성하며, 브랜치 업데이트 슬롯 을 소모하지 않습니다.

예상 동기화 트리 와 의 차이 가 대기 중인 배치 의 일부 인 경우에만 의도치 않은 원격 진전 이 허용됩니다. 평가 도중 에 수행 된 다른 편집 사항들은 오래된 입력 을 기반으로 검증된 번역 발행 대신, 발행 실패 합니다. 기존 풀 리퀘스트 는 해결을 위해 유지됩니다.

## 배치

런 은 검증된 파일 변경 사항을 수집하고 25 개 파일 또는 15 분 후 발행 을 요청합니다. 이러한 임계치는 푸 시 한도를 우회하지 않습니다. 냉각 기간 동안 추가 완료된 파일 이 대기 중인 배치 에 합류하며, 동일한 경로 에 반복된 변경 사항 은 최신 콘텐츠 를 유지합니다.

런 종료 시, 최종 플러시 는 동일한 예산 을 기다립니다. 세션 은 활성 상태를 유지하며 대기 동안 심박 신호를 보냅니다. 잠복 중 에 데이터베이스 트랜잭션을 열어두지 않고 주기적으로 취소 및 진입 을 재확인합니다.
