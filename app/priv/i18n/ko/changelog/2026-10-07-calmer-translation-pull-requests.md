%{
  title: "더 차분한 번역 풀 리퀘스트",
  summary: "활발한 저장소에 Glossia 를 적용했을 때 배운 점, 그리고 이로 인해 번역 풀 리퀘스트 가 어떻게 바뀌었는지"
}
---

당신의 도구가 실제 저장소에 처음 접했을 때 많이 배웁니다. 우리에게 그것은Tuist 였습니다. 그들의 팀은 하루에 `main` 로 여러 번 병합을 하고, Glossia 는 우리가 그걸 위해 만든 대로 정확히 수행했습니다. 모든 변경사항을 번역하고 준비되자마자 파일을 푸시했습니다. 그 결과 거의 모든 병합마다 새로운 pull request 가 발생했고, 각각 약 150 개의 커밋을 포함하며, 누구도 요청하지 않았던 체크들로 가득 찬 CI 큐가 나타났습니다. 일부 문서 페이지에서도 컴포넌트와 경고가 평문으로 구조를 잃고 돌아왔습니다. 우리가 계속 이야기하는 조용한 배경 경험은 아닙니다.

그것은 우리를 상처받게 만들었습니다. 우리는 항상 최고의 번역 시스템은 생각할 필요가 없는 것이라고 말했기 때문입니다. CI 를 범람하거나 문서를 망가뜨리는 pull request 는 그 반대입니다. 그래서 우리는 다시 번역이 저장소에 도달하는 방식을 되돌아보다가 예상했습니다.

Glossia 는 이제 프로젝트당 하나의 pull request 를 유지하며 콘텐츠가 변경될 때마다 이를 확장합니다. 해당 브랜치에 이미 있는 lock 파일을 읽기 때문에, 새로운 것만 번역하고 파일 하나하나가 아닌 배치로 푸시합니다. Tuist 와 같은 저장소의 경우, 이전에는 150 번에 달했던 푸시가 이제 몇 번으로 줄었습니다.

우리는 또한 우리가 다루지 않아도 되는 문서의 일부도 손을 대지 않았습니다. Glossia 는 과거에 번역한 모든 페이지를 다시 구축했습니다. 그런데 완벽하게 이해하지 못한 것, 예를 들면 Phoenix 컴포넌트나 GitHub 경고는 번역 후에도 구조 없이 나올 수 있었습니다. 이제 번역한 문장만 교체하고 나머지는 작성하신 대로 그대로 둡니다. 우리가 예상하지 못했던 좋은 부작용은 rodas: 모델이 이제 전체 문장과 페이지의 나머지를 보았기 때문에 번역이 더 잘 읽힙니다. 일본어에서는 이제 링크가 영어 문장에 있던 자리에서 위태롭게 맞춰져 있을 필요가 없습니다.

마지막으로, pull request 는 이제 일어났던 일을 알려줍니다. 어떤 언어와 파일이 번역되었는지, 어느 커밋에서 왔는지, 성과는 어떻게었고, 어떤 전문 용어들이 영향을 미쳤는지, 그리고 만약 있다면 무엇이 주목해야 하는지 알려줍니다. 우리는 그것이 검토 요청하기 전에 신중한 동료에게 남기는 메모와 같다고 생각합니다.

Tuist 팀이 우리가 이를 파악하는 동안 보여준 인내심에 감사드립니다. Glossia 가 언제든 이렇게 여러분에게 방해가 된다면 그 이야기를 듣고 싶습니다.
