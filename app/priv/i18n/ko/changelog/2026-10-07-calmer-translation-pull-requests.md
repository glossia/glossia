%{
  title: "차분한 번역 풀 리퀘스트",
  summary: "자주 변경되는 리포지토리에 Glossia 를 풀어놓고 배운 점과, 그 결과 번역 풀 리퀘스트가 어떻게 변했는지."
}
---

처음 도구가 실제 저장소를 마주할 때 많은 것을 배울 수 있습니다. 우리에게 그 대상은 Tuist 였습니다. 그들의 팀은 `main` 로 매일 여러 번 병합하며, Glossia 는 우리가 설계한 대로 작동했습니다: 모든 변경 사항을 번역하고 준비되자마자 각 파일을 푸시했습니다. 결과적으로 거의 모든 병합마다 새로운 PR 이 생성되었으며, 각각 약 150 개의 commit 을 포함하고 있었으며, 아무도 요청하지 않은 체크들로 가득 찬 CI 대기열이었습니다. 일부 문서는 컴포넌트와 알림이 평문으로 누출되어 돌아왔습니다. 우리가 계속 이야기하는 조용한 배경 처리 경험은 아니었습니다.

그것은 우리를 당황시켰습니다. 우리는 항상 생각할 필요 없는 것이 최고의 번역 시스템이라고 말해왔기 때문입니다. CI 에 과부하를 주거나 문서를 망가트리는 PR 은 정반대입니다. 그래서 우리는 번역이 저장소에 도달하는 방식을 다시 고려했습니다.

Glossia 는 이제 프로젝트당 하나의 PR 을 유지하며 콘텐츠가 변경됨에 따라 이를 확장합니다. 이미 해당 브랜치에 있는 lock 파일들을 읽기 때문에 새로 추가된 것만 번역하고 파일 하나씩 푸시가 아닌 배치로 푸시합니다. Tuist 같은 저장소의 경우 예전에는 150 회 푸시였지만 이제는 손에 꼽을 수 있는 몇 회로 줄어듭니다.

우리는 건드리지 않는 문서 일부도 건드리지 않습니다. Glossia 는 이전엔 번역한 모든 페이지를 다시 구축했고, 완전히 이해할 수 없는 내용, 예를 들어 Phoenix 컴포넌트나 GitHub alert 는 다른 쪽으로 누출될 수 있었습니다. 이제 번역한 문장만 교체하고 나머지는 작성하신 대로 정확히 유지합니다. 우리가 예상하지 못했던 좋은 부수효과가 있습니다: 모델이 이제 전체 문장과 페이지의 나머지 부분을 보게 되니 번역문이 더 읽기 좋습니다. 일본어에서 이제 링크가 영어 문장 안에 어색하게 위치하지 않아도 됩니다.

결국 PR 은 이제 어떤 일이 생겼는지 알려줍니다. 어떤 언어와 파일이 번역되었으며, 어떤 commit 에서, 점수가 어떻게 나왔는지, 어떤 glossary 용어가 이를 결정했는지, 그리고 만약 있다면 주의가 필요하다는 사항까지입니다. 우리는 이를 리뷰 요청 전에 신중한 동료님이 작성해 놓는 메모와 같습니다.

Tuist 팀의 인내심에 감사드립니다. 만약 Glossia 가 이런 방식으로 당신에게 방해가 된다면, 그 이야기를 들려주길 바랍니다.
