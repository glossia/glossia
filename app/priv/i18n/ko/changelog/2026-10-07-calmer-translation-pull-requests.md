%{
  title: "더 차분한 번역 풀 리퀘스트",
  summary: "수정이 잦은 레포지토리에 Glossia 를 풀어놓으며 배운 점, 그리고 이로 인해 번역 풀 리퀘스트가 어떻게 변했는지"
}
---

도구와 실제 저장소를 처음 마주할 때 많은 것을 배웁니다. 우리에게는 Tuist 가 그랬습니다. 그들의 팀은 하루에 여러 번 `main` 에 병합하고, Glossia 는 우리가 지향했던 대로 작동하여 모든 변경사항을 번역한 뒤 파일마다 즉시 푸시했습니다. 그 결과는 거의 모든 병합마다 새 Pull request 가 생기고 각각 약 150 개의 커밋과 아무도 요청하지 않았던 검사가 가득 찬 CI 대기열이 되었습니다. 일부 문서 페이지도 컴포넌트와 알림이 일반 텍스트로 새어 나오는 경우도 있었죠. 우리가 계속 이야기하는 조용하고 배경 처리 경험이 아닙니다.

그것은 우리를 아팠습니다. 우리는 늘 최고의 번역 시스템은 생각할 필요가 없는 것이라고 말해왔습니다. CI 를 마비시키거나 문서를 망가뜨리는 Pull request 는 그 반대입니다. 그래서 우리는 다시 돌아와 번역이 저장소에 도달하는 방식을 재고했습니다.

Glossia 는 이제 프로젝트마다 하나의 Pull request 를 유지하며 콘텐츠가 변경될 때마다 확장합니다. 해당 브랜치에 이미 있는 lock 파일도 읽기 때문에 새로 추가된 것만 번역하며, 파일 하나씩이 아닌 배치로 푸시합니다. Tuist 와 같은 저장소의 경우, 예전에 150 회가 있던 푸시는 이제 몇 번으로 줄었습니다.

우리는 또한 다룰 필요 없는 문서 부분을 건드리지 않는 멈춤을 했습니다. Glossia 는 이전까지 번역한 모든 페이지를 다시 빌드했고, 완전히 이해하지 못한 부분, 예를 들어 Phoenix 컴포넌트나 GitHub alert 는 가장자리에서 일반 텍스트로 새어 나올 수 있었죠. 이제 번역한 문장만 교체하고 나머지는 작성하신 그대로 둡니다. 우리가 기대치 못했던 좋은 효과도 있었습니다: 모델이 이제 전체 문장과 페이지 나머지를 보게 되므로 번역이 더 자연스럽습니다. 일본어에서는 링크가 이제 영어 문장 내에서 어색하게 자리 잡고 있을 필요가 없습니다.

마지막으로, Pull request 는 이제 무슨 일인지 알려줍니다. 어떤 언어와 파일이 번역되었는지, 어떤 커밋에서 왔는지, 결과가 어떻게 나왔는지, 어떤 Glossary 용어가 영향을 미쳤는지, 그리고 만약 있다면 주의가 필요한 부분까지. 우리는 이것이 심층 요청 전에 주의 깊은 동료가 남기는 메모와 같습니다.

이 문제를 해결하는 과정에서 Tuist 팀의 인내에 감사드립니다. Glossia 가 이런 식으로 여러분에게 방해된다면, 우리는 이를 듣고 싶습니다.
