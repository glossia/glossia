  summary: "수정이 잦은 레포지토리에 Glossia 를 풀어놓으며 배운 점, 그리고 이로 인해 번역 풀 리퀘스트가 어떻게 변했는지"
}
---
도구는 실제 저장소를 처음 마주할 때마다 많은 것을 배웁니다. 우리에게 그것은 Tuist 였습니다. 그들의 팀은 하루에 `main` 브랜치로 여러 번 병합하며, Glossia 는 우리가 만들어둔 대로 정확히 작동했습니다. 모든 변경 사항을 번역하고 준비되자마자 각 파일을 푸게 했죠. 결과로 거의 모든 병합마다 새로운 pull request 가 생성되고, 각각 150 개 정도의 커밋이 있었으며, 아무도 요청하지 않은 체크들로 가득 찬 CI 대기열이 있었습니다. 그들의 문서 페이지 일부에서는 컴포넌트와 경보가 평문 텍스트로 방출된 상태로 돌아왔습니다. 우리가 계속 이야기하는 조용하고 배경 같은 경험도 아닙니다.

그게 좀 아팠죠. 왜냐하면 우리 항상 최고의 번역 시스템은 고려할 필요가 없는 것이라고 말했기 때문입니다. CI 를 물처럼 가득 채우거나 문서를 망가뜨리는 pull request 는 그 반대입니다. 그래서 우리는 다시 와서 번역이 저장소에抵达하는 방식에 대해 다시 생각했습니다.

이제 Glossia 는 프로젝트당 하나의 pull request 만 유지하며, 내용이 바뀌면 이를 확장합니다. 이미 그 브랜치에 있는 lock 파일을 읽기 때문에, 새로운 것만 번역하고 파일 하나하나로가 아닌 배치 단위로 푸는 방식으로 작동합니다. Tuist 처럼 저장소를 사용할 경우, 과거에는 150 회에 달했던 것이 이제는 수 개 정도의 푸시만큼만 됩니다.

우리 또한 당신의 문서에서 우리가 건드릴 수 없는 곳을 건드리는 것을 멈췄습니다. Glossia 는 과거에 번역한 모든 페이지를 다시 빌드했는데, 완전히 이해하지 못한 것들, 예를 들어 Phoenix 컴포넌트나 GitHub 경고는 다른 쪽에서 평문으로 누출될 수 있었습니다. 이제 번역한 문장만 교체하고 나머지는 당신처럼 작성한 그대로 둡니다. 우리가 예상치 못했던 좋은 부수 효과 가 있었습니다: 모델이 이제 전체 문장과 페이지 나머지 부분을 보게 되었기 때문에, 번역이 더 읽기 좋습니다. 일본어에서 링크는 이제 영문 문장에서의 어색한 위치에서 머물러 있을 필요가 없습니다.

마지막으로, pull request 는 이제 일어난 일을 알려줍니다. 어떤 언어와 파일이 번역되었으며, 어떤 커밋에서 이유로 진행되었고, 점수가 어떻게 되었는지, 어떤 어휘 용어가 내용을 형성했는지, 그리고 어떤, 혹 있다면 주의가 필요한지 것입니다. 우리는 이것이 신중한 동료들이 검토를 요청하기 전에 당신에게 남기는 메모인 것처럼 생각합니다.

이 문제를 이해하는 동안 Tuist 팀의 인내심에 감사드립니다. Glossia 가 만약 이런 식으로 당신의 일을 방해하게 된다면, 우리는 그것을 들어드리고 싶습니다.
