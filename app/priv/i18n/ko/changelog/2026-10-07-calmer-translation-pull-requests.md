%{
  title: "더 차분한 번역 병합 요청",
  summary: "바쁜 저장소에 Glossia 를 마음껏 활용해본 경험에서 배운 점과, 이로 인해 번역 병합 요청이 어떻게 변화했는지"
}
---

도구와 실제 저장소를 처음 마주할 때 많이 배웁니다. 우리에게 이 첫 만남은 Tuist 였습니다. 그들의 팀은 매일 `main` 으로 여러 번 병합하고, Glossia 는 우리가 그것을 위해 만들고자 했던 대로 정확히 작동했습니다: 모든 변경 사항을 번역하고 준비되는 즉시 각 파일을 푸시했습니다. 그 결과 거의 모든 병합마다 새로운 Pull Request 가 생성되었고, 각각 약 150 개의 커밋이 있으며, 아무도 요구하지 않았던 체크들이 가득한 CI 큐였습니다. 그들의 문서 페이지 중 일부도 컴포넌트와 경고가 일반 텍스트로 도출되어 깨졌습니다. 우리가 계속 이야기하는 조용한 배경 경험은 아니었습니다.

그것은 우리의 자존심에 상했습니다. 왜냐하면 우리는 항상 최고의 번역 시스템은 생각할 필요가 없는 것이라고 항상 말했기 때문입니다. CI 를 물증하거나 문서를 망가뜨리는 Pull Request 는 그 반대입니다. 그래서 우리는 다시 돌아와 번역이 당신의 저장소에 도달하는 방식을 다시 고려했습니다.

Glossia 는 이제 각 프로젝트마다 하나의 Pull Request 만 유지하며 콘텐츠가 변경됨에 따라 그것을 확장합니다. 이미 해당 브랜치에 있는 lock 파일 을 읽어서 새로 추가된 만 번역하고 파일 하나하나 대신 배치로 푸시합니다. Tuist 의 영구제와 같이, 이전에는 150 회에 달했던 푸시가 이제 소수의 몇 번으로 축소됩니다.

우리는 이제يقاف 맞춰서 우리의 능력이 닿지 않는 문서 부분을build 하지 않았습니다. Glossia 는 예전마다 번역한 각 페이지를 재생성했는데, 완벽이 이해하지 못했던 것, 예를 들어 Phoenix 컴포넌트나 GitHub 경고, 같은 것들이 다른 쪽에서 도출되어 깨진 채로 돌아올 수 있었습니다. 이제 그것은 단지 번역한 문장만 교체하고 나라는 것은 당신이 쓴 그대로 그대로 두었습니다. 우리가 예상하지 못했던 좋은 부작용이 있었습니다. 현재 모델은 더 이상 전체 문장 일부와 페이지의 나머지를 보므로 번역이 더 읽기 편한 자연스러움을 갖습니다. 일본어에서 링크가 이제 영어 문장에서 어색한 곳에 가게 될 필요가 없습니다.

마지막으로, Pull Request 는 이제 무엇을 알려줍니다. 어떤 언어와 파일이 어떤 커밋에서 번역되었으며, 그 점수가 어떻게 되었고, 어떤 사전 용어가 그 모양을 형성했으며, 무엇이든 주의가 필요한지 알려줍니다. 우리는 그것을 심사 요청 전에 주의 깊은 동료이던 세심한 스승님이 남기라고 생각됩니다.

이 문제를 해결하는 동안 Tuist 팀의 인내심에 감사드립니다. 만약 Glossia 가 당신의 길에 이렇게 걸리게 된다면, 우리는 그것이 무엇인지 듣기를 기꺼이 합니다.
