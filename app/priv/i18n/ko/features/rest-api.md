## 개발자 우선

REST API 는 Glossia 의 핵심입니다. 대시보드, CLI, 그리고 [MCP 서버](/features/mcp-server) 는 모두 동일한 엔드포인트를 사용합니다. 새로운 기능을 추가할 경우 API 에 먼저 적용되며, 그 다음 모든 곳에서 제공됩니다.

즉, UI 에 의해 제한받지 않습니다. CI/CD 통합부터 사용자 지정 대시보드까지, 상상이 되는 모든 워크플로우를 동일한 안정적이고 문서화된 인터페이스 위에 구축할 수 있습니다.

## 인증

Glossia 는 모든 API 인증에 OAuth 2.1 과 PKCE 를 사용합니다. 이 흐름은 1 차와 3 차 클라이언트를 모두 지원합니다. 전체 안내를 보려면 [인증 및 권한 부여 문서](/docs/reference/apis/authentication) 를 참조하세요.

**동적 클라이언트 등록** -- 클라이언트는 리디렉션 URI 와 승인 유형을 사용하여 `/oauth/register` 에서 프로그램 방식으로 등록합니다. 수동 승인 단계는 없으며, 포털을 클릭할 필요도 없습니다.

**PKCE 권한 부여 코드** -- 사용자는 브라우저 기반 동의 화면을 통해 클라이언트를 승인합니다. PKCE 확장은 비밀을 저장할 수 없는 공개 클라이언트로도 토크를 안전하게 유지하도록 보장합니다.

**토큰 수명** -- 액세스 토큰은 표준 OAuth 엔드포인트를 통해 교환, 조회, 취소할 수 있습니다. 토큰 엔드포인트의 속도 제한은 무차별적 공격으로부터 보호합니다.

## 권한 부여

접근 제어는 두 레이어를 사용합니다. [인증 문서](/docs/reference/apis/authentication) 는 범위, 역할, 그리고 전체 권한 행렬을 자세히 다룹니다.

**범위** 는 토큰이 액세스 가능한 리소스 카테고리를 정의합니다. `voice:read` 를 가진 토크는 음성 구성을 읽을 수 있지만 수정할 수는 없습니다. `resource:action` 패턴을 따르며 `account:read`, `organization:write`, `glossary:admin` 는 용어집 관리용이며 그 외에도 있습니다.

**정책** 은 사용자와 특정 리소스 간의 관계를 확인합니다. 올바른 범위를 가진 유효한 토크조차 사용자가 소속되지 않은 조직에는 액세스할 수 없습니다. 모든 요청은 두 레이어에 대해 확인됩니다.

## 페이징, 필터링, 그리고 정렬

모든 목록 엔드포인트는 일관된 메타데이터를 포함한 페이징 된 결과를 반환합니다:

각 응답은 `total_count`, `total_pages`, `current_page`, `page_size`, `has_next_page?`, 및 `has_previous_page?` 를 포함하여 클라이언트가 추측 없이 페이징 제어를 구축할 수 있습니다.

인덱스된 필드를 필터링하려면 `filters[field]=value` 쿼리 매개변수를 사용합니다. 오름차순 또는 내림차순 정렬하려면 `order_by[]` 매개변수를 사용합니다. 모든 리소스에서 인터페이스는 동일합니다.

## OpenAPI 와 대화형 문서

전체 OpenAPI 3.1 규정은 `/api/openapi.json` 에서 제공됩니다. [대화형 API 참조](/docs/reference/apis/rest) 는 Scalar 를 통해 엔드포인트 탐색, 스키마 확인, 브라우저에서 직접 테스트 요청을 생성할 수 있습니다.

언어에 관계없이 클라이언트 라이브러리는 해당 규격에서 생성할 수 있습니다. 계약은 버전화되어 안정적이므로, 새로운 기능이 출시되어도 통합이 끊어지지 않습니다.
