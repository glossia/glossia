## 개발자 우선

REST API 는 Glossia 의 핵심입니다. 대시보드, CLI, 그리고 [MCP 서버](/features/mcp-server) 모두 동일한 엔드포인트를 사용합니다. 새로운 기능을 추가하면 API 에 먼저 등록되며 그곳에서 다른 모든 곳에서 노출됩니다.

이는 UI 에 의해서만 제한되지 않음을 의미합니다. 상상할 수 있는 모든 워크플로우, CI/CD 통합부터 맞춤형 대시보드까지, 동일한 안정적이고 문서화된 인터페이스 위에 구축할 수 있습니다.

## 인증

Glossia 는 모든 API 인증에 OAuth 2.1 와 PKCE 를 사용합니다. 인증 흐름은 1 차 및 3 차 클라이언트 모두를 지원합니다. 다음은 [인증 및 권한 부여 문서](/docs/reference/apis/authentication) 전체 워크스루를 위해.

**동적 클라이언트 등록** -- 클라이언트는 프로그램 방식으로 등록됩니다. `/oauth/register` 그들의 리디렉션 URI 와 권한 유형과 함께. 수동 승인 단계 없이, 포털 클릭이 필요 없습니다.

**PKCE 를 활용한 인증 코드** -- 사용자는 브라우저 기반 동의 화면을 통해 클라이언트를 승인합니다. PKCE 확장은 비밀을 저장할 수 없는 공개 클라이언트에게도 토큰이 안전하도록 보장합니다.

**토큰 수명 주기** -- 액세스 토큰은 표준 OAuth 엔드포인트를 통해 교환, 검토, 철회될 수 있습니다. 토큰 엔드포인트의 속도 제한은 무차별 공격을 방지합니다.

## 권한 부여

접근 제어는 두 계층을 사용합니다. 이 [인증 문서](/docs/reference/apis/authentication) 권한 범위, 역할, 및 전체 권한 매트릭스를 상세히 다룹니다.

**범위** 토큰이 접근 가능한 리소스 범주를 정의합니다. 특정 권한을 가진 토큰은 `voice:read` 읽을 수는 있지만 수정은 불가능합니다. 범위는 다음 `resource:action` 패턴: `account:read`, `organization:write`, `glossary:admin` 용어 관리 등을 위해,

**정책** 사용자와 특정 리소스 간의 관계를 확인합니다. 올바른 범위를 가진 유효한 토큰이라도 사용자에게 소속되지 않은 조직에 액세스할 수 없습니다. 모든 요청은 두 레이어 모두에 대해 확인됩니다.

## 페이징, 필터링, 정렬

모든 목록 엔드포인트는 일관된 메타데이터와 함께 페이징된 결과를 반환합니다:

각 응답에는 포함됩니다 `total_count`, `total_pages`, `current_page`, `page_size`, `has_next_page?`, 그리고 `has_previous_page?` 따라서 클라이언트는 추측하지 않고 페이징 컨트롤을 구축할 수 있습니다.

인덱싱된 필드를 사용하여 필터링 `filters[field]=value` 쿼리 매개변수입니다. 오름차순 또는 내림차순으로 정렬 `order_by[]` 매개변수입니다. 인터페이스는 모든 리소스에서 동일하게 유지됩니다.

## OpenAPI 및 인터랙티브 문서

전체 OpenAPI 3.1 규격은 다음에서 제공합니다. `/api/openapi.json`. 해당 [인터랙티브 API 참조](/docs/reference/apis/rest) Scalar 로 구동되며 브라우저에서 직접 엔드포인트를 탐색하고, 스키마를 검사하며, 테스트 요청을 보낼 수 있습니다.

어떤 언어든 클라이언트 라이브러리는 사양에서 생성할 수 있습니다. 계약은 버전 관리를 통해 안정적이므로 새 기능이 출시되더라도 귀사의 연동은 중단되지 않습니다.
