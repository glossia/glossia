## 개발자 우선

REST API 가 Glossia 의 뼈대입니다. 대시보드, CLI, 와 [MCP server](/features/mcp-server)는 모두 동일한 엔드포인트를 사용합니다. 새로운 기능을 추가할 때, 먼저 API 에 배치되고 그 이후 모든 곳에서 노출됩니다.

이것은 UI 에 의해 제한되는 것이 절대 아니라는 뜻입니다. CI/CD 통합부터 사용자 지정 대시보드까지 상상할 수 있는 어떤 워크플로우든 동일한 안정적인 문서화된 인터페이스 위에 구축할 수 있습니다.

## 인증

Glossia 는 모든 API 인증에 OAuth 2.1 과 PKCE 를 사용합니다. 이 플로우 는 1 차 클라이언트와 3 자 클라이언트를 모두 지원합니다. 전체 walkthrough 에는 [인증 및 권한 부여 문서](/docs/reference/apis/authentication)를 참조하세요.

**동적 클라이언트 등록** -- 클라이언트는 리디렉션 URI 와 부여 유형과 함께 프로그래마틱은 `/oauth/register`에서 등록합니다. 수동 승인 단계가 없으며 측은 침해해야 하는 포털도 없습니다.

**PKCE 와 인증 코드** -- 사용자는 브라우저 기반 동의 화면을 통해 클라이언트를 승인합니다. PKCE 확장어는 비밀을 저장할 수 없는 공개 클라이언트에서도 토큰이 안전하게 유지되도록 보장합니다.

**토큰 생명 주기** -- 액세스 토큰은 표준 OAuth 엔드포인트를 통해 교환하고, 심문하고, 주의할 수 있습니다. 토큰 엔드포인트에 대한 제한은 브루포스 공격을 방지합니다.

## 권한 부여

접근 제어는 두 계층을 사용합니다. [인증 문서](/docs/reference/apis/authentication) 는 범주, 역할, 및 전체 권한 매트릭스에 대해 상세합니다.

**범위** 는 토큰이 접근할 수 있는 리소스 범주 를 정의합니다. `voice:read` 토큰을 가진 경우 voice 구성 을 읽을 수는 있지만 수정할 수는 없습니다. 범위는 `resource:action` 패턴을 따릅니다: `account:read`, `organization:write`, `glossary:admin` 표시어 관리를 위해 및 이에тый 수 있습니다.

**정책**는 사용자와 특정 리소스 간의 관계를 검증합니다. 올바른 범위를 가진 유효한 토큰이지만 사용자에게 관계를 않는 조직에 접근할 수 없습니다. 모든 요청은 두 계층 모두에 대해 체크됩니다.

## 페이징, 필터링, 및 정렬

모든 목록 엔드포인트는 일관된 메타데이터로 페이징된 결과를 반환합니다:

매 응답은 `total_count`, `total_pages`, `current_page`, `page_size`, `has_next_page?`, 및 `has_previous_page?`을 포함하므로 클라이언트는 추측하지 않고 페이징 제어를 구축할 수 있습니다.

인덱스 필드는 `filters[field]=value` 쿼리 파라미터를 사용하여 필터링합니다. 오름차순 또는 내림차순은 `order_by[]` 파라미터를 사용합니다. 인터페이스는 모든 리소스에서 동일합니다.

## OpenAPI 와 인터랙티브 문서

전체 OpenAPI 3.1 사양은 `/api/openapi.json`에서 사용할 수 있습니다. [인터랙티브 API 참조](/docs/reference/apis/rest)는 Scalar 로 지원되며 엔드포인트를 탐색하고 스키마를 검사하며 브라우저에서 직접 테스트 요청을 만들 수 있습니다.

언어별 클라이언트 라이브러리는 사양으로 생성될 수 있습니다. 계약은 버전 관리되어 안정적이므로 새로운 기능을 출시할 때 통합이 깨지지 않습니다.
